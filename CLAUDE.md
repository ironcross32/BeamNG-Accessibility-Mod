# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

BEAM is a screen reader mod for BeamNG.drive — an accessibility tool that converts real-time vehicle telemetry into audio cues, spatial compass clicks, and speech output for blind and visually impaired players. It runs on Windows 10+ and requires administrator privileges (for keyboard hooks).

## Build & Run Commands

**Package manager:** uv (with `uv.lock` for deterministic resolution)

```bash
# Install dependencies
uv sync

# Run main telemetry receiver (requires admin)
python beamtel.py

# Run configuration GUI
python configurator.py

# Run diagnostic listeners
python diagnostic/beam_listener.py
python diagnostic/diagnostic_listener.py
```

**Build executables with Nuitka** (build settings are embedded as Nuitka pragmas at the top of each file):
```bash
nuitka beamtel.py
nuitka configurator.py
```

There are no tests in this codebase.

## Architecture

### Two-Part System

The project has two halves that communicate via UDP:

1. **Python side** (this repo root) — Receives telemetry, generates audio, handles speech output
2. **Lua mod** (`bng_mod/`) — A directory junction to `%LOCALAPPDATA%/BeamNG/BeamNG.drive/current/mods/unpacked/bng_screenreader_mod/`. Edits to `bng_mod/` are live in the game.

### Python Components

- **beamtel.py** — Main entry point. UDP telemetry listener, keyboard command system (F9 hotkey + modifier combos), drives audio and speech.
  - **The alignment readout is one key with three answers.** `F9` `I` speaks the cannon's firing state when `cannon_active` (you are sitting in a ramp machine), otherwise the docking readout, otherwise "instrument is off". Cannon-first because once you are in the cannon the alignment task is over and the aiming task has begun; folded into the existing key rather than given a binding of its own, for the same reason the slam gate rides on the docking toggle. `_dock_phrase` dispatches on the mode to `_dock_phrase_impl` (unchanged, and `dock_readout_sim.py` scenario 16 asserts it is byte-identical to before the split) or `_dock_phrase_ramp`, which shares none of its vocabulary — there is no band, no thickness, and nothing on a car that goes up or down.
  - **`cannon_active` is derived from geometry, not from a jbeam name allowlist.** `rampGeometry` resolving a ramp on the *player's own* vehicle is exactly the signal, pushed as `CANNON:0|1`. The two aiming values then come free off existing telemetry, because large_cannon's controller publishes them there itself: `electrics.values.rpm = targetInclination * 1000` and `electrics.values.gear = "<strength>%"`.
  - **That gear abuse is also a regression, and is suppressed rather than tolerated.** The cannon rewrites the gear string on *every* press of the strength keys, so without a `cannon_active` gate on the gear-change announcement, aiming produces a stream of `extended_gear_to_phrase("80%")` across the whole manoeuvre. The strength is not lost — `F9` `I` reads it on demand, which is the right shape for a value you sweep and then check. (The swept `rpm` needs no such gate: it never reaches `audio.py`, and the shift tone is driven by the `DL_SHIFT` dashboard bit, which a cannon has no engine to set.)
  - **The mode latch is not cleared on `DOCKCLEAR`/`DOCKFAIL`.** Losing the target is not a change of mode, and clearing it there re-announces every time you drift across the feed's edge — measured at twenty announcements for one approach. Only a part swap, a vehicle change or the toggle resets it, and the toggle claims the latch itself so it and the listener cannot both announce the same change. `implement_proximity_sim.py` scenario 12 asserts both halves.
  - **The `DOCK:` parse ladder must be `elif`, not a second `if`.** A successful 15-field split leaves `len == 15`, which is also `!= 13`, so an independent second test immediately re-splits it down to 11 and throws the mode and margin away on every ramp packet.
- **audio.py** — Procedural audio synthesis engine. Real-time stereo 48kHz float32 via `sounddevice` callback. Compass clicks, shift/TC/steering tones, warning buzzers, drift alerts, heading guidance, scanner beeps, obstacle detection tones.
  - **Articulation / hydraulic steering tone** — for machines whose steering does not self-centre (the WL-40 wheel loader bends its frame with a pair of opposed rams, so releasing the joystick leaves it bent). Driven by `actualSteering`, which is **0.0 on every vehicle with normal self-centring steering** — that is what auto-detects the hydraulic ones, so nothing here needs a per-vehicle check. Pitch (`HYDRO_STEER_LO_HZ`→`HI_HZ`) and level (`MIN_DB`→`MAX_DB`) rise with the offset, HRTF azimuth tracks it out to `HYDRO_STEER_MAX_AZIMUTH_DEG`, and the voice is **FM** rather than a sine because the loader itself is loud enough to bury one. The C:M ratio glides from an exact 2.0 near straight (sidebands land on harmonics — clean) to a non-integer 2.76 at full lock (off-harmonic — rough), with the modulation index rising alongside, so being badly off-centre *sounds* wrong rather than merely higher. Ratio and index follow `norm ** HYDRO_STEER_FM_DIRT_CURVE`, **not** `norm` — scaling them linearly is piercing in normal use, because half lock already lands at ratio 2.38 and a 1.5 kHz centroid. Cubed, the ratio holds within ~0.1 of the integer through the middle of the range and only goes wild in the last quarter. Pitch stays linear in `norm`; it's only the timbre that's curved. **`HYDRO_STEER_MAX_AZIMUTH_DEG` must stay well under 90°** (75° now): the KEMAR set's interaural level difference peaks near 67.5° and then *falls* about 5 dB out to 90°, so mapping full lock to 90° made turning harder past ¾ lock read as the sound coming back toward centre. The sim asserts this. Note the azimuth scales on raw `actual_steering` while level and pitch scale on the `HYDRO_STEER_FULL`-normalised value, so the stereo image keeps opening after the tone has saturated. Carrier and modulator phase, ratio and index are all glided across the callback block; stepping any of them per-callback zippers. and a **centre-crossing click** fires once as the frame arrives at straight — silence alone is ambiguous, since it also means "idle". That click is deliberately *atonal* (seeded band-limited noise, 2.5–7 kHz): the compass and cam clicks are FM tones around a 900 Hz carrier, so anything pitched near there gets mistaken for one. Band-limited rather than plain high-passed, because raw noise peaks near Nyquist — thin, and the first thing to go with high-frequency hearing loss. The click arms only past `HYDRO_STEER_DEADZONE * HYDRO_CENTER_REARM` so hunting around centre can't machine-gun it. Level uses a dB *range*, not a linear scale to zero, or the near-straight case would be inaudible — which is the case the feature exists to report. `diagnostic/hydro_steer_sim.py` (`python diagnostic/hydro_steer_sim.py`) replays the gate/envelope/click state machine against a fake clock — run it after touching that block.
  - **Loader implement tones** — two voices for the WL-40's bucket/forks, both driven off the implement block in the extended struct and both gated by one shared fade envelope. Both are **split left/right by a fixed equal-power pan** (`IMPL_STREAM_PAN`, ground left, tilt right). They were originally both centre-panned, reasoning that the articulation tone already owns the HRTF slot, the implement is dead ahead by definition, so an azimuth of 0 carries no information and would cost two `np.convolve` per callback for nothing. That was true and beside the point: **two continuous sounds from one point in space fuse into one object** — the same principle this file invokes to justify rendering the docking beat pair centre, running the other way. The two voices are continuous, and they overlap in register (the 180 Hz carrier sits 1.6 semitones under the tilt scale's 200 Hz floor and its sidebands land across the middle of it), so centred they were reported as *one tone that changes character*, with lift and tilt indistinguishable. The split is **not a direction cue, it is a streaming cue** — a constant offset cannot be misread as a bearing because a bearing moves and this does not — and being pure gain it costs two multiplies, not the convolution a real azimuth would. `implement_tone_sim.py` scenario 6c asserts the mirror and the equal-power sum. `diagnostic/implement_tone_sim.py` and `diagnostic/implement_proximity_sim.py` replay both state machines against a fake clock — run them after touching either block.
    - **Ground proximity (FM).** Grit means "close to the ground"; pitch means "you are levering the machine off its wheels". Keeping those on two axes is the whole design, which is why the carrier is **fixed during the approach** — a rising pitch can then only ever mean lift. The C:M ratio starts on an exact integer far out and drifts off it as the implement nears the ground, with the index rising alongside. **`IMPL_GROUND_RATIO_DRIFT` must stay below 0.5**: at 1.0 the drift would arrive at the *next* integer exactly at contact, so the tone would sound clean at the moment it means "about to hit" — the inverse of its meaning. The dirt curve is **2.0, not the articulation tone's 3.0**: there, grit is an alarm reserved for the last quarter of travel, so cubing is right; here the drift *is* the graded distance readout and has to be legible from about a metre out, and cubed it leaves 2.0 m → 0.5 m nearly clean. When the implement is actually against the ground and jacking the machine up, a smoothstep ramps the ratio onto the next integer (clean again) and the carrier rises by `IMPL_GROUND_JACK_OCTAVES` with the lift. **`IMPL_GROUND_INDEX_HI` and `IMPL_GROUND_MAX_DB` were both pulled back after play-testing** (3.2→2.2 and −16→−19.5 dB, together about a quarter off the brightness at contact). The original values assumed near-the-ground was a state you pass *through* on the way to a dig; getting a bucket **under** something means working there continuously, and at the old settings the tone was harsh enough to be a reason not to use the feature. The level is only a default — `implement_ground_tone_dbfs` overrides it, so an existing config keeps whatever it already had. **Both implement tones map their level as a span hanging below the configured value** (`IMPL_GROUND_SPAN_DB`, `IMPL_TILT_SPAN_DB`), not as an interpolation up from `IMPL_*_MIN_DB`. The MIN constants are the quiet end *at the default level*, not an absolute floor: the old form inverted as soon as the configured level fell below one of them, and the configurator allows −120, so a user turning the ground tone down to −40 got −30 dBFS two metres out and −40 at contact — quieter as the bucket approached, loudest with nothing to report. `implement_tone_sim.py` scenario 15 asserts monotonicity at −45 and −80 and that the default is unchanged.
    - **Tilt (quarter-tone, pure sine).** A sine rather than FM so it is instantly distinguishable against the two FM voices, and because steps are easiest to count on an uncluttered spectrum. 400 Hz is level — genuinely level since the tilt axis became the implement's floor plane rather than a diagonal across it (see `implementFlags` below); the scale's code did not change but its *meaning* did, and it was previously reporting level at an angle nothing can enter. ±24 quarter-tone steps reach 200 Hz and 800 Hz at the implement's **real** mechanical stops, which are learned since the last restart (falling back to `IMPL_TILT_FALLBACK_SPAN_DEG` so it is usable on the first lift). **A running extreme is not a mechanical stop, and using it as one was the "first tilt after a load snaps, then it's fine" bug**: while the implement is still travelling outward the running max *is* the current angle, so `tilt/span` is exactly 1.0 and the step pins to ±24 for the whole stroke — measured at a 22-step jump in one tick, then pegged, going sane only once a real stop had been passed. An extreme is promoted to a stop only after the implement retreats `IMPL_TILT_STOP_CONFIRM_DEG` off it, and the newly learned span is swapped into the scale only while within `IMPL_TILT_SPAN_SWAP_DEG` of level — the one place every span agrees on step 0, so the rescale is inaudible; adopting it at angle jumps the readout by however much the fallback over-estimated the real travel (~9 steps on the WL-40). `implement_tone_sim.py` scenario 6b asserts both, and asserts that the old form pegs. The two ends are not equidistant from level, so the map is two-sided about a shared zero. Linear degrees → logarithmic frequency is what makes the steps evenly *perceived*; a linear-Hz map bunches them badly at the bottom. The frequency is one-poled with `IMPL_TILT_GLIDE_TAU`, **never `linspace`d across a block to the new value** — that turns a discrete step into portamento and destroys the countability the scale exists for — and every step change fires a 6 ms notch, which is what makes a fast sweep countable rather than one continuous slide.
    - **The shared gate** fades both tones out ~1 s after the implement stops moving and re-attacks in ~30 ms. There is **no hold timer**: `implementActivity` already folds in the ram's travel *rate*, so a momentary joystick release mid-lift keeps the gate open on its own. The ground tone's gate additionally opens on **closing rate** (`IMPL_GROUND_CLOSING_MPS`), not just on actuation — driving forward into a pile with a motionless bucket is the implement's position changing relative to the ground, and gating purely on joystick input would go silent during exactly the approach the tone exists to report. While the gate fades, the tilt step is **frozen** at its last actuated value, or a bucket settling under gravity re-steps mid-fade and reads as though it were still being commanded. The articulation tone is ducked `IMPL_HYDRO_DUCK_DB` while the gate is open, using the previous callback's gate value (that block runs first) — one buffer of latency on a 4 dB change, i.e. inaudible.
  - **Docking instrument (`DOCK_*` constants, `_dock_*` state)** — the loader alignment tones, gated by `F9` `Ctrl+I`. Two voices for three dimensions: the panned pulse carries lateral on the stereo image and range on its repetition rate, the beat pair carries vertical. `diagnostic/dock_tone_sim.py` replays the gate/phase/lock state machine against a fake clock — run it after touching that block.
    - **Ramp mode reuses all four voices and changes only constants.** `update_dock_target(range, lateral, null_value, mode, acquire, bearing_deg)`. **The mode travels with the values, not on `set_dock_mode`**, because the two arrive on different threads (the F9 keypress vs the 10 Hz listener): a mode change sitting one packet ahead of its own scaling puts 24 Hz/m through a figure the other mode's slope was sized for, which saturates the beat and fires a spurious lock chime — the instrument announcing "aligned" at a moment nothing is. On a mode change `_dock_lock_armed` and `_dock_beat_env` are **reset**, because the arm latch is hysteresis on a quantity whose scale has just changed by an order of magnitude; `dock_tone_sim.py` scenario 13 asserts zero chimes across the switch and asserts the un-reset form fires one. `DOCK_RAMP_LATERAL_FULL_M` is 3.0 against the implement's 1.2 because on a ramp approach you are routinely three metres off centre at fifteen out, and at 1.2 the pan would be pinned hard over through the whole acquire phase — the one phase in which the pulse is the only voice and the pan is carrying everything. `ramp_resolve_sim.lua` scenario 10 now asserts the audio-vs-mod range invariant, which was previously only a comment.
    - **In ramp mode the null channel is LATERAL, not yaw** (`DOCK_RAMP_BEAT_HZ_PER_M`, 2.0). It carried yaw originally, which contradicted this instrument's own reasoning: the implement readout deliberately keeps squareness *off* the continuous channels because "it only matters at the instant of entry", and ramp mode then sonified exactly that while leaving the one axis you must nail to fit between two walls on the pan alone. Reported from the seat as *"the tones don't really let me know where I am side to side"*, which is what an instrument with no null channel on its most important axis sounds like. Lateral now arrives three ways that reinforce: the **pan** says which side, coarsely and spatially; the **beat** says how far off, finely and self-calibrating, chiming on the null; the **tremolo rate** says which side again, categorically — and that last one is the only one of the three that survives on speakers, where a 700 Hz pulse's low-frequency stereo image largely does not. Fast (`DOCK_AM_ABOVE_HZ`) means the centreline is to your **right**; arbitrary, so it is asserted in `dock_tone_sim.py` scenario 12 rather than remembered. The slope sets the lock window as always: 2 Hz/m → chime at 0.25 m, re-arm at 1.25 m, comfortably inside the ~1.2 m of margin a car has in a 2.15 m half-width mouth. Yaw moved to the spoken tap, where the implement readout already puts it. `null_value` is ignored in ramp mode and the pair is driven from `lateral_m` **inside** `update_dock_target`, so there is exactly one lateral figure and the two voices cannot be handed different ones.
    - **The ramp cane tap is two numbers and then only what is wrong.** Cut back hard after the same play-test ("too much verbiage"): it used to open with `Cannon ramp, Large Cannon standard white` on every press — twelve syllables identifying a machine you are already looking at — and then read four facts whether or not any needed acting on. Now the target is named **once, on acquisition**, by the mode announcement (`Ramp alignment, <machine>`, re-fired on a target change and latched under the same rules as `last_dock_mode`, i.e. never cleared by `DOCKCLEAR`); the tap itself is `<offset> <side>, <range> <unit>` with the unit spoken once, and squareness (`RAMP_DOCK_YAW_SAY_DEG`, 8°), clearance and ramp pitch appear **only as bad news**. The word "square" is gone entirely: nothing in this readout confirms that things are fine, because that is what the tones are for.
    - **Ramp mode has two phases, and they answer different QUESTIONS with the same three channels.** Lateral offset and squareness are corrections to a line you are already on; from beside or behind the machine there is no such line, and reading them out there ("four metres right, 123 degrees left") gives an operator nothing to do, because what they need first is simply *where the mouth is*. So outside the approach corridor the pulse becomes a beacon: its rate follows the straight-line distance to the mouth (`hypot` of the signed along-range and the lateral, derived in `update_dock_target` rather than sent, so it cannot disagree with its own terms) and it is panned at the **true bearing to the mouth over the whole circle** — deliberately *not* squeezed into `DOCK_MAX_AZIMUTH_DEG`, which is a front-hemisphere ceiling appropriate to a steering error, when the whole point of this phase is that the mouth can be behind you. The null channel is **held out entirely**, both because the "offset from the centreline" of a line you are not on is most of the width of the machine — nulling it drives you into its flank — and because the pair arriving as you come into the corridor is then itself the "you are lined up on it now" cue. `_ramp_acquire` is latched once per packet in `beamtel.py`'s listener — one authority for the tones and the spoken readout, atomic with the numbers by construction — and is hysteretic (`RAMP_CORRIDOR_ENTER_M`/`EXIT_M`) because the boundary swaps what the pan *means*. Losing the target, a part swap or a vehicle change all reset it to hunting. `dock_readout_sim.py` scenario 17 and `dock_tone_sim.py` scenario 14 assert both halves, including that the old floored range pinned the pulse at its contact rate from twelve metres out.
    - **The hunting phrase names a place, not a correction.** Bearing first then distance (`82 right, 9.9 meters`), plus `wrong side` when you are past the mouth plane, and the lateral/squareness/clearance clauses are dropped outright — the clearance one is actively misleading off the line, since the margin is the mouth's half-width minus your *current* offset and reads as "too narrow by three metres" about a car that fits. The bearing is `atan2(lateral, range) + yaw`, exact rather than approximate, and derived in Python for the same reason the distance is.
    - **The two clauses of the hunting phrase are in different reference frames, so only one of them may use a direction word.** The bearing is measured from the driver's nose; the mouth-plane clause is measured against the ramp. Both are routinely true at once — aimed squarely at an entrance you have already driven past is an ordinary state while hunting — and wording the second one `behind` produced `ahead, 73.9 feet. behind`, which is not contradictory but reads exactly as though it were. `wrong side` cannot be mistaken for a bearing. It also fires on the **sign of the range** rather than on `RAMP_CORRIDOR_MIN_RANGE_M`: a car half a metre short of the mouth plane is in the doorway, and the threshold called that wrong side too. `dock_readout_sim.py` scenario 17 sweeps 280 geometries asserting no utterance ever carries two direction words, and asserts the old wording collides.
    - **It replaces rather than adds.** The scanner block is suppressed outright while the dock gate is open and the articulation tone is ducked by `DOCK_HYDRO_DUCK_DB` (−12, far harder than the implement's −4). Not a mix decision: articulation says what your input *did*, the docking pan says what you *need*, and on a final approach they are the same axis twice — the goal wins. Both read the *previous* callback's `_dock_gate_env` since the dock block runs last; one buffer on a level change is inaudible. The articulation centre-crossing click is untouched, so the frame reference survives.
    - **Phased by range**, so no more than three dimensions are ever live: silent past `DOCK_MAX_RANGE_M`, pulse only in to `DOCK_BEAT_RANGE_M`, pair fading in inside that. The pair has its own envelope rather than sharing the gate, or the acquire phase would be three quiet dimensions instead of two real ones. At four metres the vertical genuinely does not matter and you are still steering; three channels there is how the obstacle detector became something the user never switched on.
    - **Vertical is a beat pair nulling to unison, not a pitch.** Self-calibrating (no reference frequency to learn), the ear resolves a beat far finer than a pitch, and it is texturally unmistakable against the two FM voices and the pure-sine tilt scale. Three things about it are corrections to a first version that failed in listening — it was reported as *"one tone that stutters and raises and lowers in pitch"*, which is precisely what that version produced:
      - **Both partners move, symmetrically about `DOCK_REF_HZ`.** Holding one fixed and sliding the other moves the pair's *average*, and two tones that close fuse into a single pitch percept sitting at that average — so the listener hears a tone gliding, with the beating masked behind it. Symmetric placement nails the centre pitch so the only thing that varies is the beat. Measured: 330.1 Hz centre across the whole error range.
      - **The detune is specified as a beat rate in Hz** (`DOCK_BEAT_HZ_PER_M`, `DOCK_BEAT_MAX_HZ`), not as an interval in cents. Cents makes the audible result a function of `DOCK_REF_HZ`, and the original 200-cent cap was ~40 Hz apart at 330 Hz — far outside the range where beating is heard as beating at all. **Past roughly 15 Hz of separation the percept turns into roughness and then into two separate pitches**, so the cap has to stay under it.
      - **The pair is rendered CENTRE, not summed into the panned pulse.** Two sounds from one point in space fuse into one object. Splitting them is also honest — the vertical null is not a directional quantity — and free, since centre needs no convolution, the same argument the ground and tilt tones already make.
      - The tremolo sign carrier multiplies the **sum**, not one partner: modulating a single tone adds sidebands and muddies the very beat the pair exists to produce.
    - **Beating is signless**, so above-versus-below rides on a tremolo whose *rate* differs (`DOCK_AM_ABOVE_HZ`/`DOCK_AM_BELOW_HZ`), suppressed inside the lock window — a steady unison is the clearest available "stop".
    - **The unison lock chime is an armed latch inside the callback**, like the articulation centre-crossing click: hysteresis (`DOCK_LOCK_CENTS`/`DOCK_LOCK_REARM_CENTS`) on a continuous quantity, fired from the callback so it is sample-accurate and cannot machine-gun while hunting the null. Silence cannot report a null on its own — a smooth tone is also what "nothing to say" sounds like. It is a *descending two-note* figure because every other slot is taken: FM around 900 Hz (compass/cam clicks), a noise burst (articulation centre), single sines near 1 kHz (scanner/coupler). `DOCK_LOCK_WAVEFORM` must be regenerated at **both** build sites, as `HYDRO_CENTER_CLICK_WAVEFORM` is.
    - Only the pulse is user-levelled (`dock_tone_dbfs`); the pair sits at a fixed offset from it, or a mix exists in which the null cue is inaudible under the range cue.
- **hrtf.py** — HRTF binaural panning. Loads pre-baked MIT KEMAR horizontal-plane HRIRs from `hrtf_kemar_horizontal.npz` (numpy), interpolates impulse responses by azimuth, FFT-resamples to 48kHz. Used by audio.py for spatial compass clicks. The `.npz` is generated at build time by `bake_hrtf.py` from `mit_kemar_normal_pinna.sofa` — this keeps h5py + the HDF5 native libraries (~6.5 MB) out of the shipped build.
- **configurator.py** — wxPython GUI for `beamtel_config.json`. Speech backend/voice enumeration via Prism, real-time tone testing.
- **speech.py** — All speech output, backed by Prism (the `prismatoid` wheel). Picks a backend by priority (`auto`) or by configured name, re-acquires it when a screen reader starts or exits, and exposes per-backend capability bits plus a braille primitive. Replaced the old SRAL wrapper, which upstream deprecated in favour of Prism in August 2026.
- **ai_describer.py** — AI Describer pipeline. Captures the primary monitor (`mss`), sends the image to a vision model with a blind-friendly system prompt, returns the spoken description. Multi-provider: a registry at the bottom of the module dispatches on `ai_describer_provider` to one of two backends — Google Gemini (`generateContent`) or OpenAI (`/v1/responses`, default `gpt-5.6-terra`). Each provider owns its own config keys (Gemini's keep the original unprefixed names; others are namespaced, e.g. `ai_describer_openai_*`) and declares its extra request parameters via `extras_for()`, which the configurator turns into controls automatically. Model lists are hand-curated allowlists because neither provider's model listing exposes a vision-capability flag. API keys are validated against each provider's free model-listing endpoint. Logs all descriptions and API errors to `%LOCALAPPDATA%/beamtel/ai_descriptions.log`. Invoked in-game by F10 then Space.
- **nvda_ws_speaker.py** — aiohttp WebSocket server on port 8765. Bridges UI events to speech output.
- **bnh_logger.py** — Rotating file logger (`bnvdahook.log`, 1MB max, 3 backups).
- **diagnostic/** — Standalone UDP listeners for debugging telemetry protocols.

### Lua Mod Components (`bng_mod/`)

Entry point: `scripts/bng_screenreader_mod/modScript.lua` — loads all GE extensions.

- **`lua/vehicle/protocols/796F6C6F313035.lua`** — Custom extended telemetry protocol (filename is hex for "yolo1035"). Sends binary struct at 60Hz on port 4444 with steering, temps, G-forces, tire pressures, air pressure. (The diagnostic dump commands DUMP/PDUMP/HDUMP/DAMAGE are **not** here — they live in `vehicleScanner.lua` on 4448→4447.)
  - **`actualSteering`** — where the wheels/frame actually are, versus where the driver is asking. Resolved in three tiers, and the first tier is non-obvious: **hydraulic cylinders are not top-level powertrain devices.** `powertrain.lua` blacklists `hydraulicCylinder` from the device factory and `hydraulicPump` instantiates them into its own `connectedConsumers` list, so `powertrain.getDevice("steerL")` returns nil and you must walk `getDevicesByCategory("hydraulicPowerSource")` to reach them. (There is also no `.relExtension` field; it's `currentExtend` / `currentExtendPercent`. An earlier version used both of these non-existent things, which is why the WL-40 tone never worked.) For an opposed ram pair the value is the *difference* of the two extensions — exactly zero when straight, needing no centre-calibration constant and immune to an asymmetric `minExtend`/`maxExtend`. Tier 2 is the classic `hydros.hydros` scan, which **must** keep testing `steeringAutocenterEnabled == false` rather than `~= false`: `input.lua` treats nil as autocentering *enabled*, so accepting nil would make every ordinary car report a bent frame. Tier 3 is 0.0, which is what keeps the Python-side tone silent on normal vehicles.
  - **Implement block (`implementFlags` and friends)** — the loader's bucket/forks, resolved in the same VM and for the same reason: it is the only place with `v.data.nodes`, the hydraulic cylinders, `obj:castRayStatic` **and** `obj:getSurfaceHeightBelow`. Everything is silent on ordinary vehicles by construction — the cylinder walk finds nothing, `IMPL_FLAG_PRESENT` never gets set, and the Python status metrics and tones stay hidden. There is no per-vehicle check anywhere in it.
    - **The node set is resolved by NAME, never by geometry.** A tempting "everything forward of the tilt ram" rule is wrong: the WL-40's own lift arm (`la3`–`la5`, `la12`–`la14`) reaches forward of the tilt ram and would be swept in, corrupting the tilt axis and the clearance. Tier 1 joins `v.data.activeParts` (keys are full slot *paths*, so match `attachment|implement` on the path) to `nd.partOrigin` — `partOrigin` is the part **name**, not a path (`common/jbeam/slotSystem.lua:90`), so it also indexes `v.data.activePartsData` directly for the friendly name. Tier 2 matches `partOrigin` itself against `bucket|fork|grapple|…`. Because it is all name-driven, `resolveImplementNodes` logs what it landed on — that line is the first thing to look at if a machine ever reports nothing.
    - **Five fixed cids, picked once from design-space `nd.pos`.** Re-deriving an AABB live would be ~120 `getNodePosition` calls at 20 Hz; picking `edgeL/C/R` and `heelL/R` once costs five a tick. The fore/aft sign is *derived* — centroid of the implement versus centroid of the machine — rather than assuming a jbeam axis convention. Selection is three stages, and the third is the one that was missing: a fore/aft band at each end, then the **floor band** (`IMPL_FLOOR_BAND` of the implement's design-space vertical extent), then the lateral extremes of what is left. Without the floor constraint the heel picks are the lateral extremes of the rear band at *any* height, which on the WL-40's block-handler forks is the top of the backplate — so `edgeMid → heelMid` was a diagonal across the attachment rather than the plane the load rides on, and every angle derived from it was out by roughly the height of the implement. It fell back to the unconstrained pick when the floor band holds fewer than two candidates, so a flat implement still resolves.
    - **Tilt is the world pitch of that floor plane, and `0°` now means level** — not "as modelled". With a genuine floor axis, world pitch already *is* the angle from level, so the design-pose offset is not wanted; it is still computed and logged, because a large value now means the floor band landed on something that is not the floor. The old form reported 6° at the fork stop where the tines were 47° nose-up, and fed that to `audio.py`'s quarter-tone scale, whose 400 Hz "level" therefore meant an angle nothing can be driven into. World-referenced rather than vehicle-referenced because a slope is exactly when spilling matters.
    - **The tilt axis is `edgeL`/`edgeR` only, never the three-point edge mean.** `getImplementFrame`'s origin on the GE side is that same two-point midpoint, and the entry gate measures this same axis from there; two halves of one instrument reporting angles a degree or two apart is a disagreement that costs an afternoon. `edgeC` is picked nearest the **midpoint of `edgeL`/`edgeR`**, not nearest the vehicle centreline — on a centred implement the two rules choose the same node, which is why the centreline rule looked right, but on anything offset or side-shifted it lands well off the pair's centre and drags the mean with it. `implement_resolve_sim.lua` scenarios 13–14 assert the floor band and the re-pick, and assert the old forms fail.
    - **`obj:getSurfaceHeightBelow` does not return nil when there is no surface** — it returns a huge negative number (the game itself wraps it as `max(-1e6, …)`). The guard is a sanity *band* on the computed distance, not a nil check. `core_terrain.getTerrainHeight` is the nil-returning one and is deliberately not used here. A `castRayStatic` is taken alongside and the smaller kept, which is what makes terrain-less maps (smallgrid) work.
    - **Jacking is detected from a stalled ram, not from wheel load.** A loader's front-axle load swings several-fold between an empty and a full bucket, so "downForce collapsed versus baseline" has no stable baseline. A ram that refuses to move (`|d/dt currentExtendPercent| < 0.02/s`) while commanded hard (`> 0.6`) is by definition against a load; airborne front wheels only *confirm* it, separating "lifting the machine" from "pushing into dirt". The magnitude comes off the surface machinery instead: an EMA of the front axle's height above ground taken while the wheels are loaded, subtracted from the live value. Self-calibrating, no per-vehicle constant — at the cost of reading 0 until the machine has sat on its wheels once since the last reset.
    - Two clearance numbers on purpose: `implementEdgeHeight` (the cutting edge, the **status readout**) and `implementMinClearance` (min over all five points, what **drives the tone**) — the corner about to dig in is not necessarily the cutting edge. `implementFlags` is a bitmask rather than a bare present/absent float because `articulationDeg = 0` is otherwise ambiguous between "straight" and "no hydraulic steering", and articulation validity is independent of whether an attachment is fitted. `articulationDeg`'s *magnitude* is the measured yaw between the front and rear axle axes, but its **sign is taken from the already-trusted normalised articulation**, so it can never disagree with the steering tone. The whole block is throttled to 20 Hz and wrapped in `pcall`: it runs on the physics thread, where a throw would take the entire telemetry protocol down rather than just the loader features.
- **`lua/ge/extensions/vehicleGeometry.lua`** — Per-vehicle derived node geometry (extents, hull cids, front/rear contact bands, vertical occupancy histogram) for **any** vehicle, player or target. No ports of its own; it is a library the scanner and `implementProximity` both call. `diagnostic/vehicle_geometry_sim.lua` (`lua diagnostic/vehicle_geometry_sim.lua`) replays the classification and the distance query against synthetic clouds with known ground truth — run it after touching any of it.
  - **The reason it exists**: `vehicleScanner` measured `originPos:distance(targetPos)` and `getPosition()` is the object's reference node, so every distance was centre-to-centre. That carried half a vehicle of phantom range at each end and was **orientation-dependent** — broadside and nose-on to the same car at the same real gap reported the same figure. The sim's scenario 2 is that exact comparison and is the check most worth keeping.
  - **The loader is a cid list, not a branch.** Nothing downstream asks "is this a loader"; it asks for a *contact set* and a *surface set*. A generic car in forward is its own front node band, the same car in reverse is its rear band, a WL-40 is the five implement cids. That is what makes it impossible for loader work to regress the generic case — the loader is a different **answer**, not a different code path.
  - **The fallback chain terminates at today's behaviour** and is the whole safety property: hull cids → nearest hull node; else extents → closest point on the oriented box; else `getPosition()`. A vehicle whose async resolve never lands still answers, just less precisely, so no caller handles a nil. **Giving up has to be recorded, not just stopped**: `M.request` is documented as cheap to call every tick and every query does call it, so clearing `pending` after `MAX_TRIES` with nothing in `cache` merely re-arms the resolve on the next frame — the cross-VM chunk went out every 3 s and the "staying on fallback" warning was logged every 9 s for the whole session. A `failed` set gates `M.request` and is cleared per vehicle in `dropVehicle`/`dropAll`, so a reset or part swap still gets a fresh attempt. A malformed reply (`#ext ~= 6`) is flagged the same way; a VM answering with the wrong shape will keep doing so.
  - **`up:cross(fwd)` is the lateral vector, in both this file and `implementProximity`.** They must match: `implementProximity`'s `boxFrame` projects onto its own vector and clamps the result against `minR`/`maxR` taken straight from this cache, where `VEH_SCRIPT` measured them along its. It built the negation (`fwd:cross(up)`), which mirrored every lateral test against a cached target — the containment call and the slam footprint both answering for the far side of the vehicle. It survived because the strided fallback measures with whatever frame it is handed and so stays self-consistent: the readout was right for the first few ticks after a spawn and flipped when the async resolve landed. Both names (`rgt`, `right`) are misnomers — the vector points to the driver's *left* — and renaming either is exactly how they would stop agreeing. `vehicle_geometry_sim.lua` scenario 11 asserts the agreement, asserts the old form inverts, and greps both sources.
  - **`nearestSurfacePoint` keeps the SMALLER of the box and node answers**, the way the vehicle VM keeps the smaller of its terrain height and its raycast. The two tiers fail in opposite directions: the box encloses the body so it can only under-read, but it is exact at the surface; the node sweep is a sparse sample so it *over*-reads near contact by up to half the node spacing — thinning a car's shell to 48 measured 0.19 m of over-read, i.e. clear air reported while the tines are touching. That measurement is why `HULL_MAX` is 128 and not lower.
  - **`HIST_BINS` sets the finest pocket the mod can see at all**, because band thickness is quantized to the bin height. At 24 bins a 1.63 m target gave 0.068 m per bin, which silently turned `implementProximity`'s `BAND_MIN_HEIGHT_M` of 0.10 into "at least two bins" and discarded every genuine single-bin void — a real thin pocket was unreachable regardless of whether it existed. 48 bins is 0.034 m there, making the same threshold a real ~3-bin test. The wire format is `table.concat(hist, ",")` and both ends ship in the same mod, so no shim is needed — but `M.onVehicleGeometry`'s `#hist == HIST_BINS` guard is what makes a half-updated install fail loudly instead of mis-binning, and must stay.
  - **Extents are a gap-trimmed range, not raw min/max** (`OUTLIER_GAP_M`, `TRIM_MAX_FRAC`). A detached bumper stays in the *same object*, so raw extremes stretch the box across the empty air between car and debris and report solid surface where there is none — and they wreck the normalisation, collapsing every real body node into a slice of the 0–1 range so hull and band classification stop distinguishing anything. A percentile trim is the wrong tool because a detached part is a **dense** cluster; what separates it from the body is empty space, so that is what gets measured. The debris still normalises outside 0–1, trips the face test, and stays visible to the node tier.
  - **`M.debugVehScript()`** exists so the sim can compile the cross-VM chunk. A syntax error inside a `queueLuaCommand` string does not fail where it is written — it fails in another VM, silently, and the only symptom is that geometry never resolves and every caller sits on the `getPosition()` fallback for the whole session.
- **`lua/ge/extensions/rampGeometry.lua`** — The drive-in mouth of a ramp-equipped machine (the stock `large_cannon`, whose `cannon_ramp` slot is a funnel you drive a vehicle into before firing it out of the barrel). No ports of its own; a library `implementProximity` calls. Structurally a sibling of `vehicleGeometry.lua` — same cross-VM resolve, same epoch guard, same `failed` set, same `M.debugVehScript()` — but a different question, and folding it into that file would put a name-matched special case inside the one file whose whole premise is that it has none. `diagnostic/ramp_resolve_sim.lua` (`lua diagnostic/ramp_resolve_sim.lua`) replays the resolve against the real jbeam coordinates — run it after touching any of it.
  - **"Not ready" is not "no ramp".** The chunk returns `no node data` / `no nodes` when `v.data.nodes` does not exist yet, which is a fact about a VM still spawning and not about the vehicle. Treated as terminal (which it was), a cannon is permanently invisible or not depending purely on when the first resolve happened to fire — a bug whose only symptom is "it worked, then I restarted and got nothing". Those two reasons are counted in `notReady` and retried under the same `MAX_TRIES` budget as a silent VM, so a machine that answers that way forever still costs three chunks and no more.
  - **Silent on ordinary vehicles by construction, and terminal on the FIRST round trip.** `vehicleGeometry`'s chunk returns silently when it has nothing, which makes "no answer yet" and "nothing to say" indistinguishable and costs three retries over 9 s to tell apart. This one *always* replies, with an empty cid list when it found no `ramp_` nodes, and that sets `failed` immediately — so a car costs exactly one cross-VM chunk and one reply for the whole session. That is the entire cost model; without it every car in the scene re-issues a chunk every 3 s forever, which is the bug `vehicleGeometry`'s `failed` set already exists to fix.
  - **The along-ramp axis is the ramp centroid's displacement from the MACHINE centroid, never the ramp cloud's longest axis.** The tempting rule is not merely fragile here, it is *wrong today*: large_cannon's ramp is 5.792 m long but its inner row flares out to `ramp_L_6b` at x 3.449, making the cloud **6.898 m wide**. Longest-axis would call the mouth a side wall and report lateral offset as range. The displacement does not depend on the ramp's proportions at all — the ramp hangs off one end of a ~16 m machine — and it derives *which end is the mouth* in the same step, which longest-axis cannot do. Guarded by `AXIS_DOMINANCE`, and the resolve is **rejected and logged** rather than guessed at when unmet. Same centroid trick `796F6C6F313035.lua` uses for the implement's fore/aft sign.
  - **The drivable half-width comes from a WALL rule, not the implement resolver's floor-band rule.** `ramp_L_8a` is the *outer foot of the side wall* and sits at exactly floor height, so "lowest vertical band, then lateral extremes" answers ±2.785 where the truth is ±2.148 — 0.63 m of phantom clearance per side, which on a car is the difference between fitting and tearing the mirrors off. The wall is where something *sticks up*: per side, the smallest |lateral| among mouth-row nodes between `WALL_MIN_H` and `WALL_MAX_H` above the floor plane and outside `MIN_WALL_LATERAL_M`. Both guards are load-bearing and neither is sufficient alone — `MIN_WALL_LATERAL_M` stops a low centre rib being read as the left wall but only excludes an overhead node while it sits near the centreline, and the first offset ramp puts it back in scope; `WALL_MAX_H` is the one that holds, because it is a property of the node rather than of where the ramp happens to be sitting. large_cannon has exactly such a node: `ramp_M_0`, 2.1 m up on the centreline, which without a ceiling on the rule collapses the mouth outright. Scenario 3 asserts 2.148 **and** asserts the naive form answers 2.785 and disagrees about whether a given car fits. It is all name-driven, so the resolve **logs what it landed on** — including the naive figure even when the rule worked, because that is the one line that turns "the clearance feels wrong" into an answer.
  - **`ROW_BAND` is 0.35, far wider than the implement resolver's 0.15, because a mouth is not one row of nodes.** large_cannon's is three rows spread over 1.26 m of a 5.79 m span — the toe on the ground, the floor lip, the raised wall — and the wall row is the one the half-width rule depends on. At 0.15 the band captures only the toe, so the wall is never seen and the rule silently falls through to its own fallback. The valid range is 0.218 to 0.782; 0.35 sits with 60% margin above the floor.
  - `M.mouthFrame(vehID)` reads the five cids **live** every tick (the same five-call budget the implement's sample set already costs), because the whole assembly tilts on its `ramL`/`ramR` cylinders — geometry derived from design space is a lie the moment the inclination control moves. `centre` is the two-point midpoint of the edges, not the mean of all three, for the same reason `getImplementFrame` excludes `edgeC`. `left` is `vec3(0,0,1):cross(axis)`, and `vehicle_geometry_sim.lua` scenario 11 now greps this file too — three files have to agree on `up:cross(fwd)` and nothing but that grep enforces it.
- **`lua/ge/extensions/vehicleScanner.lua`** — Nearest vehicle detection, target cycling, coupler compatibility matching, alignment teleport. Sends CSV on port 4445, receives commands on port 4448. Range on the 4445 packet is the **surface gap** via `vehicleGeometry`; **bearing deliberately still aims at the target's box centre**, because a bearing to the nearest surface point swings wildly at close range as the winning point hops between corners, and bearing is the number you steer with. **Bearing sign and magnitude MUST come from the same frame.** The angle is measured from `forwardVec` (the implement heading when the override is active) and the left/right sign from `refForwardVec` — the *same* vector, snapshotted before the reverse negation. Deriving the sign from the chassis heading instead is a bug that is invisible on every rigid vehicle and vicious on an articulated one: the two frames differ by the articulation angle, so for a target near the *cab's* centreline the magnitude is the articulation angle while the sign flips, and the reading snaps ±30° without passing through zero. Measured at a 60.1° single-tick jump against 0.1° once fixed; `vehicle_geometry_sim.lua` scenario 10 asserts both. `refUpVec` follows the same rule — world up with the flattened implement heading, chassis up with the chassis heading. **`toTargetVec` is also flattened**, or three metres of boom travel shrinks the dot product and inflates the bearing with no yaw change at all, i.e. lifting the bucket appears to steer the machine. Coupler distance mode is untouched by any of this — it already does node-to-node with `rearOverhang`/`frontOverhang` compensation and already assumes reversing, so a generic flip layered on top would double-count.
  - **Reverse moves the contact set to the rear band and negates the reference heading**, so a target dead behind reads ~0° rather than ~180°. `GEAR:R`/`GEAR:F` is pushed from `beamtel.py` on change (it already decodes gear from the telemetry struct; cheaper than a cross-VM electrics poll), aged out after `GEAR_STALE_SEC` and backed by a velocity-along-forward fallback — gear is preferred because at a standstill about to reverse the readout should already be rear-referenced, and velocity reads zero there. **The resolved direction then rides back on the 4445 packet as a fourth field, and Python's speech reference reads it from there** — not from the gear it pushed. Mirroring the push locally is wrong in precisely the two cases where Lua ignores it: after `GEAR_STALE_SEC` it is on velocity instead (roll backwards down a slope in D and the bearing is rear-referenced while Python still believes forward, so speech says "in front of you" about what you are reversing into), and a vehicle switch clears it outright. The field is optional on the wire — the parse is positional with a `len(parts) >= 2` guard — so an older mod simply falls back to the pushed gear.
  - **`playerLeftVec` must keep being built from the UN-negated forward vector.** It is `up × fwd`, so negating `fwd` silently negates the cross product and reports left as right for as long as the vehicle is in reverse. The driver's physical left side does not move when they select reverse; positive stays LEFT in every gear. `vehicle_geometry_sim.lua` scenario 8 asserts it *and* asserts that the buggy form would invert, so the check cannot pass for free.
  - **The implement override is scoped to forward only.** Phrasing the rule as "the implement supplies the *forward* contact set" rather than "loaders use the implement" is what makes reversing a loader fall out for free — it drops to the rear band like any other vehicle, with no loader-specific code. Backing up measured from the bucket was the single worst case in the old build: the whole machine length of error, in the wrong direction.

- **`lua/ge/extensions/implementProximity.lua`** — What the loader's bucket or forks are about to run into. Port 4469→4470. Deliberately does **not** handle the ground: that is the vehicle VM's job (see `implementFlags` below), because that VM owns the implement node set and has both `obj:getSurfaceHeightBelow` and `obj:castRayStatic`. This extension covers only what the vehicle VM cannot see — other spawned objects. In BeamNG most "props" (cones, barriers, haybales, pallets) *are* spawned vehicle objects, so `be:getObject` covers them; map-placed `TSStatic` clutter is not enumerable and shows up only in the vehicle-VM ground raycast.
  - **Node cloud for contact, oriented box for containment.** These answer different questions and neither substitutes for the other. When a part breaks off a vehicle its nodes stay part of the *same object*, so a detached bumper lying in the dirt is invisible to that vehicle's bounding box but perfectly visible in its node cloud — hence the strided node-to-node narrow phase for "about to hit something". The box is used for the opposite question, "are the tines *inside* the vehicle's volume without touching it", i.e. under the frame ready to lift. Box overlap alone false-positives constantly, because a solid box also contains the air beside a low car's wheels, so containment additionally requires ≥2 implement points inside and the implement centroid *below* the box's mid-height. It deliberately does **not** also require a nearest-approach greater than `CONTACT_M`: that clause made "under it" and "touching it" mutually exclusive, so tines resting against the underside of a load — the state immediately before a lift, and the one an operator most needs confirmed — reported contact and dropped the "under" entirely. `contact` is its own field on the `NEAR:` line, so the two are independent. **That count, and the slam gate's, are over the five sample cids — never the full `implCids` cloud.** `INSIDE_MIN_PTS`/`SLAM_OVER_MIN_PTS` are counts, not fractions, so feeding them ~120 nodes quietly redefines "over it" as "about 2% of the bucket is over it", and since losing the footprint takes *every* point the state then cannot be dropped again either — `COMMITTED` fired beside the target. The narrow-phase nearest-approach sweep keeps the full cloud, because that is the tier that sees a part which has broken off. The box is built from `getDirectionVector()`/`getDirectionVectorUp()`/cross and the extents measured from the node cloud — **not** `be:getObjectOOBBHalfExtentsXYZ` against world axes, which for a car parked at any angle describes a box it isn't in.
  - **The cid list is pushed, not pulled.** `796F6C6F313035.lua` resolves the implement (it has `v.data.nodes` and `partOrigin`) and hands the result over with `obj:queueGameEngineLua` on spawn and after every reset. Re-deriving the name matching here would be two copies of one fragile thing, and because the resolution only ever changes when it re-runs, the newest push is always authoritative — there is no window in which this extension could hold cids belonging to a part that is no longer fitted. The cache is still dropped on `onVehicleSwitched`/`onVehicleResetted` and the extension stays quiet until the next push, because stale cids return confident *wrong* world positions rather than an error.
  - **Pushes are stored per vehicle (`implByVeh`) and only the player's is promoted.** They used to land straight in the shared globals whichever vehicle sent them, which was survivable while each pushed once (last spawn quietly won) but not once the push became a heartbeat — two claimants then take it in turns every few seconds. The vehicle-side match is pure name matching against `IMPL_PART_WORDS` (`bucket`, `fork`, `blade`, `scoop`, `plow`), which a bucket *seat*, a wiper *blade* or a hood *scoop* can satisfy, so an ordinary car parked beside the loader could take ownership and flip the scanner's origin between the cutting edge and the reference node on a 4 s cycle. Nothing logged it, because the re-push is idempotent and only speaks when the payload changes.
  - **`getImplementFrame`'s hemisphere test guards both operands.** The lateral baseline was length-checked but `veh` was not, and it is the other half of the same sign test — flattening the machine heading collapses it to numerical residue when the machine pitches near vertical (nose into a pile, jacked on its own bucket), and the test then picks a side per tick. It does not degrade gracefully: negating `fwd` negates the derived left vector, so the bearing *mirrors*. It now holds `lastGoodFwd` instead of guessing.
  - Active by default rather than keybind-toggled: with no implement resolved a tick costs one `getPlayerVehicle` and an early return, and an ON-on-startup handshake would break when BeamNG is launched after beamtel.
  - **The docking readout (`DOCK:` line, `DOCK_ON`/`DOCK_OFF`/`BANDNEXT`/`BANDPREV`/`BANDAUTO`)** is the alignment instrument, separate from the proximity speech above and off by default — it is a mode you enter to line something up, not ambient awareness, and it is meaningless with no implement fitted. Three numbers plus a reference: lateral and vertical are what you steer and lift with, range says how long you have to get them right. **Yaw is reported but is deliberately not a fourth continuous channel** — it only matters at the instant of entry, and sonifying a fourth axis is exactly how the obstacle detector became unusable.
  - **It is not a pocket finder — the reference band is *selected*, not derived.** Lifting and ramming want different bands out of identical geometry: forks into a pallet want the void, forks through a window want the glass, a bucket into a flank wants the sill. `vehicleGeometry.bands()` collapses the histogram into alternating GAP/SOLID runs and `autoSelectBand` picks one (lowest real void for forks, tallest solid face for a bucket), with a key to override. Selecting rather than deriving is also what makes the reference *announceable*: with a derived pocket the operator could never tell what the readout was measuring against.
  - **Auto-selection needs to know a bucket from forks, which is otherwise Python's job.** Only the *choice* is made in Lua (`implementIsFork`); the spoken naming stays in `beamtel.py`'s `_implement_word`. One copy of each: Lua picks, Python speaks.
  - **A manual band pick is scoped to one target and one implement.** `resolveBand` drops back to auto when the target id changes, and every cid-cache invalidation clears it too — an index against a pallet means nothing against the car you have since turned toward. Cycling clamps rather than wraps, and the clamp is written back, or holding the key past the end runs the index away and the same number of presses is needed to get back into range.
  - `vertical` is `bandMid - implementEdge.z`, so **positive means raise**; `lateral` is positive-LEFT, matching the scanner bearing and the compass clicks. `diagnostic/dock_readout_sim.py` asserts both signs, because a sign error here reads as perfectly plausible speech and this project has already lost time to one.
  - **The slam gate (`SLAM:` line)** is the destruction case, and it is three discrete hysteretic states rather than a continuous readout because nulling is the wrong *shape* for it — an overhead drop wants to be decisively above, then over, then commit, not to drive an error to zero. `overBox` is the plan-view half of the existing containment test with the `implCentre.z < boxMidZ` clause dropped; the height half is the clearance test instead. **It needs no new geometry** — the five cids are already resolved and pushed, and the mode only changes which of them drive the test.
    - Both thresholds are asymmetric on purpose: clearance uses `SLAM_CLEAR_ENTER_M`/`SLAM_CLEAR_EXIT_M`, and the footprint takes `SLAM_OVER_MIN_PTS` to claim but *all* points to lose. Without that, a machine idling on its suspension at the boundary toggles continuously, and this cue is meant to mark a decision. `vehicle_geometry_sim.lua` scenario 9 runs 200 ticks of threshold wobble and asserts zero state changes.
    - It rides on the **docking toggle** rather than a key of its own — same act, other end, and a second mode key is one more thing to remember mid-manoeuvre.
    - Only `COMMITTED` is spoken. The other two are waypoints you pass through, and narrating each would talk over the manoeuvre it describes. `NONE` fires no cue at all: leaving the gate is not an event, and marking it would fire constantly while manoeuvring in a yard.
    - **The committed earcon RISES where the docking lock chime FALLS.** They are the only two-note figures in the mod, and opposite contours are what stop "arrived at the null" and "armed to drop" being confused — an expensive confusion, given what the second one leads to.
  - **Ramp mode is the instrument's second ANSWER, not a second instrument.** Everything else in this file measures from an implement to a load; ramp mode measures from the vehicle you are driving to the drive-in mouth of a ramp on some other machine. Same toggle, same wire format, same three audio channels, so there is no second mode key and no second set of tones to learn. The mode is auto-selected per tick and never sticky: implement fitted → today's behaviour byte for byte; otherwise the nearest vehicle with a `rampGeometry` resolve in range. The one structural change was turning the `not implCids` early return into a **fall-through** — a machine with no implement is exactly the machine you drive *into* a ramp — and every other early return is untouched and still names itself, which is what stops ramp work being able to regress the implement case. `SLAM:` is implement-only, and so is the `NEAR:`/`CLEAR` proximity speech: on a car there is no bucket.
    - **The origin is `vehicleGeometry.contactPoints(playerID, +1)`**, the identical non-implement fallback `vehicleScanner` already uses — reused rather than reinvented, so the ramp readout and the scanner bearing measure from the same point on the same vehicle. Forward band unconditionally, never `activeDirection`: you drive *forwards* into a cannon.
    - **`range` is measured ALONG the ramp axis, not straight-line to the mouth centre.** Straight-line inflates with lateral offset, so drifting sideways would sound like backing away, and it would bottom out at the offset instead of at zero. `lateral` is positive-LEFT as everywhere else in the mod. `yaw` is deliberately **not** folded to ±90 the way the implement's squareness is — a pallet has no front or back as far as the tines are concerned, and a ramp emphatically does.
    - **That range is SIGNED, and the feed ceiling is the in-plane distance rather than the range.** It used to be floored at zero, on the reasoning that crossing the mouth plane should read as arrived. True of the last half metre, false of everything else: the negative half-space is the *entire hemisphere behind the mouth plane*, which is where a driver circling a sixteen-metre cannon looking for its entrance spends nearly all of their time. The floor pinned the range channel at 0 throughout — the pulse ran at its contact rate and never moved, and the readout said "mouth 0.0 feet" from ten metres away on the wrong side, which is the bug this whole phase split came out of. Consumers apply their own floor. Testing the *signed* range against `RAMP_REPORT_M` would then leave the whole negative half-space permanently under the ceiling, so the gate is `hypot(range, lateral)` — which is also the honest answer on the approach side, where ten metres out and eight across is fifteen metres from the mouth, not ten. `ramp_resolve_sim.lua` scenario 9 asserts both and asserts what the floored form reported.
    - **`M.rampTruth()` prints the sign in words.** Negative means behind the mouth plane, and that one fact is worth more than the other three numbers put together while the entrance is still being hunted for.
    - **The width margin takes the WORSE side of the player's box** (`max(|minR|, |maxR|)`), because the vehicle origin is not necessarily on its lateral centreline and reporting clearance from the roomier side of an off-centre car is the one error here that ends with a mirror torn off. `-1` is the not-measured sentinel and must never be `0`, which reads as exactly touching both walls.
    - **Ranges are per mode, not a raise of `REPORT_M`** (`RAMP_REPORT_M` 45.0 against 6.0): the implement instrument is short-range on purpose. `RAMP_SEARCH_M` is 70 rather than reusing `BROAD_RADIUS_M`, because that prefilter measures to the object's *reference node*, which on a ~16 m cannon sits ten to fifteen metres behind the mouth — a mouth twenty metres away can have its object centre thirty-five metres away and be filtered out before it is ever looked at; it has to keep clearing `RAMP_REPORT_M` by more than half a machine length or it silently becomes the real ceiling.
    - **The FEED ceiling and the range at which anything is sonified are different jobs**, and conflating them killed the instrument in the one place it was most needed. At 20 m *measured to the mouth*, parking beside a sixteen-metre cannon at the barrel end puts the mouth outside the feed, so the mod sent `DOCKCLEAR` — which clears the reason as well as the reading — and `F9` `I` answered "Nothing in range" about a machine the scanner was reporting nine feet away, with the toggle-on message naming no mode. Indistinguishable from a switched-off instrument. The feed now runs to 45 m while audio fades out at `DOCK_RAMP_MAX_RANGE_M` (25), and that gap is the design: **the spoken readout keeps answering after the tones have gone quiet**, which is the state someone reaches for the key in. The phrase names it (`too far for tones`) rather than leaving unexplained silence.
    - **Ramp mode never sends `DOCKCLEAR`.** "There is no ramp" is already a `DOCKFAIL`; "there is one and it is over there" is the most useful sentence this instrument can produce for someone who cannot find it, so past the ceiling it sends `DOCKFAIL:<name> ramp mouth <n> metres away`, rounded to the metre so the dedupe still holds most ticks. `ramp_resolve_sim.lua` scenario 9 greps for the absence of the `send("DOCKCLEAR")` **call** — not the word, which appears in the comment explaining why it is not there.
    - `M.rampTruth()` is the ramp analogue of `dockTruth()` and earns its place by the same argument: this resolve's failure mode is "it landed on the wrong node", which produces confident, plausible numbers and is invisible to every kind of inspection except printing what it chose.
  - **The entry gate** answers the question none of the three continuous channels can: lateral, vertical and range can all be nulled perfectly and the tines still not go in, because a tilted implement climbs through the selected band's whole thickness after a few centimetres of travel and hits the far side. `resolveEntry` is pure trigonometry on numbers already resolved — the floor plane's world pitch `θ` (`edgeMid → heelMid`, the same axis the vehicle VM reports as tilt), the tine length `L`, and the band thickness `T` — giving a usable insertion depth `d = min(L, T / sin|θ|)`, or `L` below `IMPL_ENTRY_LEVEL_DEG`. Hysteretic (`IMPL_ENTRY_MIN_DEPTH_M`/`IMPL_ENTRY_EXIT_DEPTH_M`) for the same reason `SLAM_CLEAR_*` is: it drives a one-shot earcon, and a machine breathing on its suspension at the threshold would machine-gun it.
    - **Reported as a depth, not as a maximum angle.** "The tines go in 15 centimetres" is directly actionable; "you are 12° over the limit for this band" asks the operator to redo geometry the mod has already done.
    - `θ` and `d` ride as **two fields appended to the end of the `DOCK:` line**, parsed positionally with a length guard — the same optional-tail contract the scanner packet's fourth field uses, because `bng_mod/` is a live junction and the two halves genuinely do go out of step. `d = -1` is the "could not measure" sentinel; Python treats that and a missing field as silence rather than as `0`, which would read as *perfectly level*.
    - Spoken only when it is bad news (`_dock_phrase` gains a "tines enter … , too steep" clause), and marked by a **one-shot earcon on the transition into enterable** — a single high sine at `ENTRY_CUE_HZ`, because both two-note contours are taken and a third would be one distinction too many mid-manoeuvre. Python edge-detects with the *same two thresholds* the mod applies; using only the enter threshold there would re-introduce exactly the chatter the mod's hysteresis exists to prevent. Losing the target resets to "not known", so re-acquiring an already-enterable band is silent — the cue means "you can go in *now*".
- **`lua/ge/extensions/bnvdaAutoSpawner.lua`** — Deferred UI app spawning (currently commented out).
- **`ui/ui-vue/mods/bnvda/bnvdaRuntime.js`** — The whole UI accessibility layer, bridging BeamNG UI events to Python. (The old AngularJS `ui/modules/apps/bnvda_hook/app.js` was folded into this file and deleted.) Transport is `lua-tcp`: CEF → `bnvdaBridge.lua` → Python's TCP relay on 8766. Per-screen text extractors, a MutationObserver, a `focusin` listener and a 120 ms Vue focus poll all funnel into one `scheduleSpeak()` gate, which layers controller dominance, a same-text dedup, a 50 ms debounce, and held-navigation coalescing.
  - **Translation** — `findTranslateFunc()` must resolve `window.vueI18n.global.t` (petite-vue-i18n, published by the game's `ui-vue/src/services/translation.js`) on Vue screens, falling back to `window.angular$translate.instant` (published by `entrypoints/main/main.js`) on the remaining AngularJS ones. `bngApi.engine.translate` does **not** exist in 0.39; probing it first meant every lookup fell through to the last-resort key-humanizer, which spoke raw key fragments — `ui.common.vehicleAccessoryOn` as "vehicleAccessoryOn", and state keys like `vehicle.engine.oilLevelCritical.true` as a bare "true". The humanizer is deliberately never cached, because the real translator only appears once the UI finishes booting.
  - **`cleanText` is falsy-guarded**, so it maps `false` to `""` but stringifies `true` to the literal word `"true"`. Never hand it a raw DOM `value` property — Vue components expose booleans and objects there. Use `scalarValue()` first; that asymmetry is why the artifact only ever showed up as "true".
  - **Held-navigation coalescing** — holding a direction to sweep a list, slider or dropdown otherwise speaks every item flown past. `scheduleSpeak` instead announces the first item, stays silent through the run, and speaks the landing once motion stops. The settle delay is derived from the observed repeat cadence (clamped `NAV_SETTLE_MIN_MS`–`NAV_SETTLE_MAX_MS`, i.e. 90 ms–`NAV_BURST_GAP_MS`) rather than a fixed idle debounce, because a ~500 ms wait makes the UI feel sluggish. **`NAV_SETTLE_MAX_MS` must stay >= the engine's controller repeat interval** (~240 ms on the part selector): a lower ceiling makes the settle timer fire in the gap between two repeats, which flushes on every item — defeating the coalescing entirely while still charging its full delay to every announcement. It is tied to `NAV_BURST_GAP_MS` because a gap that large already starts a new burst by definition. Only `P.KEYBOARD`/`P.CONTROLLER` are captured; `P.SYSTEM` (toasts, damage, camera, cruise control) must never be, or a sweep will delay or drop it. `UINavigation` press/release tracking both prevents an uneven repeat from flushing mid-run and shortens the wait on release, but the part selector reports no key state, so there the settle timer is the only mechanism. Gated by `ui_nav_hold_suppression`. `diagnostic/navburst_sim.js` (`node diagnostic/navburst_sim.js`) replays the state machine against a fake clock, including a scenario at the real 240 ms repeat rate — run it after touching that logic.

### Threading Model

- **Main thread**: UDP telemetry loop (blocking socket with timeout)
- **Audio thread**: `sounddevice.OutputStream` callback (high-priority)
- **Device watcher thread**: Monitors default audio device changes
- **Daemon threads**: UI listener (port 4579), scanner listener (port 4445), keyboard hook, NVDA WebSocket (asyncio event loop)

All shared state is protected by `state_lock` (threading.Lock). The audio callback minimizes lock holding by reading state snapshots.

### Telemetry Protocols

- **OutGauge** (188 bytes, format `<I4sHBBfffffffIIfff16s16si`): Standard speed, RPM, temps, gear (byte: 0=R, 1=N, 2+=1st...), dashboard light bitmask.
- **Extended** (196 bytes, format `<H4sBx9fII36f`): Adds tire/brake temps, clutch temp, G-forces, gear as string ("P","D","R","N","S3","M5"...), and the loader implement block. Field order in `getStructDefinition()` **is** the wire format, and `beamtel.py` unpacks the float tail positionally — a field added on one side and not the other silently shifts everything after it. The previous 164-byte layout (`28f`, pre-implement) is still decoded as `EXT_FORMAT_V1` and padded, because `bng_mod/` is a live junction into the game install: without that, a mod half newer or older than the Python half would fail the length check and take **all** extended telemetry down — no speed, no gear, no warning lights — with no error anywhere. Add new fields at the end, bump the count, and add a new `_V1`-style fallback rather than widening the old one.
- **MotionSim** (magic "BNG1", format `<4s21f`): 3D position and orientation (yaw, pitch, roll).

### Configuration

Config file: `%LOCALAPPDATA%/beamtel/beamtel_config.json` (shared by beamtel.py and configurator.py). Defaults are hardcoded in `DEFAULT_CONFIG` dicts; user values are merged on top. Config corruption triggers auto-backup (.bak) and reset to defaults.

Most settings are consumed on the Python side. `ui_nav_hold_suppression` is the exception: it is enforced in the mod's JS runtime, so beamtel pushes it over the bridge as a `settings` message. The runtime pulls it with a `settings_request` on every transport activation rather than relying on the push alone — at startup the config-change broadcast fires before the Lua bridge has connected and would be dropped.

## Key Patterns

- **Audio callback pattern**: Check triggered events → read state under lock → generate samples → mix all sources → clip to [-0.999, 0.999] → write stereo interleaved output.
- **Keyboard command lifecycle**: F9 → install hooks + 4-second timeout → process key → unhook. Modifier tracking (Ctrl/Shift/Alt) handled in `_on_next_key_press`.
- **Fallback strategy**: configured speech backend → Prism's highest-priority available one, re-acquired on failure; preferred audio device → system default; air pressure controller → electrics scan for vehicles without dedicated tanks.
- **Nuitka build config**: Embedded as `# nuitka-project:` pragmas at the top of `beamtel.py` and `configurator.py`. Both build as `--onefile`. beamtel requires admin (`--windows-uac-admin`) and a console; configurator disables the console.
- **Cross-VM Lua communication**: Vehicle VM ↔ Game Engine VM via `vehicle:queueLuaCommand()` and `obj:queueGameEngineLua()`. All UDP socket I/O uses LuaSocket.

## Lua Constraints

BeamNG.drive retail uses **LuaJIT (Lua 5.1)**:
- `string.pack`/`string.unpack` are NOT available. Use `string.format` text CSV for UDP packets.
- `castRayStatic(origin, dir, maxDist)` — raycasts against static geometry only. Vehicles use soft-body physics and are invisible to raycasts; use `be:getObject(i)` enumeration instead.
- `core_terrain.getTerrainHeight(pos)` — terrain height queries at arbitrary world positions.
- Lua extensions export a module table `M` with hooks: `onExtensionLoaded()`, `onWorldReadyState(state)`, `onUpdate(dtReal, dtSim, dtRaw)`.

## Dependencies

numpy, sounddevice, wxpython, aiohttp, keyboard, prismatoid (+cffi), zstandard. Prism's native library ships inside the prismatoid wheel (`prism/_native/`), so no DLLs are staged in the project root. Packaging it needs three explicit `--include-data-files` entries (see `prism_nuitka_args()` in `build.py`): `prism.dll` and `_prism_cffi.pyd` at `prism/_native/`, because `--include-data-dir` silently drops binaries and Nuitka cannot follow the `__path__` splicing in `prism/_native.py`; plus `python3.dll`, the stable-ABI forwarder that the abi3 extension links against and that Nuitka does not bundle. Build-time only: h5py (used by `bake_hrtf.py` to extract the SOFA file into `hrtf_kemar_horizontal.npz`; not bundled into the executable).
