# Lua/JS: UI Runtime: Binding readouts and the binding editor

Part of `ui/ui-vue/mods/bnvda/bnvdaRuntime.js`. The overview, the poll/event model and the shared text helpers are in `lua-ui-runtime.md`.

Which device a binding readout names, how hints are read, and the edit-binding popup.

- **Binding readouts name ONE device — the one in the player's hands.** `bngBinding.vue` renders one `.binding-container` per variant, and with an Xbox pad and a DualSense both plugged in that is the same action twice, once per glyph set. A sighted player skims the pair; a listener hears every hint and every prompt twice, and half of each pair names buttons that are not on the pad they are holding. `pickBindingVariants` keeps only the containers whose glyphs belong to the active device family, taken from `Controls.lastDevices` — the game's own most-recently-used ordering (`core_input_bindings.getRecentDevices`), i.e. the very rule `bngBinding` follows for its own `useLastDevice` lookups, so the speech and the screen cannot end up talking about different pads.
  - **The icon NAME is the only thing that carries the family.** `BngIcon` renders a bare glyph character with no class, attribute or data hook naming the icon, so once it is in the DOM the reverse map built in `buildGlyphMap` is the sole route back — and `controls.js` names every control icon by family prefix (`xboxA`, `psCross`, `mouseLMB`), which is what makes the map possible at all.
  - **Keyboards, wheels and generic joysticks are the EMPTY family, not an unknown one.** `CONTROL_ICONS` has no family for them, so `bngBinding` falls back to a `<kbd>` carrying the control name and their containers hold no glyph whatsoever. Treating "no glyph" as unclassified would drop every keyboard binding; it is a first-class family, and it is appended to the preference order when it is not already there so a keyboard-only binding is still announced while a pad is active — the alternative is silence about a control that is on screen. Where no family matches, the fallback is the **first** container and never the whole set, because an unnameable family is still one device's worth of binding and reading the set is the same double announcement arriving in the one case nobody would think to look at.
  - **`Controls` must be bound to `window.bngVue.controlsStore`, not `window.bngVue.controls`.** The latter is a hand-written facade (`main.js`'s `exposeControlsStore`) that forwards a chosen subset of *methods* and carries none of the store's reactive properties — `lastDevices` among them. Binding to it left `makeViewerObj` working, so nothing looked wrong, while every device query silently answered `undefined`.
- **Hints are read per `.binding-wrapper`, NEVER per `.binding-container`.** `Hint.vue` wraps its whole row of bindings in a `<div>` that carries that same `binding-container` class, so a container scan matches the outer div **and** each `BngBinding`'s own container inside it — and `getBindingFriendlyName` reads the outer one whole. A hint with a single button therefore came out as "A button or A button", which is most of what "everything reads twice" turned out to be; the two-pad duplication above is the other half and they are independent. `binding-wrapper` is `BngBinding`'s own root and nothing else uses it, so it cannot nest. Legacy Angular hints have no wrapper, hence the container fallback.
- `diagnostic/binding_readout_sim.js` (`node diagnostic/binding_readout_sim.js`) replays all of the above against a fake DOM built to the shape `bngBinding.vue` and `Hint.vue` actually emit. It **lifts the functions out of the source by name** rather than copying them — this area's failure mode is a readout that is merely wrong rather than broken, so a sim carrying its own copy would keep passing across exactly the edit that breaks the mod — and every scenario also asserts what the previous form answered, so no check can pass for free.
- **The edit-binding popup: the two action buttons are named by ICON, and the conflict list announces itself.** Both failures were found in one DOM dump of `[bng-ui-scope=options-edit-binding-popup]`, and they are independent.
  - **0.39 moved the action buttons OUT of the assigned-control row.** `EditBindingBasicInfo.vue` renders `.detail-controls-actions` as a **sibling** of the `.bng-row`, both children of `.detail-controls` — so `closest(button, '.bng-row, [class*=row]')` matches nothing, the branch that named them never fired, and both fell through to the generic fallback. They carry no text, no `aria-label` and no tooltip, and `cleanText` strips the PUA glyph, so each announced as the bare word **"Button"**: the driver could not tell the reassign button from the one that deletes the binding.
  - **They are identified by their icon (`icons.edit` / `icons.trashBin1`), compared against the catalog through `iconGlyphOf`, never by position.** `todPlayLabel` already reads the TOD play/pause button this way, for the same reason — the icon *is* the identity when there is nothing else. Position is not merely fragile here, it is unusable: the trash button is rendered under `v-if="!isNewBinding"`, so on a new binding the lone button is Reassign at index 0 and an index rule is right only by luck. An **unrecognised glyph is announced as the neutral "Binding action" rather than guessed at** — guessing is a one-in-two chance of calling the destructive button the harmless one, which is the single wrong answer in this popup that costs the user a binding. The old row walk is kept below it, so a layout that puts the buttons back inside the row still resolves; the icon branch runs first, so the two can never disagree about a button they both see.
  - **The conflict list was rendered but silent, and had been since the 0.39 port.** `.detail-conflicts` carries its "This control is also assigned to:" in a header that is **not a nav item**, so nothing said a conflict existed at all — the `.conflict-row` items were announced only if you already knew to arrow down into them. The dump had **seven** on screen unspoken. The summary that used to speak this lived in `handleBindingEditResult` on the AngularJS panel; that path did not regress at the cleanup, it was orphaned outright by the Vue rewrite (every selector it used matched zero elements) and `8fde680` removed what was by then a corpse. So the warning has been missing since the port, not since the removal — worth stating, because the commit is the obvious suspect and is not the cause.
  - **Keyed on the conflict NAMES, never on the popup opening.** Reassigning to a different control without leaving the popup produces a new set that must be announced, and an unchanged set must not re-announce on every poll tick. Sent at `P.SYSTEM`, which held-navigation coalescing never captures — a warning that a sweep could delay or drop is not a warning. An **empty set is deliberately silent** rather than "no conflicts": opening the editor is not a question anyone asked, and narrating the non-event on every open is the chatter the slam gate's `NONE` state already refuses. Absence of the warning is the all-clear.
  - **The summary landed every time and was never heard, because the popup's own focus move cut it off.** Being sent at `P.SYSTEM` protects it from the nav-burst coalescing, which is a different mechanism and does nothing about a later utterance *interrupting* it — and the focus announcement that follows the popup being populated is exactly that. So it arms the same queue the tab name uses (`armSpeakQueue`): the next navigation utterance goes out with `interrupt:false` and plays behind it rather than over it.
    - **The queue is named for the mechanism, not for the tab** (`_speakQueueAfterText`/`_speakQueueUntil`, armed through `armSpeakQueue`/`clearSpeakQueue`). It has two callers now, and a variable called `_vueTabQueueText` holding a conflict summary is how the next reader concludes the conflict path has no queue and adds a second one.
    - **The duration is per arm, and the conflict window is longer than the tab's** (`VUE_CONFLICT_QUEUE_MS` 2500 against `VUE_TAB_QUEUE_MS` 900). A tab name is two words and the landing focus follows it closely; a conflict summary is a whole sentence of action names, so the focus move it has to outlast can arrive much further into it.
    - **The COUNT is per arm too, and that is the half that actually fixed it** (`VUE_CONFLICT_QUEUE_MAX` 4, against 1 for a tab). A tab name is followed by exactly one thing, so one is right there — but the binding popup emits a short **burst** as it settles, and with a cap of one the window was spent on the first item while the second interrupted the summary regardless. The fix was live, correct, and produced the identical symptom, which is why it needed the mod's own `speech_log` to see: it records `interrupt` per utterance, and the sequence read `summary(interrupt) → 'Automatic'(+29 ms, queued) → 'Assigned control, A button'(+234 ms, INTERRUPT)`. Both follow-ups are `P.CONTROLLER`, so nothing in the source tells the settle burst from a real move; only the count does. The cap is what bounds the cost — uncapped, a held sweep inside the window stacks an utterance every ~240 ms behind a summary nobody is waiting on any more, which is the hazard the one-only rule existed for. Past either bound, a genuine move interrupts again (measured at +2891 ms in the same log).
    - Note the neighbouring hazard, which is not what bit here but shares the door: `scheduleSpeak` clears any pending `speakTimer`, so a focus announcement scheduled within `DEBOUNCE_MS` of the summary would **replace** it outright and the summary would never be spoken at all. The text-keyed arm degrades correctly there — no emit, no window — rather than protecting the wrong utterance.
  - `diagnostic/binding_editor_sim.js` scenario 11 drives the real `emitSpeak` against a fake clock with the real five-conflict sentence, asserting the landing item queues, that only one does, and that the **un-armed** form interrupts — so the check cannot pass for free. `tab_readout_sim.js` scenario 10 lifts the same renamed helpers, which is what keeps the two callers from drifting.
  - `diagnostic/binding_editor_sim.js` (`node diagnostic/binding_editor_sim.js`) replays all of it against a fake DOM built to the shape the dump shows, lifting the functions out of the source by name for the reason `binding_readout_sim.js` gives. It builds **both** layouts and asserts the old row walk answers "Button" on 0.39 while still working on 0.38, so neither check can pass for free, and it greps the source for the icon lookups and for the branch ordering the fix depends on.
- **The controller hints wait for the user to be idle, and any movement restarts the wait** (`VUE_HINT_IDLE_MS`, 3 s; `vueHintNoteActivity`). The poll's `activityChanged` only sees DOM focus moves, so it is not enough on its own: the radial menu has none, because its items are painted on a canvas. There the hint went out 3 s after entering a menu however busy the stick was, and the next item cut it off. A direction press in `trackNavigationInput` and every radial centre change now cancel the pending hint, and the next poll tick re-arms it for a full 3 s. `diagnostic/radial_sim.js` scenario 11 covers it.
