# App: settings, speech, AI describer, secrets, UI bridge, updater, logger

The Rust app's service modules. The reasoning below was worked out on the Python application this was ported from; where a decision only made sense there, it says so.

- **The settings panel** (`src-tauri` `panel.rs` + `ui/`, backed by `beam-base` `config.rs`): the GUI for `beamtel_config.json`. Speech backend and voice enumeration via Prism, real-time tone testing (`src-tauri` `tones.rs`).
- **beam-speech**: all speech output, backed by Prism through the `prismer` crate, statically linked into the exe (no DLL to ship or find); `prism.rs` adapts it, sharing one context across threads and serialising calls. Picks a backend by priority (`auto`) or by configured name, re-acquires it when a screen reader starts or exits, and exposes per-backend capability bits plus a braille primitive. Prism replaced the old SRAL wrapper, which upstream deprecated in favour of Prism in August 2026; the hand-written `libloading` FFI to `prism.dll` was replaced by Prismer in November 2026.
- **beam-engine ai_describer.rs**: the AI Describer pipeline. Captures the game window (`capture.rs`, GDI `BitBlt`, with the UI hidden for the grab), sends the image to a vision model with a blind-friendly system prompt, returns the spoken description. Multi-provider: the registry (`beam-base` `ai_registry.rs`) dispatches on `ai_describer_provider` to one of two backends, Google Gemini (`generateContent`) or OpenAI (`/v1/responses`, default `gpt-5.6-terra`). Each provider owns its own config keys (Gemini's keep the original unprefixed names; others are namespaced, e.g. `ai_describer_openai_*`) and declares its extra request parameters, which the settings panel turns into controls automatically. Model lists are hand-curated allowlists because neither provider's model listing exposes a vision-capability flag. API keys are validated against each provider's free model-listing endpoint (`try_validate_api_key`). Logs all descriptions and API errors to `%LOCALAPPDATA%/beamtel/ai_descriptions.log`. Invoked in-game by F10 then Space. Network calls use `ureq`, which ignores the Windows registry proxy and uses bundled TLS roots: a corporate proxy is the case to check if validation fails on one machine only.
- **beam-base secretstore.rs**: at-rest protection for the secrets in `beamtel_config.json`, today the two AI describer API keys. Windows DPAPI (`CryptProtectData`), stored as `dpapi:v1:<base64>`.
  - **DPAPI rather than a keyring or a passphrase, because it is the only store that needs no key of our own.** The ciphertext is tied to the Windows *user account*, so beamtel needs no first-run prompt and no secret of its own to unseal it, while a copied config file, a synced profile or a backup carries nothing usable. Scope is deliberately the user and not the machine (no `CRYPTPROTECT_LOCAL_MACHINE`): another account on the same PC must not be able to read the key. This is not secrecy from code already running as the user: anything with that privilege can call `CryptUnprotectData` too. It is the guarantee a browser gives a saved password, and it is the one that matters here: the key stops being visible in a file people paste into bug reports.
  - **Which settings are secrets is decided by NAME, and there is exactly one list.** `SECRET_NAME_PARTS` is matched as a substring (the names are compound, `ai_describer_openai_api_key`) so a provider added later is covered the day it is added rather than the day someone notices. The MCP server's `get_config` masking reads that same list rather than carrying its own copy: two lists would drift on the first new provider, and the failure would be silent in the direction that leaks.
  - **A failed *seal* falls back to plaintext; a failed *unseal* does not fall back to anything.** The two are not symmetric. Refusing to store a key because DPAPI was unreachable turns hardening into a feature outage, and the caller has just validated that key against a live endpoint. But a protected value that will not decrypt is a fact, and `unprotect` returns **None** for it, distinct from `""`, because a blob from another Windows account (a restored profile, a copied config) is not "no key configured": the fix is to enter it again, and announcing "no API key set" would send the user hunting for a key that is plainly there in the file.
  - **Migration is on LOAD, and writes back.** `migrate_config` runs inside config loading for both the engine and the settings panel, so an existing install is sealed on the next run rather than only when the user next re-enters a key they have no reason to touch again. The panel writes it back too: a config that is only ever opened and closed would otherwise stay in the clear forever. Idempotent: an already-marked value is skipped, so a load costs nothing after the first.
  - **The key is unsealed at the point of use, never into `ai_describer_settings`.** The describe worker unseals into its own frame; the settings, which is what state dumps and the MCP surface see, hold only the sealed form.
- **beam-engine ui_bridge.rs**: the WebSocket server on port 8765 (tokio + axum) plus the GE-Lua TCP relay on port 8766. Bridges UI events to speech output and validates `accessibility_action` messages against the six controller-menu commands before handing them to the command-dispatch worker. Drift events reach `beam-reports` `drift_speech.rs` through its `register_drift_event_callback`.
- **beam-engine updater.rs**: the GitHub-only auto-updater. One release asset (`ASSET_NAME`, `BeamNG_accessibility_mod.zip`), one hand-maintained `APP_VERSION`, and a two-phase install that survives the restart the self-replacement forces. **There is no release pipeline yet**: the Python one (`build.py`, `release.yml`, `scripts/release.ps1`) was removed, and `xtask` has to take over packaging the asset, stamping the mod zip and checking `APP_VERSION` against the tag before the updater has anything to fetch.
  - **The running exe cannot replace itself, so the swap happens after we exit.** Windows holds the image open for the life of the process, so `apply_and_restart` writes a windowless `.cmd` that waits until the program is gone, then robocopies the staged tree over the program directory and starts the new exe. **It asks the FILE, not the process table.** The question the helper actually has is "can I overwrite this yet", and opening the exe for append answers it directly: a sharing violation for as long as Windows holds the image, success (writing nothing, hash unchanged) the moment the last handle goes. That also settled a two-process problem the Python's onefile build had (a bootstrap plus the payload it spawned, both with the exe's name, and the bootstrap held the image), so a PID wait would release the copy early. The `tasklist | find` pipeline it replaced was wrong in **both directions**, because its stderr went to `nul` and any failure of `tasklist` itself was then indistinguishable from "no such process": measured 2026-08-28, one call took **103 seconds** and answered "gone" while beamtel was still up, and the post-start check answered "did not appear" about a process that had in fact started. The verification after `start` is the identical test read the other way round (a running beamtel holds its own image open, so a writable exe is one nothing is running from). A wait timeout abandons the update without touching either the live executable or its cache.
  - **The helper still removes `.appdata` before the copy.** That was the Python build's onefile cache, a fixed name beside the exe holding the old build's unpacked payload, and the only moment it is safe to delete is the one the helper runs in. A Rust build creates no `.appdata`, but the first Rust update lands on top of a Python install, so the step stays until no Python install can be updating.
  - **The helper uses `CREATE_NO_WINDOW` plus a new process group**, because standard-handle redirection does not control console allocation and `DETACHED_PROCESS` makes `CREATE_NO_WINDOW` inapplicable; the new group isolates the helper from console-control events, and an ordinary Windows child process survives its parent's exit. Its standard handles are explicit null handles, because the release exe has no console to inherit. **Every step after the copy is logged and VERIFIED**, because `start` is asynchronous and reports almost nothing: an older helper's last line was written *before* the launch attempt, so a restart that silently never happened left no evidence anywhere. Every external command is fully qualified to `%SystemRoot%\System32`, and the `cmd.exe` launch is fully qualified and uses `/d`, so PATH or Command Processor AutoRun customizations cannot change the helper that runs.
  - **The program directory is where the exe was launched from** (`beam_base::paths::program_dir`). The Python had to use `sys.argv[0]` rather than `sys.executable`, which under its onefile build pointed into a temp extraction directory that Windows deletes. `program_dir()` is also the directory `install_mod_interactive` reads the mod zip out of, so the two halves of the install cannot disagree about where the program lives.
  - **The pending flag is written only AFTER the download validates and stages.** `pending_update_version` is a promise to the next run that there is a new mod zip beside the exe waiting to be installed; a promise made at the "yes, update" answer could not be kept by a download that then failed, and the next start would offer to install an update that was never applied. The next run also requires that flag's version to equal its own `APP_VERSION`: helper timeouts, copy failures and restart failures happen after the old app has exited and therefore cannot clear the flag, but they necessarily leave the old version running on the next launch. That mismatch clears the stale promise and returns to the ordinary update offer instead of falsely announcing success.
  - **The launch is GATED, not reordered.** The game launch sits in the middle of `run_engine`, after speech, audio and the UI bridge, and moving it would change what is initialised by the time the game starts. So `LAUNCH_GATE` blocks just that block while everything above it proceeds under the dialog, and `LAUNCH_ALLOWED` is read once immediately after the wait, which is why `deny()` fires at the point of no return, immediately before the helper is spawned, and not at the user's "yes": denying earlier would strand a user whose download then failed or who cancelled it, because the engine reads the decision once and never looks again. The wait has a timeout, and the timeout is the failure path: a flow that never answers degrades to an ordinary start rather than to a game that never starts.
  - **A failed check is silent and a failed update is loud.** `check_latest` answers `None` for every failure it can have (offline, rate limited, malformed JSON, a release with no matching asset), because a check that cannot complete must never hold up a startup, still less the game behind it. Once the user has said yes, the opposite applies: every failure reports itself, because they are now waiting for something.
  - **The bundle is validated before anything is staged, and the required members are the test.** A truncated download and an HTML error page saved under a `.zip` name are both plausible, and everything after this point overwrites the user's install: reading every member's CRC plus the presence of the exe and `bng_screenreader_mod.zip` is what separates a release asset from a file that merely arrived. The zip-slip guard in `stage` is there for the same reason and not because the archive is untrusted: this is the one place in the project that writes remote-named paths into the program directory.
  - **`ASSET_NAME` must equal the release asset's name, and `APP_VERSION` must equal the tag.** Both are one contract seen from two ends with nothing in the code that ties them together. The Python pipeline checked the tag half before building, because a drifted `APP_VERSION` does not fail loudly: every client simply concludes it is already up to date and the release reaches nobody. The xtask release must do the same.
  - **The manual button's gate decides nothing.** Startup and the Main-tab button run the same flow; by the time the button can be pressed the deferred launch has long since been released, so its gate is `NullGate` rather than an already-set one: an inert gate cannot fire a second launch. `manual` additionally makes the flow ignore the config gate and report the up-to-date case, which the startup check deliberately does not.
  - **Phase two reuses `install_mod_interactive` rather than copying it**, so the post-update install and the Install Mod button are the same act, including the version comparison and the freeroam-layout cleanup. Every one of its early exits has already told the user what went wrong, so the caller must not report anything a second time. The flag is cleared whichever way the user answers (it records that an update was applied and the mod has not been *offered* yet, and it has now been offered), and declining does not withhold the game.
  - **Which mod zip is newer is decided by a STAMPED version, never by file mtime.** The packager writes `bnvda_mod_version.json` (`MOD_VERSION_MEMBER`) into the mod zip and `mod_zip_version` reads it back. An mtime cannot answer this question, because nothing in the path treats it as data about the build: the installer's own copy *preserves* it, so an installed zip carries whatever some other machine's clock said when it was built; unpacking a release does not restore it at all and invents "now"; and robocopy forwards whatever it is handed. Comparing those compares clocks across machines, which is how a freshly downloaded release came to announce itself as older than the copy it was replacing. An **unstamped** installed zip is treated as older, which is correct (it predates stamping), and a byte-identical pair short-circuits to "already installed" before any version is read. Where neither side carries a stamp the dialog says so rather than inventing a direction. The xtask packager must keep writing the stamp.
  - **The dialogs say the minimum and carry no links.** The offer is the two version numbers and the question, and it ends there: the release notes are commit messages rather than a maintained changelog, so `Release` carries no `body`, and neither the restart nor the mod prompt after it needs announcing in advance because each announces itself when it happens. There is no releases-page URL in the failure boxes: getting a link out of a message box with a screen reader is possible but painful, so a URL there is a cost with no payoff. Accessible is not the same as chatty.
  - **`APP_VERSION` is in the window title** (`src-tauri` `shell.rs`, "BeamNG Accessibility <version>"), so the running version is something a screen reader announces on focus rather than something you go looking for, which is what makes "did that update actually land?" answerable after the self-replacement restart. It is appended, so `find_game_window`'s `startswith` prefix match is untouched.
- **beam-base logger.rs**: rotating file logger (`bnvdahook.log`, 1 MB max, 3 backups).
