# App: beam-engine and the small report modules

The engine half of the Rust app (`rust/crates/beam-engine`: telemetry, listeners, keyboard layers, menus) and the pure report modules it drives. Ported from the Python `beamtel.py` and its helpers; Python names cited here keep their spelling in the Rust without the leading underscore (`rust_plans/engine-map.md` maps each one). Sims are Rust tests: `cargo test -p <crate> --test <name>`.

- **beam-engine** — Main entry point. UDP telemetry listener, keyboard command system (F9 hotkey + modifier combos), drives audio and speech.
  - **Hill-climb challenge reports are captured in-process.** `beam-road` `challenge_results.rs` pairs every 20 Hz `R2` packet with the closest telemetry snapshot between native mission start and finish events, writes a durable NDJSON trace plus an atomic summary under `%LOCALAPPDATA%/beamtel/challenges/hill_climb`, and computes time-weighted surface, slip, control, speed, and data-quality statistics. Completion speaks the official time and opens the report in the existing virtual browser; Functions > Challenge reports reopens retained attempts.
  - **Controller navigation has three flat, wrapping screens with independent cursors.** Startup selects Status. `status_up`, `status_down`, and `status_repeat` operate on the selected screen; `next_menu` and `previous_menu` wrap through Status, Functions, and Click spots; `activate` repeats the selected Status value or runs the selected Function or clickspot. Ctrl+S still controls only arrow-key capture and resets the Status cursor when enabled, while its arrows use the same screen-aware navigator. `STATUS_METRICS` remains the one telemetry catalog. `FUNCTION_ITEMS` is a category-tagged catalog that routes to the existing F9 handlers through synthetic in-process events, so controller activation does not inject keys or duplicate command implementations. The one exception is terrain scan: its direct handler requires live driving telemetry and never falls through to UI activation. Availability is recalculated for every press, including scanner, waypoint, nearest-POI, camera, redline, turbo, pneumatic, and terrain dependencies. Crossing a category boundary in either direction prefixes the category; entering Functions always speaks screen, category, and item. TCP callbacks enqueue onto the serial `command-dispatch` worker before taking the state lock or speaking.
  - **Road-guidance diagnostic capture is in-process.** `beam-road` `road_diagnostics.rs` receives each validated `R2` packet from the sole 4462 listener and pairs it with the closest telemetry snapshot; a second process could not bind the same UDP port. The MCP `road_diagnostic` tool controls durable NDJSON recording and review. Detailed Lua fields are opt-in for the recording window, and the summary distinguishes raw settled packets from actual audio scheduling events. See [road-guidance-diagnostics.md](road-guidance-diagnostics.md).
  - **Click spots is a controller screen over the same cache and activation path as the keyboard browser.** Detection off exposes one enable item routed through the existing Ctrl+Shift+C handler; loading and empty results expose spoken, non-mutating placeholders. `TRIGGER_LIST:<count>` starts a staged transfer and `TRIGGER:` rows are published only when every announced cache index has arrived, so navigation never sees a partial list. Lua sends `TRIGGER_LIST_PENDING` before activation, recache, and vehicle-switch rebuilds and `TRIGGER_LIST_OFF` on shutdown/world reset, preventing stale controls from surviving a vehicle change. Controller Activate and virtual-browser Enter both call `activate_clickspot`, preserving the SNAP, delayed press, and delayed release sequence exactly. The live-applied `announce_clickspot_actions` setting defaults to false and gates both successful `SNAP_OK` “Jumped to …” confirmations and `SNAP_FAIL` “Cannot jump, …” errors; discovery speech remains available.
  - **Status capability filtering remains shared across keyboard and controller input.** Tire pressures and brake temperatures are individual wheel metrics whose availability comes from Lua's telemetry-presence mask, so `F/RL/RR`, `FL/FR/R`, and ordinary four-corner layouts all use the same catalog without phantom zero rows. The same mask exposes Clutch Temperature only when Lua found a powertrain device with live clutch thermals. Engine and Oil Temperature need `TELEMETRY_HAS_ENGINE_TEMP` (a combustion engine exists; an EV reports 0 C for both, which used to be read as 32 F). The decoder ORs that bit into every pre-v5 packet, and OutGauge has no mask, so both keep the old behaviour. `TELEMETRY_HAS_ELECTRIC` brings in Motor Power, Motor Torque and Range. Range reads "unknown" while Lua sends `-1`. It does **not** hide then: rows are addressed by index, so a row whose availability follows its reading (here, appearing and vanishing as the car moves and stops) shifts every row below it under the cursor, and the controller's repeat button reads a different metric. A row's availability must depend only on what the vehicle *has*. On a pure EV the Fuel row becomes Battery, because `fuel` is the combined storage ratio; a hybrid keeps Fuel. F9+E says "No engine temperature" rather than reading a number that doesn't exist. Boost Pressure uses OutGauge's standard `OG_TURBO` capability bit in both the stock and extended packet, so naturally aspirated vehicles omit that row instead of reading zero boost. The extended packet sets the bit and carries the reading for a supercharger as well as a turbo; the stock packet still knows only turbos. `beam-reports` `induction_report.rs` words the `F9` `Alt+T` report (see `docs/lua-telemetry-protocol.md`).
  - **`F9` `Space` is one key with two answers, split on whether the game world is live.** Driving, it fires a terrain sonification scan; in a menu it keeps doing what it always did and activates the on-screen control. That is a real disambiguation rather than a priority call: the only screens `bnvdaRuntime.js` offers a context action for are the freeroam wizard and the configurator, both of which run with **no level loaded**, so the two answers can never both apply. The world test is `world_is_active()` — telemetry seen on 4444 within `WORLD_ACTIVE_TELEMETRY_S` — because that feed is the vehicle VM's own protocol and therefore exists exactly when a level is loaded with a vehicle in it. It is physics-driven, so it also stops while the game is **paused**, and a scan is declined there; that is the conservative way round, since the fallback is the harmless no-op the key already did. The scan speaks nothing on success: the reference ping at the head of the cloud *is* the acknowledgement, and speech would talk over the first half-second of the scan it was announcing. A watchdog thread speaks only if the mod never answers, because silence and a dead extension are otherwise identical.
  - **The cannon shot readout has no keybind, and that is the design.** It announces itself when the car comes to rest, which is the only moment it has anything to say — and the moment you are guaranteed to be listening, having just heard the crash. `cannon_shot_phrase` follows `dock_phrase_ramp`'s doctrine because it fires unprompted after a crash and every clause it adds is one nobody asked for: distance and how far off line, always, since those two *are* the outcome; apex, what it stopped beside, and the comparison against the previous shot only when each is the interesting thing about that shot. Nothing in it confirms a shot went well — there is no such thing as a good shot out of a cannon with no horizontal aim, and saying so would be inventing a target. It uses the **whole-number long-distance form**, not `fmt_distance`, which is tuned for implement clearances and renders a 300 m shot as "984.3 feet". The comparison clause is what makes a session-only log worth keeping with no key to read it back: the answer to "did raising the barrel do anything" arrives inside the announcement of the shot that answered it, and it skips a previous shot that never settled, because that one has no landing place to compare against. Spoken **without** `exclude_from_buffer` — unlike every keypress readout this is unsolicited, so it is exactly the kind of thing worth replaying.
  - **`terrain_scan_listener` reads with a 65535-byte buffer**, not the 1024/2048 the other listeners use. A snapshot is one datagram of a few kilobytes, and a short read there fails as a landscape that stops halfway rather than as an error. It also *renders* the scan on its own thread — see `render_scan` in `beam-audio`.
  - **The alignment readout is one key with four answers.** `F9` `I` speaks the cannon's firing state when `cannon_active` (you are sitting in a ramp machine), otherwise the docking readout, otherwise **your own machine's deck state** when it has a ramp of its own, otherwise "instrument is off". Cannon-first because once you are in the cannon the alignment task is over and the aiming task has begun; folded into the existing key rather than given a binding of its own, for the same reason the slam gate rides on the docking toggle. `dock_phrase` dispatches on the mode to `dock_phrase_impl` (unchanged, and `dock_readout_sim` (`beam-engine`) scenario 16 asserts it is byte-identical to before the split) or `dock_phrase_ramp`, which shares none of its vocabulary — there is no band, no thickness, and nothing on a car that goes up or down.
  - **`F9` `Shift+V` is one key with two alignments**, routed on `dock_mode_active`: instrument on sends `RAMPALIGN` to the mod, otherwise the scanner's `ALIGN` path runs byte for byte as before. `ramp_align_phrase` is a pure function next to `dock_phrase` rather than inline in the listener, because the wording and the two margin bands are the part worth checking without the game; `dock_readout_sim` (`beam-engine`) scenario 18 mirrors it, including that an `NA` margin is **silent** — a false "it will not fit" about a machine that fits is how a driver learns to ignore the clause.
  - **The deck readout is the answer for the machine you are SITTING IN**, and every other figure this key can produce measures from one machine to another. It exists because fixing the phantom-cannon bug left a hole: from the seat of a `us_semi` rollback the key used to answer with the cannon's aiming state (wrongly), and once that was corrected it answered "Docking instrument is off" — correct, and useless. `ramp_self_phrase` reads the ramp's live pitch and then every hydraulic group the machine has, and it reads them out **unconditionally** rather than following `dock_phrase_ramp`'s bad-news-only rule: that rule is about clauses nobody asked for appended to an utterance that was going to happen anyway, whereas these numbers *are* the question, and a readout that went quiet because the deck happened to be level would be indistinguishable from a broken one.
    - **It is ordered strictly BELOW a live docking reading, unlike the cannon branch.** The cannon wins outright on the argument that once you are in the cannon the alignment task is over; that argument does not carry here, because a hauler is a perfectly ordinary thing to drive up somebody else's ramp, and an alignment readout the driver deliberately switched on must not be displaced by a fact about their own bed. So the branch fills in the three cases that previously had nothing useful to say and changes no case that did.
    - **Tilt is an ANGLE off live geometry; extension is the RAM's own travel.** Not a stylistic split — the geometric route is wrong in exactly the pose the readout exists for. Measuring the mouth's displacement from the machine's reference node along the deck axis is exact at rest and picks the tilt up as false extension, because the reference node does not lie on the axis the deck rotates about: measured on the rollback, a pure 10.2° tilt with the bed fully home slid the mouth **0.123 m** along its own axis, i.e. four inches of announced extension on a deck that had not moved, growing with the angle. The ram carries no such term — against the same vehicle its stroke tracked the geometrically measured deck travel to **1 cm over 4.88 m**. The angle keeps the tilt job because it is what the driver of the car about to go up the ramp needs, it is what `dock_phrase_ramp` already speaks, and it survives on a ramp with no hydraulics at all; the rams then say how much stroke is *left*, which the angle cannot.
    - **Groups are named by their own `directionElectricsName`, never by a word list.** That field is the string the vehicle's own Special Vehicle Keys bindings are driven by, so a machine nobody has thought about reports its controls under the names its own key list already uses. A leading segment shared by **every** group is dropped (`upfit_tilt` / `upfit_extendRetract` / `upfit_extendRetractFeet` → "tilt", "extend retract", "extend retract feet") and that requires **two or more groups** — a prefix is only identifiable as a namespace by several names sharing it, and on a machine with one group its first segment may be the only word saying what the thing does. `dock_readout_sim` (`beam-engine`) scenario 19 asserts the guarded and always-strip forms differ.
    - A long stroke reads as a **distance** and a short one as a **percentage** (`RAMP_SELF_DISTANCE_STROKE_M`). Both figures are always available; the question is which one a driver can act on. Five and a half metres of deck travel is the run-up they are about to drive; "1 of 2 feet" is a worse way of saying 34 percent. It is a property of the ram, so nothing needs to know what vehicle it is on.
    - **The lip's height above ground is the third figure, and it is the only one that answers "can a car get onto this".** Neither of the other two does it alone. Measured on a `us_semi` `tc82s_rollback`: home and level the lip sits **1.30 m** up, **full tilt alone only brings it to 0.95 m**, and it is running the bed fully out *as well* that puts it at **0.15 m**. So a driver reading pitch and extension has to combine them; the lip is the answer directly, and it is stated in **both** directions (`Lip on the ground` / `Lip 4.3 feet up`) rather than as bad news only — this readout is solicited, so silence there would be indistinguishable from a mod half that cannot measure it. `be:getSurfaceHeightBelow` reports failure as a huge **negative**, not nil, so both copies use a magnitude band; `-999` is the sentinel and must never be `0`, which reads as the single most reassuring thing this readout can say.
    - **Both latches heartbeat, and that is a correction found in testing rather than a precaution.** The VM pushes hydraulics on change and `implementProximity` sends `RAMPSELF:` on change, and neither latch can be cleared by the *other* process restarting — which is exactly what happened: with beamtel restarted and `implementProximity` reloaded, the GE table was empty, the VM's change test then suppressed every push, and the key stayed silent until the bed was physically moved. The failure is invisible, because the fallback answer ("docking instrument is off") is a real answer for a real reason. The `ON` probe does re-arm the GE latch, but it cannot reach the VM's. Same argument, same interval and same fix as `IMPL_PUSH_HEARTBEAT_S`, which this repo already paid for once.
    - `-999` is the mod's "could not measure" pitch sentinel and must never be `0`, which reads as a perfectly level ramp; beamtel renders it as `Ramp angle unavailable` and still reads the rams out.
  - **`cannon_active` is derived from geometry, not from a jbeam name allowlist — but "has a ramp" is NOT that geometry.** The two aiming values come free off existing telemetry because large_cannon's controller publishes them there itself: `electrics.values.rpm = targetInclination * 1000` and `electrics.values.gear = "<strength>%"`. The signal was `rampGeometry.has()` on the player's own vehicle, which was sound for exactly as long as large_cannon was the only vehicle whose ramp resolved at all; `rampGeometry`'s part tiers exist precisely so a rollback, a tilt deck and a dry van resolve too, and every one of them then latched `CANNON:LARGE`. Measured from the seat of a `us_semi` `tc82s_rollback`: **"Inclination 100 percent, strength unknown"** — the inclination being the truck's *own engine RPM* over a thousand, pegged because its `hydraulicsCombustionEngineControl` raises idle to 1500 the moment the pump engages, and the strength a gear string that is not a percentage. It also silently masked the ramp readout that machine *should* get, because the cannon branch of `F9` `I` wins ahead of `dock_phrase_ramp`. The signal is now `rampGeometry.isCannon()`, resolved from the presence of large_cannon's **own controller** in the vehicle VM — a capability check on the source of the readout, the same shape of argument `cannonGeometry` makes in demanding a `beamType 7` launcher beam rather than trusting a filename.
  - **That gear abuse is also a regression, and is suppressed rather than tolerated.** The cannon rewrites the gear string on *every* press of the strength keys, so without a `cannon_active` gate on the gear-change announcement, aiming produces a stream of `extended_gear_to_phrase("80%")` across the whole manoeuvre. The strength is not lost — `F9` `I` reads it on demand, which is the right shape for a value you sweep and then check. (The swept `rpm` needs no such gate: it never reaches `beam-audio`, and the shift tone is driven by the `DL_SHIFT` dashboard bit, which a cannon has no engine to set.)
  - **The mode latch is not cleared on `DOCKCLEAR`/`DOCKFAIL`.** Losing the target is not a change of mode, and clearing it there re-announces every time you drift across the feed's edge — measured at twenty announcements for one approach. Only a part swap, a vehicle change or the toggle resets it, and the toggle claims the latch itself so it and the listener cannot both announce the same change. `implement_proximity_sim` (`beam-engine`) scenario 12 asserts both halves.
  - **The `DOCK:` parse ladder must be `elif`, not a second `if`.** A successful 15-field split leaves `len == 15`, which is also `!= 13`, so an independent second test immediately re-splits it down to 11 and throws the mode and margin away on every ramp packet.
- **beam-reports wheel_report.rs** — Status-screen wheel rows, pure: parses `wheelReport.lua`'s WHEELS packet and labels each wheel from its position (axles, sides, inner/outer, `dual`, `trailer`). `beam-engine`'s `wheel_report_listener` stores the rows, and `wheel_rows` entries in `STATUS_METRICS` expand them through `status_rows()`, falling back to the struct's fixed slots when the report is stale. See `docs/lua-wheel-report.md`; sim `wheel_report_sim` (`beam-reports`).
- **beam-reports camera_lineup.rs** — Pure geometry, tone mapping and wording for the free-camera line-up guide (`F9` `Alt+G`); the listener and key layer are the `lineup_*` block in `beam-engine`, the synthesis `render_lineup`. See `docs/camera-lineup.md`; sim `camera_lineup_sim` (`beam-reports`).
- **beam-reports audio_debug.rs** — Pure row parsing, spoken wording and left/right stepping for the audio debug browser (`F9` `J`); the sockets and browser glue are the `aud_*` block in `beam-engine`. Kept out of beamtel so `audio_debug_row_sim` (`beam-reports`) can import it. See `docs/lua-audio-debug.md`.
- **beam-reports drift_speech.rs**: speech for the game's free-roam drift display, fed by `driftAccessible.lua`'s `drift_event` frames through `register_drift_event_callback`. See [lua-drift.md](lua-drift.md).
  - `drift_phrase` reads the display's own text, with "+80" said as "plus 80".
  - `DriftAnnouncer.quiet()` is the window in which `beam-engine` holds back the automatic speed announcement and the spoken compass heading. Both guards still advance their state (`last_bucket`, `last_announced_compass_idx`), so nothing is spoken late. The compass clicks are untouched.
  - Spoken gear changes (`report_gear_change`) stay on in the window but queue instead of interrupting. In the first driven run, seven shifts cut off the drift speech, including a burst of four bonus and combo lines. F9 gear queries still interrupt.
  - The window ends on `hidden`, or 10 s after the last event, so a lost `hidden` can't mute them for good. Lua sends a silent `alive` every 3 s while the display shows, which keeps a long slide inside the window.
  - It is off with `drift_speech_enabled`. Sim: `drift_speech_sim` (`beam-reports`).
- **beam-reports fuel_stations.rs**: pure parsing and wording for `fuelStations.lua` (see `docs/lua-fuel-stations.md`).
  - `row_line` gives the browser line: name, distance (`format_long_distance`), an eight-way direction relative to the car, fuel types, then "unofficial, the game can't refuel here" or "not for your vehicle".
  - `event_phrase` gives what each event says, or nothing to stay quiet.
  - **The bearing arrives car-relative and positive left**, computed in GE from `up:cross(fwd)`. No compass heading is involved, so the 180° heading offset cannot creep in.
  - **`beam-engine` keeps only what the key needs:** target id and name, in range, parking. It updates these from events on the command worker.
    - `scan_done` clears them, because a new catalogue means a new level.
    - F9 then Shift+F reads them to choose between cancel parking, park, and the list.
    - Rows are swapped in whole on `FS_END`, like the environment browser.
    - `FS_WAIT` extends the no-reply timer to 8 s and says "Finding fuel stations".
