# Lua/JS: UI Accessibility Runtime

- **`lua/ge/extensions/bnvdaAutoSpawner.lua`** — Deferred UI app spawning (currently commented out).
- **`ui/ui-vue/mods/bnvda/bnvdaRuntime.js`** — The whole UI accessibility layer, bridging BeamNG UI events to Python. (The old AngularJS `ui/modules/apps/bnvda_hook/app.js` was folded into this file and deleted.) Transport is `lua-tcp`: CEF → `bnvdaBridge.lua` → Python's TCP relay on 8766. Per-screen text extractors, a MutationObserver, a `focusin` listener and the Vue focus poll all funnel into one `scheduleSpeak()` gate, which layers controller dominance, a same-text dedup, a 10 ms debounce, and held-navigation coalescing.
  - **The poll decides WHAT changed; the game's events decide WHEN it runs.** The engine dispatches `uinav-focus` on `document` the moment a target holds focus and carries `focus-visible` (`services/uiNavFocus.js`), and every input arrives as the `ui_nav` DOM event with both edges. Each calls `kickVuePoll()`, which runs `pollVueFocus` on a zero timeout and marks the tick so `processFocusChange` skips `FOCUS_DEBOUNCE_MS`. Measured on the part selector before this, focus-event-to-speech was 81–135 ms against a nominal 55: the observer, `focusin` and the poll all re-armed one 30 ms debounce, and a tick usually landed inside it.
    - **The poll's CPU cost was never the problem** — about 2 ms a tick with 130 part rows expanded (median 1.6, worst 2.7). The lag was waiting, not work. Worth stating because the size of the parts tree is the obvious suspect.
    - **The event kicks the poll rather than announcing by itself.** The poll body is the one place that knows a tab change speaks before the item under it, that a category echo is swallowed, that a parts dropdown is mid-activation and that the binding popup's stale markers are to be ignored. A second announcer on the event would have to re-derive all of that, and would speak the landing item ahead of the tab name it belongs to.
    - **The kick is deferred, never inline.** The listeners are capture phase, so they run before the game's handler has changed anything and before Vue has flushed.
    - **The interval is now only a fallback**: `NAV_POLL_FAST_MS` (60) for `NAV_POLL_ACTIVE_MS` after any input or any change it finds, `NAV_POLL_IDLE_MS` (150) otherwise. A click kicks it too; a keystroke only keeps it fast. `uinav-focus` fires twice per move a few ms apart, and the second tick finds the signature unchanged.
    - AngularJS screens are untouched: `vueScreenRoot()` is null there, the kicked tick returns early, and the observer path announces as before.
  - **Translation** — `findTranslateFunc()` must resolve `window.vueI18n.global.t` (petite-vue-i18n, published by the game's `ui-vue/src/services/translation.js`) on Vue screens, falling back to `window.angular$translate.instant` (published by `entrypoints/main/main.js`) on the remaining AngularJS ones. `bngApi.engine.translate` does **not** exist in 0.39; probing it first meant every lookup fell through to the last-resort key-humanizer, which spoke raw key fragments — `ui.common.vehicleAccessoryOn` as "vehicleAccessoryOn", and state keys like `vehicle.engine.oilLevelCritical.true` as a bare "true". The humanizer is deliberately never cached, because the real translator only appears once the UI finishes booting.
    - **In 0.40 `vueI18n.global.t` is not enough on its own: try the game's `$ctx_t` first** (`window.bngVue.app.config.globalProperties.$ctx_t`, i.e. `contextTranslate` in `services/translation.js`). `preprocessLocaleJSON` keeps every string with an AngularJS `{{x | translate}}` placeholder *out* of the Vue messages and serves it from `angular$translate` instead, and only the game's wrapper knows to route those keys there. Vue alone returned the bare key for `ui.camera.switched`, `vehicle.driveModes.defaultMode` and `vehicle.vehicleController.shifterModeChanged`. `$ctx_t(descriptor, true)` also translates the context values, including the `{ txt, prefix }` objects `driveModes.lua` sends for a mode name.
    - **`messageForSeatedPlayers` sends `{ msg, context }` with the context *beside* the key**, so a string payload has to pick up `meta.context`, or the gearbox message reads "switched to '' behavior".
    - **An untranslated key is also what silenced repeated drive mode presses.** The raw key was the same text for every mode, so the per-category repeat filter swallowed each press after the first, and the two-step status messages the ETK's drive modes trigger in the same frame were all that was left to speak. Translated, each mode reads differently, and because the drive mode message arrives last in that frame, it wins the debounce.
    - **Camera names**: `onCameraNameChanged` carries the internal name, which in 0.40 is dotted (`onboard.hood`, and `occupant.FL` for the new per-seat cameras). `cameraDisplayName` reads `ui.camera.mode.<name>`. A seat's label lives only in `CameraConfigChanged`, which is cached, and the position (front right, and so on) is added to the generic "Passenger Seat".
  - **`cleanText` is falsy-guarded**, so it maps `false` to `""` but stringifies `true` to the literal word `"true"`. Never hand it a raw DOM `value` property — Vue components expose booleans and objects there. Use `scalarValue()` first; that asymmetry is why the artifact only ever showed up as "true".

  - **Vehicle selector filter chips state themselves only by class** (`DetailedFilters.vue`, `getFilterOptionClass`), so `vueFilterChipState` reads `filter-active` as "on", `filter-inactive` as "off" and `filter-locked` as "locked". `filter-neutral` deliberately says nothing: it means every option of that filter is enabled, i.e. nothing is filtered. The game's toggle is not a flip, which is why: pressing a chip while its filter is neutral enables **only** that chip (`gridSelectorUtils/filterModule.lua`, `toggleFilter`), and switching the last one off resets the filter to neutral. A filter category heading adds "filtered" from the accordion item's `has-active-filters`. The focused chip re-announces after a toggle with no extra code, because `vueFocusSignature` signs on the element's class.
    - **0.40 opens the selector on the filter panel** (`VehicleSelector.vue`, `defaultDetailsMode: "advanced"`), and controller focus first lands where the D-pad reaches nothing; B twice gets back to the grid. That is the game's, and is left alone on the expectation that it is fixed upstream.
  - **A focused text input is not typeable until `maincef` is the canvas's first responder, and only a mouse click ever makes it one.** The symptom was the parts search on a fresh launch: Y announced "Search, edit", the input genuinely held DOM focus, and every letter drove the game instead (F left the vehicle, H honked) -- until the player clicked into the bar once, after which the controller route worked for the rest of the session. The mod's focus handling was never at fault. The engine routes keys to CEF only while the `maincef` GuiControl (`lua/ge/client/init.lua`) is the Torque canvas's first responder; `setCEFTyping(true)`, which `BngTextInput.js` issues on the input's `focus` event, is necessary and **not sufficient**. Measured in 0.39.4 with the input focused and `setCEFTyping(true)` logged: `isFirstResponder()` false, a held H raised `electrics.values.horn` and produced no `keydown`; re-issuing `setCEFTyping` changed nothing; `setFirstResponder()` alone made the next key land in the input. The stock Y handler takes the same route, so this is very likely a stock gap that mouse users never meet -- not verified with the mod disabled.
    - **`claimEngineKeyboardFocus` runs on every `focusin` whose target is a text-entry element, and again in `armPartsSearchFocus`.** The `focusin` hook is what covers the fields nobody special-cased (licence plate, save-config name); the arm-time call covers a search input that already holds DOM focus and so will not fire `focusin` again. The Lua it sends is guarded on `isFirstResponder()`, so the common case is a no-op.
    - **Lua exposes `setFirstResponder` and `clearFirstResponder` on the object but not `makeFirstResponder`**, which is TorqueScript-only (`maincef.makeFirstResponder(true);`). `clearFirstResponder()` puts back the fresh-launch state, which is how to reproduce this without restarting the game.
    - No sim: the whole fault is in engine state that no fake DOM reaches. Reproduce live by clearing the first responder, pressing Y, and injecting a key at the OS level while watching the horn.
