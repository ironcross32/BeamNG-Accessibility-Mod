# Lua/JS: UI Accessibility Runtime

- **`lua/ge/extensions/bnvdaAutoSpawner.lua`** — Deferred UI app spawning (currently commented out).
- **`ui/ui-vue/mods/bnvda/bnvdaRuntime.js`** — The whole UI accessibility layer, bridging BeamNG UI events to Python. (The old AngularJS `ui/modules/apps/bnvda_hook/app.js` was folded into this file and deleted.) Transport is `lua-tcp`: CEF → `bnvdaBridge.lua` → Python's TCP relay on 8766. Per-screen text extractors, a MutationObserver, a `focusin` listener and a 120 ms Vue focus poll all funnel into one `scheduleSpeak()` gate, which layers controller dominance, a same-text dedup, a 50 ms debounce, and held-navigation coalescing.
  - **Translation** — `findTranslateFunc()` must resolve `window.vueI18n.global.t` (petite-vue-i18n, published by the game's `ui-vue/src/services/translation.js`) on Vue screens, falling back to `window.angular$translate.instant` (published by `entrypoints/main/main.js`) on the remaining AngularJS ones. `bngApi.engine.translate` does **not** exist in 0.39; probing it first meant every lookup fell through to the last-resort key-humanizer, which spoke raw key fragments — `ui.common.vehicleAccessoryOn` as "vehicleAccessoryOn", and state keys like `vehicle.engine.oilLevelCritical.true` as a bare "true". The humanizer is deliberately never cached, because the real translator only appears once the UI finishes booting.
  - **`cleanText` is falsy-guarded**, so it maps `false` to `""` but stringifies `true` to the literal word `"true"`. Never hand it a raw DOM `value` property — Vue components expose booleans and objects there. Use `scalarValue()` first; that asymmetry is why the artifact only ever showed up as "true".
  - **Held-navigation coalescing** — holding a direction to sweep a list, slider or dropdown otherwise speaks every item flown past. `scheduleSpeak` instead announces the first item, stays silent through the run, and speaks the landing once motion stops. The settle delay is derived from the observed repeat cadence (clamped `NAV_SETTLE_MIN_MS`–`NAV_SETTLE_MAX_MS`, i.e. 90 ms–`NAV_BURST_GAP_MS`) rather than a fixed idle debounce, because a ~500 ms wait makes the UI feel sluggish. **`NAV_SETTLE_MAX_MS` must stay >= the engine's controller repeat interval** (~240 ms on the part selector): a lower ceiling makes the settle timer fire in the gap between two repeats, which flushes on every item — defeating the coalescing entirely while still charging its full delay to every announcement. It is tied to `NAV_BURST_GAP_MS` because a gap that large already starts a new burst by definition. Only `P.KEYBOARD`/`P.CONTROLLER` are captured; `P.SYSTEM` (toasts, damage, camera, cruise control) must never be, or a sweep will delay or drop it. `UINavigation` press/release tracking both prevents an uneven repeat from flushing mid-run and shortens the wait on release, but the part selector reports no key state, so there the settle timer is the only mechanism. Gated by `ui_nav_hold_suppression`. `diagnostic/navburst_sim.js` (`node diagnostic/navburst_sim.js`) replays the state machine against a fake clock, including a scenario at the real 240 ms repeat rate — run it after touching that logic.
  - **Tuning slider commit debounce** — holding a direction to sweep a value on the vehicle tuning page makes the game reload the vehicle *mid-sweep*, and the value then bounces as the rebuilt list re-reads it. That is **stock behaviour, not ours** — proven by hooking `core_vehicle_partmgmt.setConfigVars` GE-side and `bngApi.engineLua` in the UI, which put the whole chain in the game's own code (`Object.setConfigVars` ← `api.apply (tuningStore.js:119)` ← `Proxy.apply`, on a timer). It is a race between three stock numbers: `bngSlider.vue` debounces its `valueChanged` emit by **500 ms** (`debounce` prop default, which `Tuning.vue` never overrides), `Tuning.vue` then debounces the apply — a full vehicle reload — by **1000 ms**, and `BngOnUiNavFocus.js` delivers the second step of a held direction at `HOLD_DELAY(400) + REPEAT_INTERVAL(100)` = **500 ms**. The slider's timer and the second step are therefore scheduled for the same millisecond, and **the nav path loses consistently** because it is two chained timers each paying its own dispatch latency while the debounce is a single one — measured first-gaps of 511, 524, 510 and 525 ms across four runs, never below 500. So the slider commits during the hold, which starts the 1000 ms apply, which reloads the car a second later while the value is still racing. Once the fast repeats begin they are ~100 ms apart and clear the timer every time, which is why it fires once near the start and not repeatedly. Raising the emit debounce past the repeat gap (`TUNING_SLIDER_DEBOUNCE_MS`, 800) is the whole fix; the only behaviour that changes is that the commit lands 800 ms after release instead of 500 ms.
    - **The patch goes on the NORMALIZED props, not on `comp.props`.** Vue normalizes a component's props declaration once and caches the result in `appContext.propsCache` (a `WeakMap`); `comp.props` is never read again, and that cached copy is what `resolvePropValue` reads for every future instance. Writing only `comp.props.debounce.default` reads back as 800 and changes nothing — every new slider still debounces at 500. Both are written. Note the app does **not** mount on `#app` in 0.39, so the app context is taken from the Vue screen root the focus watcher already resolves.
    - **The value is captured at setup into each slider's own debounce closure**, so this only reaches sliders built *after* it is applied and never ones already on screen. Moving focus between rows does not rebuild them, and neither does the post-reload data refresh (the `v-for` key is `category.name + subCategory.name + varData.name`, so Vue reuses the instances); only leaving and re-entering the **Tuning tab** does, because the panel is `v-if`-ed on the active tab.
    - **Hence the cache's own `set()` is hooked, and armed on ANY Vue screen rather than at config-screen entry.** `bngSlider` is normalized the first time one renders anywhere in the UI, and once that has happened `set()` never fires for it again — so arming late means the first visit of a session silently keeps 500. The DOM walk is only a fallback, and it must keep retrying while the screen is open: at config-screen entry the **Parts** tab is showing, so there is no tuning slider to walk up from and a single attempt at the transition finds nothing. Both of those were real bugs in the first version, along with testing only `comp.__name` — `<script setup>` components expose `__name` and others expose `name`, and checking one matched nothing at all.
    - Keyed on the presence of a `debounce` prop rather than on the component name, so an upstream rename disables the fix instead of silently patching some other component, and restored to the stock value on leaving the config screen so sliders elsewhere in the UI keep stock timing. `_sliderPatched` (screen is open) is deliberately separate from `_sliderDebounceWritten` (our value is installed), or the restore path writes back a baseline it never captured.
    - Worth reporting upstream rather than carrying forever: the honest fix is BeamNG's. 800 ms is empirical — it clears the measured 511–525 ms gaps with ~275 ms of margin, but it is still a race, so a badly stalled frame could in principle lose.
