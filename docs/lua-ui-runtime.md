# Lua/JS: UI Accessibility Runtime

- **`lua/ge/extensions/bnvdaAutoSpawner.lua`** — Deferred UI app spawning (currently commented out).
- **`ui/ui-vue/mods/bnvda/bnvdaRuntime.js`** — The whole UI accessibility layer, bridging BeamNG UI events to Python. (The old AngularJS `ui/modules/apps/bnvda_hook/app.js` was folded into this file and deleted.) Transport is `lua-tcp`: CEF → `bnvdaBridge.lua` → Python's TCP relay on 8766. Per-screen text extractors, a MutationObserver, a `focusin` listener and a 120 ms Vue focus poll all funnel into one `scheduleSpeak()` gate, which layers controller dominance, a same-text dedup, a 50 ms debounce, and held-navigation coalescing.
  - **Translation** — `findTranslateFunc()` must resolve `window.vueI18n.global.t` (petite-vue-i18n, published by the game's `ui-vue/src/services/translation.js`) on Vue screens, falling back to `window.angular$translate.instant` (published by `entrypoints/main/main.js`) on the remaining AngularJS ones. `bngApi.engine.translate` does **not** exist in 0.39; probing it first meant every lookup fell through to the last-resort key-humanizer, which spoke raw key fragments — `ui.common.vehicleAccessoryOn` as "vehicleAccessoryOn", and state keys like `vehicle.engine.oilLevelCritical.true` as a bare "true". The humanizer is deliberately never cached, because the real translator only appears once the UI finishes booting.
  - **`cleanText` is falsy-guarded**, so it maps `false` to `""` but stringifies `true` to the literal word `"true"`. Never hand it a raw DOM `value` property — Vue components expose booleans and objects there. Use `scalarValue()` first; that asymmetry is why the artifact only ever showed up as "true".
  - **Held-navigation coalescing** — holding a direction to sweep a list, slider or dropdown otherwise speaks every item flown past. `scheduleSpeak` instead announces the first item, stays silent through the run, and speaks the landing once motion stops. The settle delay is derived from the observed repeat cadence (clamped `NAV_SETTLE_MIN_MS`–`NAV_SETTLE_MAX_MS`, i.e. 90 ms–`NAV_BURST_GAP_MS`) rather than a fixed idle debounce, because a ~500 ms wait makes the UI feel sluggish. **`NAV_SETTLE_MAX_MS` must stay >= the engine's controller repeat interval** (~240 ms on the part selector): a lower ceiling makes the settle timer fire in the gap between two repeats, which flushes on every item — defeating the coalescing entirely while still charging its full delay to every announcement. It is tied to `NAV_BURST_GAP_MS` because a gap that large already starts a new burst by definition. Only `P.KEYBOARD`/`P.CONTROLLER` are captured; `P.SYSTEM` (toasts, damage, camera, cruise control) must never be, or a sweep will delay or drop it. `UINavigation` press/release tracking both prevents an uneven repeat from flushing mid-run and shortens the wait on release, but the part selector reports no key state, so there the settle timer is the only mechanism. Gated by `ui_nav_hold_suppression`. `diagnostic/navburst_sim.js` (`node diagnostic/navburst_sim.js`) replays the state machine against a fake clock, including a scenario at the real 240 ms repeat rate — run it after touching that logic.
  - **Binding readouts name ONE device — the one in the player's hands.** `bngBinding.vue` renders one `.binding-container` per variant, and with an Xbox pad and a DualSense both plugged in that is the same action twice, once per glyph set. A sighted player skims the pair; a listener hears every hint and every prompt twice, and half of each pair names buttons that are not on the pad they are holding. `pickBindingVariants` keeps only the containers whose glyphs belong to the active device family, taken from `Controls.lastDevices` — the game's own most-recently-used ordering (`core_input_bindings.getRecentDevices`), i.e. the very rule `bngBinding` follows for its own `useLastDevice` lookups, so the speech and the screen cannot end up talking about different pads.
    - **The icon NAME is the only thing that carries the family.** `BngIcon` renders a bare glyph character with no class, attribute or data hook naming the icon, so once it is in the DOM the reverse map built in `buildGlyphMap` is the sole route back — and `controls.js` names every control icon by family prefix (`xboxA`, `psCross`, `mouseLMB`), which is what makes the map possible at all.
    - **Keyboards, wheels and generic joysticks are the EMPTY family, not an unknown one.** `CONTROL_ICONS` has no family for them, so `bngBinding` falls back to a `<kbd>` carrying the control name and their containers hold no glyph whatsoever. Treating "no glyph" as unclassified would drop every keyboard binding; it is a first-class family, and it is appended to the preference order when it is not already there so a keyboard-only binding is still announced while a pad is active — the alternative is silence about a control that is on screen. Where no family matches, the fallback is the **first** container and never the whole set, because an unnameable family is still one device's worth of binding and reading the set is the same double announcement arriving in the one case nobody would think to look at.
    - **`Controls` must be bound to `window.bngVue.controlsStore`, not `window.bngVue.controls`.** The latter is a hand-written facade (`main.js`'s `exposeControlsStore`) that forwards a chosen subset of *methods* and carries none of the store's reactive properties — `lastDevices` among them. Binding to it left `makeViewerObj` working, so nothing looked wrong, while every device query silently answered `undefined`.
  - **Hints are read per `.binding-wrapper`, NEVER per `.binding-container`.** `Hint.vue` wraps its whole row of bindings in a `<div>` that carries that same `binding-container` class, so a container scan matches the outer div **and** each `BngBinding`'s own container inside it — and `getBindingFriendlyName` reads the outer one whole. A hint with a single button therefore came out as "A button or A button", which is most of what "everything reads twice" turned out to be; the two-pad duplication above is the other half and they are independent. `binding-wrapper` is `BngBinding`'s own root and nothing else uses it, so it cannot nest. Legacy Angular hints have no wrapper, hence the container fallback.
  - **The radial menu's centre readout does not speak the item's hotkey.** `Radial.vue`'s `getHotkey()` builds it as an icon glyph plus the **raw** control name, so `cleanText` strips the glyph and leaves things like `Btn_a` — and the centre state carries it for *every* wedge, so sweeping the menu reads a button name after every single item. Worse, `getHotkey` calls `makeViewerObj` with neither `device` nor `useLastDevice`, so with two pads connected the button it names is whichever device happens to come first in the bindings list rather than the one being held. The item name is what the menu is navigated by; the shortcut is not worth the interruption, still less a wrong one.
  - `diagnostic/binding_readout_sim.js` (`node diagnostic/binding_readout_sim.js`) replays all of the above against a fake DOM built to the shape `bngBinding.vue` and `Hint.vue` actually emit. It **lifts the functions out of the source by name** rather than copying them — this area's failure mode is a readout that is merely wrong rather than broken, so a sim carrying its own copy would keep passing across exactly the edit that breaks the mod — and every scenario also asserts what the previous form answered, so no check can pass for free.
  - **A tab change is a context move, and it was silent.** Changing a pause tab or sub-tab with the bumpers announced nothing at all, in either of two ways. The poll's `screenKey` looked for `[role="tab"][aria-selected="true"]`, `.bng-tab.active` and `.bng-tab.selected`; `tabList.vue` emits a plain `<Button class="tab-item tab-active-tab">` with **no ARIA whatsoever**, so that whole term was dead and evaluated to the empty string on every screen the mod has ever run on. A tab was therefore noticed only when it happened to move the route or swap the sub-screen class — and that branch *resets* the watcher (`_vueWatchSignature = ''`, `_vueWatchElement = null`) and speaks nothing, on the assumption that the landing focus move will do the talking. It frequently does not: the engine leaves focus where it was until the first D-pad tap, so the driver lands on a screen with no idea which one it is. The resolved tab path now *is* the `screenKey` term, which also fixes the tabs that never moved the route at all — a mod-contributed pause tab only flips `activeModTabId`, so the watcher previously did not notice the screen had changed either.
    - **Polled from the DOM, never hooked to the bumpers.** `tab_l`/`tab_r` are only two of the ways a tab changes — a click, a route push and `PauseShell`'s own `selectedTab` sync are the others — and the DOM is the one place all of them agree. Same argument the options category already rests on.
    - **The name comes from the Vue `tabs` provide, because an icon-only strip has no name in the DOM at all.** `bngTabs` passes `icon-only` for the pause vehicle sub-tabs (Parts, Tuning, Paint, Other, Vehicle debug), so `tabList.vue` renders the `BngIcon` and **skips the heading `<span>`**; the label survives only in a `v-bng-tooltip` that does not exist in the DOM until the mouse hovers it, which a controller never does. `tabs.vue` does hold the authoritative list — `{index, heading, icon, tooltip, active}` — and hands it down with `provide("tabs", …)`, so `vueProvided` walks `__vueParentComponent` and reads it. `instance.provides` is a plain runtime property that survives minification (Vue's own `inject()` walks it) and the game ships a build that defines `__vueParentComponent` unconditionally — the same class of internal the tuning-slider fix already rests on (`appContext.propsCache`). The DOM tier under it still answers for every strip that renders text, and where neither can name a tab the path contributes **nothing rather than a guess**.
    - **Breadcrumbs are part of the same path, because `layoutMenu` shows them INSTEAD of tabs.** `display.tabs` is gated on `breadcrumbItems.length === 0`, so drilling one level into a tab replaces the strip with a trail; without reading `.bng-path-last` as well, going deeper would read as leaving the tabs behind entirely.
    - **The tab name is spoken ALONE, and the landing item QUEUES behind it** (`_vueTabQueueText`/`_vueTabQueueUntil`, `VUE_TAB_QUEUE_MS`). The first version appended the item to the tab name instead, to make one utterance of it, and that was wrong twice over. It read focus a fixed delay after the tab flipped, and **focus usually has not moved yet at that point** — on a sub-tab change, where the old panel's element survives the switch, what it appended was the item from the tab the driver had just *left*, announced with full confidence. And where it appended nothing, the focus move arriving a moment later cut the tab name off anyway, which is the whole complaint. Waiting long enough to be sure is not on offer either: focus often never lands at all until the first D-pad tap, so the wait would be charged to every tab change in order to fix some of them. Queuing settles all of it without predicting anything — the tab name goes out as soon as it is known, the focus watcher announces whatever is *genuinely* focused whenever that happens, and the window stops the second cutting the first. Two utterances back to back take about as long as the combined one did, and neither can be stale.
      - **The window is armed inside `emitSpeak`, not at the call site**, because the tab name goes out through the same `DEBOUNCE_MS` timer as everything else — arming it any earlier and the tab name queues behind itself. Exactly **one** utterance queues, and only a `P.KEYBOARD`/`P.CONTROLLER` one: a second nav announcement is a fresh movement and must interrupt, or a held sweep stacks up behind a tab name nobody is waiting on any more, and a `P.SYSTEM` damage or toast callout is not what the window exists to protect. `nvda_ws_speaker.py` already honours `interrupt:false` on both transports and deliberately skips its repeat-dedup for queued follow-ups, so no plumbing was needed for this.
    - **A tab change must NOT reset the nav burst.** Holding a bumper sweeps tabs exactly the way holding a direction sweeps a list, and most pause tabs push a route — so the `screenKey` branch's unconditional `navBurstReset()` cleared `active` and `ema` on every step, which would have made each tab in the sweep take the leading-edge path and speak. That is precisely the chatter the coalescing exists to prevent, arriving through the one door it does not watch.
    - **Entry is not a tab change** (`_vueTabSeen`). The focus watcher already announces the landing item on arrival, and on the options screen the category announcement has just spoken — treating first sight as a change would speak over it a tick later. Tracking is *frozen*, not blanked, while the binding editor popup is up, because that popup carries a tab strip of its own and blanking would make dismissing it read as a move back onto the pause tab.
    - `diagnostic/tab_readout_sim.js` (`node diagnostic/tab_readout_sim.js`) replays all of it against a fake DOM built to the shape `tabList.vue`, `tabs.vue` and `bngBreadcrumbs.vue` actually emit, lifting the functions out of the source by name for the reason `binding_readout_sim.js` gives. It asserts the icon-only strip is named, that DOM text alone yields nothing there, and that **the old ARIA selector matched nothing at all**; scenario 10 drives the real `emitSpeak` against a fake clock and asserts the landing item queues, that only one does, that the window expires, and that a system message still interrupts. The poll wiring, which no fake DOM can reach, is grepped.
  - **Tuning slider commit debounce** — holding a direction to sweep a value on the vehicle tuning page makes the game reload the vehicle *mid-sweep*, and the value then bounces as the rebuilt list re-reads it. That is **stock behaviour, not ours** — proven by hooking `core_vehicle_partmgmt.setConfigVars` GE-side and `bngApi.engineLua` in the UI, which put the whole chain in the game's own code (`Object.setConfigVars` ← `api.apply (tuningStore.js:119)` ← `Proxy.apply`, on a timer). It is a race between three stock numbers: `bngSlider.vue` debounces its `valueChanged` emit by **500 ms** (`debounce` prop default, which `Tuning.vue` never overrides), `Tuning.vue` then debounces the apply — a full vehicle reload — by **1000 ms**, and `BngOnUiNavFocus.js` delivers the second step of a held direction at `HOLD_DELAY(400) + REPEAT_INTERVAL(100)` = **500 ms**. The slider's timer and the second step are therefore scheduled for the same millisecond, and **the nav path loses consistently** because it is two chained timers each paying its own dispatch latency while the debounce is a single one — measured first-gaps of 511, 524, 510 and 525 ms across four runs, never below 500. So the slider commits during the hold, which starts the 1000 ms apply, which reloads the car a second later while the value is still racing. Once the fast repeats begin they are ~100 ms apart and clear the timer every time, which is why it fires once near the start and not repeatedly. Raising the emit debounce past the repeat gap (`TUNING_SLIDER_DEBOUNCE_MS`, 800) is the whole fix; the only behaviour that changes is that the commit lands 800 ms after release instead of 500 ms.
    - **The patch goes on the NORMALIZED props, not on `comp.props`.** Vue normalizes a component's props declaration once and caches the result in `appContext.propsCache` (a `WeakMap`); `comp.props` is never read again, and that cached copy is what `resolvePropValue` reads for every future instance. Writing only `comp.props.debounce.default` reads back as 800 and changes nothing — every new slider still debounces at 500. Both are written. Note the app does **not** mount on `#app` in 0.39, so the app context is taken from the Vue screen root the focus watcher already resolves.
    - **The value is captured at setup into each slider's own debounce closure**, so this only reaches sliders built *after* it is applied and never ones already on screen. Moving focus between rows does not rebuild them, and neither does the post-reload data refresh (the `v-for` key is `category.name + subCategory.name + varData.name`, so Vue reuses the instances); only leaving and re-entering the **Tuning tab** does, because the panel is `v-if`-ed on the active tab.
    - **Hence the cache's own `set()` is hooked, and armed on ANY Vue screen rather than at config-screen entry.** `bngSlider` is normalized the first time one renders anywhere in the UI, and once that has happened `set()` never fires for it again — so arming late means the first visit of a session silently keeps 500. The DOM walk is only a fallback, and it must keep retrying while the screen is open: at config-screen entry the **Parts** tab is showing, so there is no tuning slider to walk up from and a single attempt at the transition finds nothing. Both of those were real bugs in the first version, along with testing only `comp.__name` — `<script setup>` components expose `__name` and others expose `name`, and checking one matched nothing at all.
    - Keyed on the presence of a `debounce` prop rather than on the component name, so an upstream rename disables the fix instead of silently patching some other component, and restored to the stock value on leaving the config screen so sliders elsewhere in the UI keep stock timing. `_sliderPatched` (screen is open) is deliberately separate from `_sliderDebounceWritten` (our value is installed), or the restore path writes back a baseline it never captured.
    - Worth reporting upstream rather than carrying forever: the honest fix is BeamNG's. 800 ms is empirical — it clears the measured 511–525 ms gaps with ~275 ms of margin, but it is still a race, so a badly stalled frame could in principle lose.
