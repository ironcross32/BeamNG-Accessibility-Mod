# Lua: `bindingLearn.lua`

- **`lua/ge/extensions/bindingLearn.lua`** — Learn Bindings Mode: a mode you switch on, press buttons in, and hear what each one *does* — while the binding does not fire. Ports 4479→4480, `F9` `Shift+B`, and a **Learn bindings mode** entry in the controller Functions menu. It is the other half of `vehicleBindings.lua`: that one **lists** the current vehicle's special controls to arrow through, this one **names whatever control you press**, on any device, for the whole of the game's binding set — the profiles BeamNG ships for common pads and wheels included. `diagnostic/binding_learn_sim.lua` (`lua diagnostic/binding_learn_sim.lua`) drives the real module against a stubbed input system — run it after touching any of it.
  - **The obvious route is a dead end, and it is worth recording why so nobody re-derives it.** `core_input_actionFilter` → `ActionMap.addToFilter(filter, action, true)` blocks an action engine-side, which is exactly the suppression half of this feature. But it blocks *silently*: there is no `onActionBlocked`, no callback, nothing. It can stop a binding and can never say what was pressed, so a mode built on it would suppress everything and teach nothing. Same for pushing a `MenuActionMap` on top.
  - **Suppression is not a mechanism — it is the ABSENCE of the original command.** Every binding reaches the engine as a command *string* plus a context enum, assembled in exactly one place: `sendBindingsToGE` (`core/input/bindings.lua:171`) calls `core_input_actions.actionToCommands(b.action)` and hands the result straight to `am:bind`. A grep of the whole game finds **only two callers of that function and both go through the module table**, so wrapping it reaches every binding there is. While the mode is on the wrapper calls through to the original and replaces the command fields with `extensions.bindingLearn.hit('<action>',VALUE,'d')`, `ctx.type = COMMAND_CONTEXT_TLUA`. `VALUE` is substituted engine-side — stock `camera.json` is full of `tlua` actions using it. The original command is simply never queued. Nothing is filtered, no action map is pushed, no global state is disturbed, and restoring is unwrapping plus a re-push.
    - **`onUp` is dropped on the suppressed path.** A release is not a discovery, and announcing both ends of every press doubles the speech for nothing. An action declared with `onUp` only — or with nothing at all — still gets a *down* command, so no binding can become unlearnable through an odd declaration.
  - **`notifyGE` is local; `getUsedBindingsFiles` is the exported handle that reaches it.** `notifyGE` (`bindings.lua:708`) is what clears every `*ActionMap` and re-pushes all bindings through `actionToCommands`, and it is a file-local. `core_input_bindings.getUsedBindingsFiles()` reaches it (`reloadBindings` → `notifyAll` → `notifyGE`) and is the cheapest exported path — its own return value is a debug file list nobody here wants. `onDeviceChanged()` reaches it too and is the fallback, but it re-enumerates the hardware.
  - **`actionMap`, `isCentered` and `isRelative` are structurally untouchable, not merely untouched.** They are returned straight out of the original call and are **never passed to the handler**, so no future edit inside the rewrite can reach them. `actionMap` decides which ActionMap a binding lands on *and* feeds the `MenuIndependent` catalogue `readActionsFromDisk` builds, so rewriting it would break menu gating game-wide from a feature that has nothing to do with menus. Making that impossible beats commenting on it; `binding_learn_sim.lua` scenario 3 asserts the handler's signature does not mention them.
  - **`modifier` is exempt for a reason that has nothing to do with menus: suppressing it BREAKS EVERY MODIFIED BINDING IN THE GAME.** On a pad, `modifier1`/`modifier2` are not device state the way a keyboard's ctrl/shift/alt are — they are ordinary *actions* (`customModifier1..6` in `actions/general.json`, `cat: "modifier"`, `ctx: tlua`) whose `onChange` is the single call that enables the modifier engine-side: `core_input_bindings.enableCustomModifier(PLAYER, VALUE ~= 0, N)`. Replace that command and holding the shoulder button sets nothing, so `modifier2 btn_a` can never match and the engine fires the **plain** `btn_a` bindings instead. Two of the three symptoms in the original report are this one bug: a modifier that is *sometimes* captured (the keyboard's native modifiers keep working, the pad's do not), and this mod's own accessibility bindings — all five of which are `modifier2 <button>` — appearing to be ignored outright. They are not ignored; they are unreachable, and what is announced is whatever the unmodified control does. Verified in a running game: with the mode on, `modifier2 lpov` announced `d-pad left. Left Signal`. `binding_learn_sim.lua` scenario 14 asserts the command survives the push.
  - **The held modifiers are therefore KNOWN, and that is what fixes the resolve.** `findControl` took the *first* binding of the action on the recent device, which is arbitrary the moment an action is bound twice on one device with different modifiers — this pad has `activateStarterMotor` on both `dpov` and `modifier1 dpov`, and `toggleCamera` on `modifier1 btn_b` and `modifier2 btn_b`, so `pairs` order decided whether the modifier was spoken. Making `customModifierN` exempt means it reports through `M.hit`, so the held set is observed rather than guessed and a candidate whose modifier set matches it is the binding the engine actually matched. The state is recorded **before** the hysteresis gates, which return early on a release — and a release is exactly the edge that clears a modifier. Where it still leaves several candidates (a keyboard's ctrl/shift/alt have no action behind them and are invisible from here, so `ctrl g` and `shift g` are indistinguishable) **every survivor is named** rather than one being picked: ambiguity that is spoken is recoverable, ambiguity resolved by table order is a confident wrong answer. Scenario 15 asserts both presses answer differently and that the first-binding form drops the modifier.
  - **An axis is named by the CONTROL, never by which command slot the engine used.** `customModifierN` is declared with `onChange` — it is a shoulder button reported through the analogue path — so classifying on the command announced `left bumper, Modifier 2, axis`.
  - **One press is one announcement, however many bindings the button carries.** A stock pad has `btn_a` on `accept`, `menu_item_select`, `shiftUp`, `triggerAction0` and `bigMapControllerSelect`, and this user's `modifier2 btn_a` carries both `beamtel_accessibility_activate` and `toggleTransbrake`. Every one of them arrives at `M.hit` in the same frame or two, and sent as separate packets each `say()` interrupts the last — so only whichever arrived last is ever heard, which reads as the alternates being *ignored* rather than as a mod that only says one thing. Hits are buffered for `HIT_COALESCE_S` and emitted grouped, and the count is spoken (`2 actions`) because "this button does two things" is itself the answer being asked for. Grouped by **control**, not simply by window: a fast two-button press is genuinely two answers, and scenario 16 asserts both halves. `suppressed` moves onto each item, since one control can fire an exempt action and a suppressed one at the same time.
  - **A modifier held over a control that carries no binding for it is UNBOUND, not the bare binding.** The engine does not refuse such a press — it falls **through** and fires the bare one, so `modifier1 rpov` with nothing bound to it announced `d-pad right. Right Signal`. That is a confident wrong answer about a different button: `modifier 1 plus d-pad right` is not `d-pad right` as far as the person mapping a pad is concerned. A hit that matched no candidate while a modifier is held is therefore *dropped*, and a group left with nothing is reported as unbound — reported rather than silently discarded, because silence is indistinguishable from the mode being broken, which is the whole failure this feature exists to avoid. The control named is the combination that was **physically pressed**, synthesised as a control string (`modifier1 ` prefix) and run through the same formatter, so it reads like any other combination.
    - **An EXEMPT fall-through is dropped too, and that is the one place the "still active" contract is deliberately not applied.** It genuinely fires — suppression is what makes the others a non-event — so keeping it is the defensible reading, and it was the first implementation. But bare `rpov` alone carries `menu_item_right`, and the same is true of every direction and face button, so almost every combination under a modifier would name a menu action instead of saying nothing is bound: the exact wrong answer the drop exists to prevent, arriving through the exemption. The trade is stated plainly rather than hidden: holding a modifier over the pause button says `nothing bound` while the pause menu opens.
    - **The modifier's OWN press must not be prefixed with itself.** The held set is recorded *before* the resolve — it has to be, because a release is the edge that clears it — so `customModifier1`'s own binding, which naturally carries no modifier token, reads as a fall-through and announced `modifier 1 plus right bumper`: the button prefixed with itself. `findControl` takes an `ignoreHeld` flag for exactly that one case. Found in a live game rather than by reasoning, which is why the sim asserts it.
  - **`items` is an optional tail and a packet without it renders as a single action** — `bng_mod/` is a live junction and the two halves genuinely go out of step, the same contract every other tail in this project carries.
  - **`cat` is both the exemption rule and the trap door — one rule, two jobs.** Exempt categories are `menu`, `menuExtra`, `accessibility` and `modifier` (that last one for the separate reason above). Every UI navigation action is `cat: "menu"` — **and so is `toggleMenues`, the button that opens the pause menu** (`actions/menu.json`). So exempting the category guarantees that if a menu does come up it is navigable and escapable, which is the one way this mode could strand somebody; `accessibility` is this mod's own six actions, i.e. the controller's route back out, and is what makes arming the mode *from* the Functions menu safe. A name list would have been the obvious spelling and would silently stop covering a menu action the game adds later.
    - **Exempt actions are still ANNOUNCED — they just also fire**, so the announcement rides *in front of* the original command rather than replacing it. That is only possible where both halves run in the same context, and every menu action and all six of this mod's own are `ctx: tlua`; anything else is left entirely alone rather than risked. The `suppressed` field on the wire carries which happened, and Python says `still active` for the second — without that, "it did something anyway" reads as the mode being broken.
  - **The action name is VETTED, never escaped.** It is about to be concatenated into a string the engine executes, so it must match `^[%w_%-%.]+$` or the binding is left completely unrewritten. Failing that way means it fires normally and is merely not learnable, which is the safe direction; the alternative is a quote breaking out of a command. The sim binds an action literally named ``evil');os.exit(--`` and asserts nothing anywhere carries it.
  - **The watchdog is the whole risk of this feature and is not optional.** With the mode on, every binding in the game points at this extension. If beamtel dies there, the controls stay dead until BeamNG is restarted — so the timeout lives on the **mod** side, where beamtel going away *is* the trigger rather than something beamtel has to notice about itself. Python sends `KEEPALIVE` every second against a `HEARTBEAT_TIMEOUT_S` of 6, comfortably more than one interval (a dropped datagram must not end the mode) and comfortably less than anyone's patience with a game that has stopped responding. Restore also fires on `M.onExtensionUnloaded`, `M.onClientEndMission`, a session cap, and an explicit `LEARN_OFF`.
    - **`learnActive` goes down FIRST in `stopLearn`**, before the unwrap and the re-push, so a rewritten command still in flight does nothing rather than talking about a mode that has ended.
    - **A re-push that fails on the way OUT is the brick case, and it is retried rather than swallowed.** The wrapper is gone but the engine still holds the commands it wrote. It sends `LEARNFAIL:norestore` — never a clean `LEARNMODE:OFF` — and retries every second until it takes. Reporting success there is the one lie in this file that would end with someone restarting the game.
  - **`M.onExtensionUnloaded` RESTORES, inverting `vehicleInfo.lua`'s rule on purpose.** That file deliberately leaves its wrapper installed on unload, because a reload is about to reclaim the slot and restoring would race a newer instance. Correct there — that wrapper is **additive** (record, then call through), so an orphan is merely useless. This one is **substitutive**, and an orphan left with no live instance points every binding in the game at a dead extension. Learn mode does not need to survive a reload; the game being playable does. It restores *before* closing the sockets, so it can still say what it did.
  - **A Ctrl+L reload of `core_input_actions` drops the wrapper silently**, and the mode would then claim to be suppressing while every binding fired normally — a mode lying about the one thing it promises. `wrapperInstalled()` is polled at 2 Hz while active and re-arms, the same re-arm `vehicleInfo.lua:489` already carries.
  - **Everything else about the wrapper is `vehicleInfo.lua`'s shape, and all four of its reasons carry over verbatim**: a mutable dispatch slot on the stock module table (a closure captures upvalues, so a wrapper installed by one instance would write into that instance's locals forever and `extensions.reload` would strand every call in the dead one), a **version integer** rather than a boolean mark (a wrapper left by an older build predates the slot and calls its own captured handler, so a boolean reads "installed" and is ignored), `ORIG_KEY` parking the original so a stale wrapper is **replaced** rather than wrapped again, and a `pcall` around the handler.
  - **A vehicle switch needs no code at all.** The game's own `onVehicleSwitched` already runs `notifyAll` → `notifyGE`, so the mode survives a vehicle change *and* picks up the new vehicle's actions for free.
  - **The physical control is resolved after the fact, because there is no device token to substitute.** The wrapper sees only the action name; the engine substitutes `VALUE`/`FILTERTYPE`/`PLAYER`/`ANGLE`/`LOCKTYPE` and nothing that names a device. So `findControl` walks `core_input_bindings.getRecentDevices()` most-recent-first and takes the first non-`unused` binding of that action — the same rule `bnvdaRuntime.js`'s `pickBindingVariants` follows, and pressing the button is itself what promotes its device. Exact for one device; a stated heuristic only when one action is bound on two pads at once. The alternative — doing our own `am:bind` loop to embed the device in the command — would name it exactly and hard-code a 27-argument engine signature that a game update will move.
  - **The speech formatting is BORROWED from `vehicleBindings.lua`, not copied** (`M.deviceKey`, `M.controlToSpeech`, `M.translate`). The two files must name one binding identically or the browser and this readout disagree about the same control. The mod duplicates a helper only where the two answers genuinely differ (`cannonShot` vs `vehicleSpawnerAccessible`); here they must not, so there is no case for a second copy — and `binding_learn_sim.lua` scenario 14 asserts the exports exist and that this file grew no `KEY_LABELS` of its own.
  - **Axes are edge-triggered with hysteresis, and the re-arm level is DERIVED.** A stick or pedal sends every frame. The report fires crossing `AXIS_MIN_DEFLECTION`, repeats no faster than `AXIS_COOLDOWN_S` while still held (holding it *should* eventually repeat — that is how you check you heard right), and re-arms instantly below `AXIS_REARM`, which is `AXIS_MIN_DEFLECTION * 0.5` rather than its own constant so the two can never be tuned into a window where releasing the stick fails to re-arm it.
  - **Timers accumulate `dtReal`, not `os.clockhp()`.** Everything here — the keepalive, the axis cooldown, the session cap — is a fact about the person and their pad rather than about the physics, so real time is right; and an accumulator makes the sim's fake clock the `dt` it hands in rather than a stubbed engine global. (This is the opposite call from `cannonShot.lua`, whose flight is aged on `dtSim` because a flight's duration is a fact about the *car*.)
  - **Rows are JSON (`LEARN:<json>`)**, the shape `vehicleInfo.lua`'s `INFO_ROW` already uses and for the same reason: the action description is free text with commas and quotes in it, and `bng_mod/` is a live junction so the two halves genuinely go out of step. `LEARNMODE:ON|OFF;<reason>` and `LEARNFAIL:<code>;<sentence>` carry the rest.
  - **Python announces from the mod's reply, never from its own request.** Entering the mode can fail on the Lua side (the wrapper, or the binding re-push), and saying "learn bindings on" locally would claim a mode that is not running — in a feature whose entire promise is that your buttons have stopped doing things. `_binding_learn_active` on the Python side drives the keepalive and nothing else.
  - **`F9` `Shift+B`, next to plain `B`.** Same subject, two directions: `B` lists this vehicle's special controls, `Shift+B` names whatever control you press on any device.
