# Lua/JS: UI Runtime: Tab and breadcrumb changes

Part of `ui/ui-vue/mods/bnvda/bnvdaRuntime.js`. The overview, the poll/event model and the shared text helpers are in `lua-ui-runtime.md`.

How pause tabs, sub-tabs and breadcrumbs are announced when they change.

- **A tab change is a context move, and it was silent.** Changing a pause tab or sub-tab with the bumpers announced nothing at all, in either of two ways. The poll's `screenKey` looked for `[role="tab"][aria-selected="true"]`, `.bng-tab.active` and `.bng-tab.selected`; `tabList.vue` emits a plain `<Button class="tab-item tab-active-tab">` with **no ARIA whatsoever**, so that whole term was dead and evaluated to the empty string on every screen the mod has ever run on. A tab was therefore noticed only when it happened to move the route or swap the sub-screen class — and that branch *resets* the watcher (`_vueWatchSignature = ''`, `_vueWatchElement = null`) and speaks nothing, on the assumption that the landing focus move will do the talking. It frequently does not: the engine leaves focus where it was until the first D-pad tap, so the driver lands on a screen with no idea which one it is. The resolved tab path now *is* the `screenKey` term, which also fixes the tabs that never moved the route at all — a mod-contributed pause tab only flips `activeModTabId`, so the watcher previously did not notice the screen had changed either.
  - **Polled from the DOM, never hooked to the bumpers.** `tab_l`/`tab_r` are only two of the ways a tab changes — a click, a route push and `PauseShell`'s own `selectedTab` sync are the others — and the DOM is the one place all of them agree. Same argument the options category already rests on.
  - **The name comes from the Vue `tabs` provide, because an icon-only strip has no name in the DOM at all.** `bngTabs` passes `icon-only` for the pause vehicle sub-tabs (Parts, Tuning, Paint, Other, Vehicle debug), so `tabList.vue` renders the `BngIcon` and **skips the heading `<span>`**; the label survives only in a `v-bng-tooltip` that does not exist in the DOM until the mouse hovers it, which a controller never does. `tabs.vue` does hold the authoritative list — `{index, heading, icon, tooltip, active}` — and hands it down with `provide("tabs", …)`, so `vueProvided` walks `__vueParentComponent` and reads it. `instance.provides` is a plain runtime property that survives minification (Vue's own `inject()` walks it) and the game ships a build that defines `__vueParentComponent` unconditionally — the same class of internal the tuning-slider fix already rests on (`appContext.propsCache`). The DOM tier under it still answers for every strip that renders text, and where neither can name a tab the path contributes **nothing rather than a guess**.
  - **Breadcrumbs are part of the same path, because `layoutMenu` shows them INSTEAD of tabs.** `display.tabs` is gated on `breadcrumbItems.length === 0`, so drilling one level into a tab replaces the strip with a trail; without reading `.bng-path-last` as well, going deeper would read as leaving the tabs behind entirely.
  - **The tab name is spoken ALONE, and the landing item QUEUES behind it** (`_vueTabQueueText`/`_vueTabQueueUntil`, `VUE_TAB_QUEUE_MS`). The first version appended the item to the tab name instead, to make one utterance of it, and that was wrong twice over. It read focus a fixed delay after the tab flipped, and **focus usually has not moved yet at that point** — on a sub-tab change, where the old panel's element survives the switch, what it appended was the item from the tab the driver had just *left*, announced with full confidence. And where it appended nothing, the focus move arriving a moment later cut the tab name off anyway, which is the whole complaint. Waiting long enough to be sure is not on offer either: focus often never lands at all until the first D-pad tap, so the wait would be charged to every tab change in order to fix some of them. Queuing settles all of it without predicting anything — the tab name goes out as soon as it is known, the focus watcher announces whatever is *genuinely* focused whenever that happens, and the window stops the second cutting the first. Two utterances back to back take about as long as the combined one did, and neither can be stale.
    - **The window is armed inside `emitSpeak`, not at the call site**, because the tab name goes out through the same `DEBOUNCE_MS` timer as everything else — arming it any earlier and the tab name queues behind itself. Keying the arm on the exact **text** is what makes that safe: an utterance that never reaches `emitSpeak` — deduped, replaced inside the debounce, or suppressed by a loading screen — simply never opens a window, instead of opening one around whatever unrelated utterance came next. Exactly **one** utterance queues, and only a `P.KEYBOARD`/`P.CONTROLLER` one: a second nav announcement is a fresh movement and must interrupt, or a held sweep stacks up behind a tab name nobody is waiting on any more, and a `P.SYSTEM` damage or toast callout is not what the window exists to protect. `nvda_ws_speaker.py` already honours `interrupt:false` on both transports and deliberately skips its repeat-dedup for queued follow-ups, so no plumbing was needed for this.
  - **A tab change must NOT reset the nav burst.** Holding a bumper sweeps tabs exactly the way holding a direction sweeps a list, and most pause tabs push a route — so the `screenKey` branch's unconditional `navBurstReset()` cleared `active` and `ema` on every step, which would have made each tab in the sweep take the leading-edge path and speak. That is precisely the chatter the coalescing exists to prevent, arriving through the one door it does not watch.
  - **Entry is not a tab change** (`_vueTabSeen`). The focus watcher already announces the landing item on arrival, and on the options screen the category announcement has just spoken — treating first sight as a change would speak over it a tick later. Tracking is *frozen*, not blanked, while the binding editor popup is up, because that popup carries a tab strip of its own and blanking would make dismissing it read as a move back onto the pause tab.
  - `diagnostic/tab_readout_sim.js` (`node diagnostic/tab_readout_sim.js`) replays all of it against a fake DOM built to the shape `tabList.vue`, `tabs.vue` and `bngBreadcrumbs.vue` actually emit, lifting the functions out of the source by name for the reason `binding_readout_sim.js` gives. It asserts the icon-only strip is named, that DOM text alone yields nothing there, and that **the old ARIA selector matched nothing at all**; scenario 10 drives the real `emitSpeak` against a fake clock and asserts the landing item queues, that only one does, that the window expires, and that a system message still interrupts. The poll wiring, which no fake DOM can reach, is grepped.
