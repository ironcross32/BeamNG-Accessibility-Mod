# Lua: Geometry Libraries (`vehicleGeometry.lua`, `rampGeometry.lua`)

- **`lua/ge/extensions/vehicleGeometry.lua`** — Per-vehicle derived node geometry (extents, hull cids, front/rear contact bands, vertical occupancy histogram) for **any** vehicle, player or target. No ports of its own; it is a library the scanner and `implementProximity` both call. `diagnostic/vehicle_geometry_sim.lua` (`lua diagnostic/vehicle_geometry_sim.lua`) replays the classification and the distance query against synthetic clouds with known ground truth — run it after touching any of it.
  - **The reason it exists**: `vehicleScanner` measured `originPos:distance(targetPos)` and `getPosition()` is the object's reference node, so every distance was centre-to-centre. That carried half a vehicle of phantom range at each end and was **orientation-dependent** — broadside and nose-on to the same car at the same real gap reported the same figure. The sim's scenario 2 is that exact comparison and is the check most worth keeping.
  - **The loader is a cid list, not a branch.** Nothing downstream asks "is this a loader"; it asks for a *contact set* and a *surface set*. A generic car in forward is its own front node band, the same car in reverse is its rear band, a WL-40 is the five implement cids. That is what makes it impossible for loader work to regress the generic case — the loader is a different **answer**, not a different code path.
  - **The fallback chain terminates at today's behaviour** and is the whole safety property: hull cids → nearest hull node; else extents → closest point on the oriented box; else `getPosition()`. A vehicle whose async resolve never lands still answers, just less precisely, so no caller handles a nil. **Giving up has to be recorded, not just stopped**: `M.request` is documented as cheap to call every tick and every query does call it, so clearing `pending` after `MAX_TRIES` with nothing in `cache` merely re-arms the resolve on the next frame — the cross-VM chunk went out every 3 s and the "staying on fallback" warning was logged every 9 s for the whole session. A `failed` set gates `M.request` and is cleared per vehicle in `dropVehicle`/`dropAll`, so a reset or part swap still gets a fresh attempt. A malformed reply (`#ext ~= 6`) is flagged the same way; a VM answering with the wrong shape will keep doing so.
  - **`up:cross(fwd)` is the lateral vector, in both this file and `implementProximity`.** They must match: `implementProximity`'s `boxFrame` projects onto its own vector and clamps the result against `minR`/`maxR` taken straight from this cache, where `VEH_SCRIPT` measured them along its. It built the negation (`fwd:cross(up)`), which mirrored every lateral test against a cached target — the containment call and the slam footprint both answering for the far side of the vehicle. It survived because the strided fallback measures with whatever frame it is handed and so stays self-consistent: the readout was right for the first few ticks after a spawn and flipped when the async resolve landed. Both names (`rgt`, `right`) are misnomers — the vector points to the driver's *left* — and renaming either is exactly how they would stop agreeing. `vehicle_geometry_sim.lua` scenario 11 asserts the agreement, asserts the old form inverts, and greps both sources.
  - **`nearestSurfacePoint` keeps the SMALLER of the box and node answers**, the way the vehicle VM keeps the smaller of its terrain height and its raycast. The two tiers fail in opposite directions: the box encloses the body so it can only under-read, but it is exact at the surface; the node sweep is a sparse sample so it *over*-reads near contact by up to half the node spacing — thinning a car's shell to 48 measured 0.19 m of over-read, i.e. clear air reported while the tines are touching. That measurement is why `HULL_MAX` is 128 and not lower.
  - **`HIST_BINS` sets the finest pocket the mod can see at all**, because band thickness is quantized to the bin height. At 24 bins a 1.63 m target gave 0.068 m per bin, which silently turned `implementProximity`'s `BAND_MIN_HEIGHT_M` of 0.10 into "at least two bins" and discarded every genuine single-bin void — a real thin pocket was unreachable regardless of whether it existed. 48 bins is 0.034 m there, making the same threshold a real ~3-bin test. The wire format is `table.concat(hist, ",")` and both ends ship in the same mod, so no shim is needed — but `M.onVehicleGeometry`'s `#hist == HIST_BINS` guard is what makes a half-updated install fail loudly instead of mis-binning, and must stay.
  - **Extents are a gap-trimmed range, not raw min/max** (`OUTLIER_GAP_M`, `TRIM_MAX_FRAC`). A detached bumper stays in the *same object*, so raw extremes stretch the box across the empty air between car and debris and report solid surface where there is none — and they wreck the normalisation, collapsing every real body node into a slice of the 0–1 range so hull and band classification stop distinguishing anything. A percentile trim is the wrong tool because a detached part is a **dense** cluster; what separates it from the body is empty space, so that is what gets measured. The debris still normalises outside 0–1, trips the face test, and stays visible to the node tier.
  - **`M.debugVehScript()`** exists so the sim can compile the cross-VM chunk. A syntax error inside a `queueLuaCommand` string does not fail where it is written — it fails in another VM, silently, and the only symptom is that geometry never resolves and every caller sits on the `getPosition()` fallback for the whole session.
- **`lua/ge/extensions/rampGeometry.lua`** — The drive-in mouth of a ramp-equipped machine (the stock `large_cannon`, whose `cannon_ramp` slot is a funnel you drive a vehicle into before firing it out of the barrel). No ports of its own; a library `implementProximity` calls. Structurally a sibling of `vehicleGeometry.lua` — same cross-VM resolve, same epoch guard, same `failed` set, same `M.debugVehScript()` — but a different question, and folding it into that file would put a name-matched special case inside the one file whose whole premise is that it has none. `diagnostic/ramp_resolve_sim.lua` (`lua diagnostic/ramp_resolve_sim.lua`) replays the resolve against the real jbeam coordinates — run it after touching any of it.
  - **"Not ready" is not "no ramp".** The chunk returns `no node data` / `no nodes` when `v.data.nodes` does not exist yet, which is a fact about a VM still spawning and not about the vehicle. Treated as terminal (which it was), a cannon is permanently invisible or not depending purely on when the first resolve happened to fire — a bug whose only symptom is "it worked, then I restarted and got nothing". Those two reasons are counted in `notReady` and retried under the same `MAX_TRIES` budget as a silent VM, so a machine that answers that way forever still costs three chunks and no more.
  - **The epoch rejects replies from before the last INVALIDATION, not replies from a superseded chunk.** The original guard was `pending[vehID].epoch ~= epoch`, which threw away the one reply this file most needs: a vehicle VM that takes longer than `RESOLVE_TIMEOUT_S` to run its queued chunk — a cannon spawning with the level — answers the first chunk *after* the retry has issued a second, so every answer was dropped as stale, three times over, and the machine landed in `failed` for the session having in fact resolved correctly every time. Nothing above `D` level said so. A success is now installed whenever it arrives; only a *failure* reply is terminal, and only when it comes from the newest chunk. The guard the epoch actually exists for — never installing cids for a part configuration that has since been reset — is unchanged, because that is what the invalidation mark records.
  - **A pooled-out vehicle is not a vehicle without a ramp.** An inactive VM cannot run a `queueLuaCommand` at all, so asking one spends the retry budget on silence and gives up permanently; the machine most likely to be inactive is a large map prop at the far end of the level, i.e. exactly what this file exists for. `M.request` declines to ask, `onUpdate` holds the entry open instead of counting a try, and `M.onVehicleActiveChanged` clears the give-up state when the VM wakes (a *cached* ramp is left alone, or crossing the pooling boundary would re-issue a chunk every time).
  - **"No ramp near you" has to say which of its half-dozen causes it is.** Out of range, VM not answered yet, answered with no `ramp_` nodes, gave up three chunks ago and resolved-but-far all sound identical from the seat and want different actions. `lastReason` is recorded on every outcome, `M.stateOf(vehID)` renders it in one line, `M.diag()` dumps every vehicle it has an opinion about, and `implementProximity.rampTruth()` falls back to listing every object inside `RAMP_SEARCH_M` with its state. `M.retry(vehID)` (or `retry()` for all) re-arms a stuck resolve without resetting the vehicle or reloading the level. **"It answered and it has no ramp" is rendered differently from "it never answered"** — the first is a settled fact about the vehicle (an ordinary car, or the stock **Old Cannon**, which is a different vehicle from `large_cannon` and has no drive-in ramp at all), the second is a fact about the attempt; both used to read as `GAVE UP`. The spoken reason is a separate, one-clause form (`M.shortStateOf`) and names the machine you are next to — `nearest is Old Cannon, 5 metres, no ramp on it` — because `DOCKFAIL` is read aloud on every `F9` `I` press and the console detail is a paragraph. `ramp_resolve_sim.lua` scenarios 12–13 drive the real module against stubbed engine globals and assert the late reply lands, the pre-invalidation reply does not, and the give-up is both explained and recoverable.
  - **Silent on ordinary vehicles by construction, and terminal on the FIRST round trip.** `vehicleGeometry`'s chunk returns silently when it has nothing, which makes "no answer yet" and "nothing to say" indistinguishable and costs three retries over 9 s to tell apart. This one *always* replies, with an empty cid list when it found no `ramp_` nodes, and that sets `failed` immediately — so a car costs exactly one cross-VM chunk and one reply for the whole session. That is the entire cost model; without it every car in the scene re-issues a chunk every 3 s forever, which is the bug `vehicleGeometry`'s `failed` set already exists to fix.
  - **The along-ramp axis is the ramp centroid's displacement from the MACHINE centroid, never the ramp cloud's longest axis.** The tempting rule is not merely fragile here, it is *wrong today*: large_cannon's ramp is 5.792 m long but its inner row flares out to `ramp_L_6b` at x 3.449, making the cloud **6.898 m wide**. Longest-axis would call the mouth a side wall and report lateral offset as range. The displacement does not depend on the ramp's proportions at all — the ramp hangs off one end of a ~16 m machine — and it derives *which end is the mouth* in the same step, which longest-axis cannot do. Guarded by `AXIS_DOMINANCE`, and the resolve is **rejected and logged** rather than guessed at when unmet. Same centroid trick `796F6C6F313035.lua` uses for the implement's fore/aft sign.
  - **A resolve is a fact about the MACHINE, not about the pose it happened to run in.** large_cannon tilts its whole assembly — ramp included — on its `ramL`/`ramR` cylinders, and two separate rules were reading that pose as though it were geometry. Both produced the same class of failure and both are asserted by `ramp_resolve_sim.lua` scenario 8, which is the file's only scenario that *rotates* node coordinates rather than editing the already-projected `f/r/u` by an axis-aligned scalar.
    - **`AXIS_DOMINANCE` is weighed against the other HORIZONTAL component, never `math.max(lateral, vertical)`.** The axis it protects is horizontal — `mouthFrame` flattens it to `vec3(raw.x, raw.y, 0)` and the vertical survives only as the scalar `pitchDeg` — so weighing it against a vertical quantity tested the answer against something the answer does not contain. Vertical displacement also carries no information about whether the along-axis is well determined: a ramp hangs low and a machine is tall, so *every* ramp on a tall machine has one. Measured in game at full inclination: displacement 8.4615 m against a vertical 2.8525 m, a ratio of 2.966 that missed the 3.0 threshold **by about three centimetres**, so the cannon resolved only while its barrel was near level. True at spawn, which is why nothing ever saw it — but a reset, a part swap, a reload or `M.retry` at elevation killed ramp mode for the session and answered `NO RAMP ON IT`, taking the docking instrument, `RAMPALIGN` and `cannon_active` with it. The **vertical rejection is a separate mechanism and is untouched**: it lives in the branch conditions, where a vertically dominant displacement makes `disp` nil and falls to the deck tier before the ratio is ever computed. Conflating the two in one `math.max` was the whole bug. The failure reason now names all three components, because reading `8.46 vs 2.85` told you the ratio missed without telling you the 2.85 was vertical, which is the entire diagnosis.
    - **A row's floor is a LINE along the ramp, not its lowest z** (`floorFitOf`, `FLOOR_FIT_MIN_SPAN_M`). A row is a *band* — the mouth row spans 1.26 m of a 5.79 m ramp — so tilt turns its along-extent into vertical extent, and "height above the lowest node in the row" starts reporting the ramp's **pitch** as wall height. large_cannon's floor lip sits 1.0 m up-ramp of the toe and 0.1 m above it, so the lip alone clears `WALL_MIN_H` at **2.9°**, and the wall rule — which takes the *smallest* qualifying lateral — then answers 0.546 m where the truth is 2.148 m. A mouth reported at a quarter of its width, with full confidence: exactly what the wall rule exists to prevent, arriving through the back door. This one was reachable in the shipped mod at any tilt over ~3° and stayed hidden only because the cannon spawns level and the chosen cids are cached for the session — so fixing the dominance gate *without* this would have turned an honest "no ramp" into a confident wrong number, which is strictly worse. Fitting a line absorbs the pitch exactly, because a rotation maps a straight row to a straight row; the reference nodes are those within `MIN_WALL_LATERAL_M` of the centreline, since the wall rule already refuses to call those walls, and nodes more than `WALL_MAX_H` above the row's lowest are excluded because `ramp_M_0` sits 2 m up on the centreline and would otherwise drag the fit with it. Too few reference nodes or too little along-spread falls back to the flat plane, i.e. to what every vehicle did before. The sim asserts the fitted form holds the half-width to 0 error from 0° to 30°, that the flat form breaks at 2.9°, and that the two agree exactly at level.
  - **The drivable half-width comes from a WALL rule, not the implement resolver's floor-band rule.** `ramp_L_8a` is the *outer foot of the side wall* and sits at exactly floor height, so "lowest vertical band, then lateral extremes" answers ±2.785 where the truth is ±2.148 — 0.63 m of phantom clearance per side, which on a car is the difference between fitting and tearing the mirrors off. The wall is where something *sticks up*: per side, the smallest |lateral| among mouth-row nodes between `WALL_MIN_H` and `WALL_MAX_H` above the floor plane and outside `MIN_WALL_LATERAL_M`. Both guards are load-bearing and neither is sufficient alone — `MIN_WALL_LATERAL_M` stops a low centre rib being read as the left wall but only excludes an overhead node while it sits near the centreline, and the first offset ramp puts it back in scope; `WALL_MAX_H` is the one that holds, because it is a property of the node rather than of where the ramp happens to be sitting. large_cannon has exactly such a node: `ramp_M_0`, 2.1 m up on the centreline, which without a ceiling on the rule collapses the mouth outright. Scenario 3 asserts 2.148 **and** asserts the naive form answers 2.785 and disagrees about whether a given car fits. It is all name-driven, so the resolve **logs what it landed on** — including the naive figure even when the rule worked, because that is the one line that turns "the clearance feels wrong" into an answer.
  - **Only `large_cannon` names its ramp nodes.** A scan of all 124 stock vehicle zips found `^ramp_` matching exactly one drivable thing (plus `large_spinner`'s *wall*, which is not one). Every real trailer ramp — `tsfb`, `dryvan`, `tiltdeck`, the `us_semi` rollback — names its nodes opaquely (`b0rr`, `cd1rr`, `tf01r`) and carries its identity only in the jbeam **part**. So the node scan has a second tier on `nd.partOrigin` (proven present, a plain string, and already what `796F6C6F313035.lua` rests on) and a third on `nd.group`, which is jbeam data and may be a **string or an array**. The name tier wins outright when populated, so the cannon resolves through the code it always did and the part tiers cannot change an answer that already worked.
    - **An allowlist plus a denylist, never a search for "ramp".** The substring test is wrong in *both* directions on the shipped data: it misses every entry except the cannon's, and it hits `tiltframe_rampiston` / `tiltframe_ramcylinder`, which are the hydraulic ram that *tilts* a rollback deck — structure you must not drive at. Matching is boundary-aware (`tiltdeck_deck` matches `tiltdeck_deck_22ft`, not `tiltdeck_deck22ft`), the same rule the implement resolver applies to its keywords, minus the camelCase-hump clause because every verified part name is snake_case. The denylist entries (`tailgate`, `door`, `dumptruck_deck`, `tiltframe_ram`, `spinner_wall`) are all near-misses the scan actually turned up, not hypotheticals — `spinner_wall` closes a standing false positive rather than guarding against a new one. `us_semi_ramplow` / `md_series_ramplow` sit in a `*_bumper_F` slot and are the entries most likely to be wrong; they are the first to drop.
    - **NOT ONE PERCENT SIGN may appear in the chunk — not in code, not in a string, not in a comment.** That rules out `string.format` *and* every Lua character class, so the part matching is plain `find(…, true)` and byte comparisons throughout. The first draft of the comment warning about this broke the resolve by spelling out the very classes it was warning against; `ramp_resolve_sim.lua`'s format check is what caught it.
    - **A "no ramp here" reply names the parts it did see** (up to `REASON_PARTS_MAX`, byte-sanitised so no quote or comma escapes into the `queueLuaCommand` string). The allowlist is a data question only in-game testing settles, so `extensions.implementProximity.rampTruth()` has to turn a missing entry into a one-word fix rather than a log dive. `lastReason` was already rendered verbatim, so this costs no new plumbing. The success path uses the reason field too, to carry which tiers fired.
  - **The DECK axis tier is a second tier, never a relaxation of the first.** The displacement rule works because a bolt-on ramp hangs off one end of a much larger machine. A tilt deck is the exact opposite — the deck *is* the trailer, its centroid sits on the machine's, `dm` is residue, and the rule rejects it. Loosening the rule to admit that would also admit every cloud whose displacement is residue for the ordinary reason (it isn't a ramp) and would put the cannon's correctness at risk to fix a case the cannon is not. So when there is no displacement to read, don't read one: fall back to the machine's own fore/aft axis with the **rear** forced as the mouth, because you drive onto a trailer from behind — the one fact the cloud cannot supply. Guarded by `DECK_LENGTH_DOMINANCE` (1.5, not `AXIS_DOMINANCE`'s 3.0: a 22 ft deck is only ~2.7x, so 3.0 would reject both vehicles the tier exists for). The ordering matters on a machine where the two disagree, and the stock fleet has one — a `*_bumper_F` ramp is on the **front**, where the displacement tier derives the mouth correctly and the deck tier's assumption would take the wrong end; `ramp_resolve_sim.lua` scenario 15 asserts the deck tier *declines* it rather than answering plausibly. Which tier fired rides in the meta (now **7** fields, and `onRampGeometry`'s malformed guard moved with it) and is rendered by `stateOf`, because the two can disagree about which end of a machine you drive into and nothing else in a readout would reveal it.
    - Everything downstream is already right for a deck: it has no side walls, so `wallUsed` falls to 0 and the existing floor-band fallback returns the deck's true width — which for a deck with nothing to hit *is* the answer. `mouthFrame` reads the five cids live, so a deck still flat reports itself through `pitchDeg` rather than being remembered as drivable.
  - **`ROW_BAND` is 0.35, far wider than the implement resolver's 0.15, because a mouth is not one row of nodes.** large_cannon's is three rows spread over 1.26 m of a 5.79 m span — the toe on the ground, the floor lip, the raised wall — and the wall row is the one the half-width rule depends on. At 0.15 the band captures only the toe, so the wall is never seen and the rule silently falls through to its own fallback. The valid range is 0.218 to 0.782; 0.35 sits with 60% margin above the floor.
    - **...and it is capped absolutely at `ROW_BAND_MAX_M`.** A fraction tracks the length of whatever the ramp happens to be *right now*, which is a constant only on a machine that cannot change its own length. A `us_semi` rollback deck is 9.24 m home and ~12 m with the bed run out, making the "mouth row" a 4.2 m slab; measured at full extension, the two wall picks came out **1.49 m apart along the ramp**. 2.0 m rather than something tighter because the cannon's three rows span 1.264 m and must all stay in the band — at 2.0 its membership is unchanged (uncapped it is 2.03 m, and there is nothing between 1.264 and 2.03 to admit or drop), so the cap cannot regress the vehicle the rule was built on.
    - **A row is not necessarily one plane, and the wall rule must decline rather than answer when it is not.** `floorFitOf` now reports whether its reference nodes actually lie on the line fitted to them. A rollback deck is **two structural levels** — an understructure at u 0.07–0.14 and the drivable surface at u 0.49–0.55 — and the fit lands between them, at a height where the machine has no floor. Every node of the real deck surface then reads as 0.22 m of wall, and the rule (which conservatively takes the *smallest* qualifying lateral) chose an inner rail 0.36 m inboard on each side: **0.936 m against a true 1.296 m, at the home pose, with no tilt or extension involved**. The tolerance `FLOOR_FIT_MAX_RESIDUAL_M` is *derived from* `WALL_MIN_H` rather than being its own number, and that equality is the argument — if the floor is uncertain by more than the height that defines a wall, every wall the row could report is inside the fit's own error bar. It counts a **share** of the reference set off the line (≥2 nodes and ≥⅓ of them), never the worst single one: a spine down the middle of a trough is one node, and condemning a row for it would send the cannon down the two-level path. Where the row is two levels the answer is the lateral extremes of the **top** surface — you drive on the plate, not the structure hanging under it — with overhead nodes excluded by `WALL_MAX_H`, or `ramp_M_0` alone becomes the "top" and collapses the mouth. `wallUsed` falls to 0, which is already how the rest of the mod reads "the wall rule did not answer here". The trade, stated plainly: on a machine with real walls *and* a multi-level floor this over-reports clearance where the old form under-reported it — the right direction for a deck, which has nothing to hit, and the direction that stops `RAMPALIGN` refusing a car that fits easily.
    - **`EDGE_TIE_M` — two nodes that close laterally are the same edge, so the STATION decides between them.** A row band holds several stations by design and a deck's side rail runs through all of them at the same lateral offset, so the extremes are a tie to the millimetre and a strict comparison resolves it by `pairs()` order. Measured in game: mouth markers **1.45 m apart along the ramp**, a live 3-D `halfW` of 1.42 m against a meta figure of 1.29 m *from the same resolve*, and the derived axis and centre skewed with it. Nothing in the meta could ever have shown it — `halfW` there is a pure lateral difference, and the lateral answer was correct throughout. The mouth row breaks ties toward the mouth end, the inner row toward the inside; both are the same rule, take the marker from the end of the ramp the row represents. `ramp_resolve_sim.lua` scenario 18 replays all of this against the **72 real `us_semi_rollback_deck` node positions** read out of a running game, reproducing the shipped `0.93566` to five decimals as its negative control.
  - `M.mouthFrame(vehID)` reads the five cids **live** every tick (the same five-call budget the implement's sample set already costs), because the whole assembly tilts on its `ramL`/`ramR` cylinders — geometry derived from design space is a lie the moment the inclination control moves. `centre` is the two-point midpoint of the edges, not the mean of all three, for the same reason `getImplementFrame` excludes `edgeC`. `left` is `vec3(0,0,1):cross(axis)`, and `vehicle_geometry_sim.lua` scenario 11 now greps this file too — three files have to agree on `up:cross(fwd)` and nothing but that grep enforces it.
