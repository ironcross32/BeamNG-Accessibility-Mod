# Lua: `vehicleGeometry.lua`

- **`lua/ge/extensions/vehicleGeometry.lua`** — Per-vehicle derived node geometry (extents, hull cids, front/rear contact bands, vertical occupancy histogram) for **any** vehicle, player or target. No ports of its own; it is a library the scanner and `implementProximity` both call. `diagnostic/vehicle_geometry_sim.lua` (`lua diagnostic/vehicle_geometry_sim.lua`) replays the classification and the distance query against synthetic clouds with known ground truth — run it after touching any of it. Scenario 14 rebuilds the wrecked Vivace and asserts both the bug and the attachment filter. With no standalone Lua on the machine, it runs inside the game: copy it under the user folder (e.g. `current/beamtel_sim_tmp/`), then `dofile` it through `lua_exec` with `io.open`/`loadfile` remapped from `bng_mod/` to `/`, `io.popen` answered from `FS:findFiles`, and **`os.exit` stubbed**, or its failure exit closes the game. Run that way, scenario 12's source greps report failures in files this area does not touch, so judge them separately.
  - **The reason it exists**: `vehicleScanner` measured `originPos:distance(targetPos)` and `getPosition()` is the object's reference node, so every distance was centre-to-centre. That carried half a vehicle of phantom range at each end and was **orientation-dependent** — broadside and nose-on to the same car at the same real gap reported the same figure. The sim's scenario 2 is that exact comparison and is the check most worth keeping.
  - **The loader is a cid list, not a branch.** Nothing downstream asks "is this a loader"; it asks for a *contact set* and a *surface set*. A generic car in forward is its own front node band, the same car in reverse is its rear band, a WL-40 is the five implement cids. That is what makes it impossible for loader work to regress the generic case — the loader is a different **answer**, not a different code path.
  - **The fallback chain terminates at today's behaviour** and is the whole safety property: hull cids → nearest hull node; else extents → closest point on the oriented box; else `getPosition()`. A vehicle whose async resolve never lands still answers, just less precisely, so no caller handles a nil. **Giving up has to be recorded, not just stopped**: `M.request` is documented as cheap to call every tick and every query does call it, so clearing `pending` after `MAX_TRIES` with nothing in `cache` merely re-arms the resolve on the next frame — the cross-VM chunk went out every 3 s and the "staying on fallback" warning was logged every 9 s for the whole session. A `failed` set gates `M.request` and is cleared per vehicle in `dropVehicle`/`dropAll`, so a reset or part swap still gets a fresh attempt. A malformed reply (`#ext ~= 6`) is flagged the same way; a VM answering with the wrong shape will keep doing so.
  - **`up:cross(fwd)` is the lateral vector, in both this file and `implementProximity`.** They must match: `implementProximity`'s `boxFrame` projects onto its own vector and clamps the result against `minR`/`maxR` taken straight from this cache, where `VEH_SCRIPT` measured them along its. It built the negation (`fwd:cross(up)`), which mirrored every lateral test against a cached target — the containment call and the slam footprint both answering for the far side of the vehicle. It survived because the strided fallback measures with whatever frame it is handed and so stays self-consistent: the readout was right for the first few ticks after a spawn and flipped when the async resolve landed. Both names (`rgt`, `right`) are misnomers — the vector points to the driver's *left* — and renaming either is exactly how they would stop agreeing. `vehicle_geometry_sim.lua` scenario 11 asserts the agreement, asserts the old form inverts, and greps both sources.
  - **`nearestSurfacePoint` keeps the SMALLER of the box and node answers**, the way the vehicle VM keeps the smaller of its terrain height and its raycast. The two tiers fail in opposite directions: the box encloses the body so it can only under-read, but it is exact at the surface; the node sweep is a sparse sample so it *over*-reads near contact by up to half the node spacing — thinning a car's shell to 48 measured 0.19 m of over-read, i.e. clear air reported while the tines are touching. That measurement is why `HULL_MAX` is 128 and not lower.
  - **`HIST_BINS` sets the finest pocket the mod can see at all**, because band thickness is quantized to the bin height. At 24 bins a 1.63 m target gave 0.068 m per bin, which silently turned `implementProximity`'s `BAND_MIN_HEIGHT_M` of 0.10 into "at least two bins" and discarded every genuine single-bin void — a real thin pocket was unreachable regardless of whether it existed. 48 bins is 0.034 m there, making the same threshold a real ~3-bin test. The wire format is `table.concat(hist, ",")` and both ends ship in the same mod, so no shim is needed — but `M.onVehicleGeometry`'s `#hist == HIST_BINS` guard is what makes a half-updated install fail loudly instead of mis-binning, and must stay.
  - **A node is part of the vehicle only while unbroken beams connect it to the reference node.** A part that breaks off stays in the *same object*, and the game's only record that it has come off is that every beam holding it is broken (`obj:beamIsBroken`). So `VEH_SCRIPT` walks the unbroken beams out from `v.data.refNodes[0].ref` and classifies only what that reaches. Found on a wrecked Vivace: in D the scanner read **0 ft** to a car 400 ft away, and in R it read **477 ft**. Its 113 debris nodes lay in five pieces (60, 80 and 114 m ahead, on top of the car it had hit; 16 and 46 m behind), and the gap trim below cut only the outermost piece at each end, so it called the rest a 97 m car whose front band was the 80 m cluster. Beam connectivity picked out the 681 body nodes exactly; measured afterwards, D read 121.7 m and R 124.8 m (one car length apart, as they should be).
    - **An intact vehicle is byte-identical, by construction rather than by test.** Nothing is computed unless some beam is broken (every stock vehicle checked had 0 broken at spawn: pickup, WL-40, US semi, tanker, Vivace, SBR), and a node is dropped only if the *intact* beam graph reaches it and the live one does not. That second rule is load-bearing: the US semi has **26 of 1,677 nodes no beam path reaches even intact** (rails and similar), and without it the first broken pane of glass would have deleted them.
    - **`MIN_ATTACHED_FRAC`**: if the live piece holding the reference node is under half of the intact reach, it is the reference node that has come off, and the filter stands down rather than describe the vehicle as that fragment.
    - **Why not the game's own box.** Every stock consumer (radar app, traffic collisions, parking, crash camera, `spawn.lua`) uses `getSpawnWorldOOBB()`, which is `initialNodePosBB` (spawn-time node extents) carried on the reference-node frame. It ignores debris, and on the Vivace it contained exactly the 681 attached nodes — but it is the *spawn* shape, so it cannot show crush, and a raised loader boom or an articulated front frame leaves it by metres. Connectivity has neither problem.
    - **This is a behaviour change for `implementProximity`**: a bumper lying in the road is no longer part of its car's surface, so the loader no longer reports it. Accepted deliberately — the alternative is a wreck's debris tens of metres away answering for the car.
  - **The cache is refreshed after a crash, not only on reset.** It used to be resolved once and trusted until `onVehicleResetted`, so a car that shed its bumper *after* the first resolve kept that bumper's cids as its front band. `lua/vehicle/extensions/beamtelGeometryWatch.lua` is loaded by `VEH_SCRIPT` into every vehicle VM that has been resolved, listens to the game's `onBeamBroke` and `onSlidenodeDetached` hooks (`lua/vehicle/main.lua`), waits for the burst to settle (`QUIET_S` 0.5 s, `MAX_WAIT_S` 2 s ceiling) and calls `M.onVehicleBroke`. That **keeps the old entry until the new reply lands** — dropping it would put every caller on the centre-to-centre fallback for the round trip, a jump in the reading just after a crash — and supersedes any resolve already in flight, since it may have run before the break. The reply's optional 8th field is the dropped-node count, logged only.
  - **Extents are a gap-trimmed range, not raw min/max** (`OUTLIER_GAP_M`, `TRIM_MAX_FRAC`). Detached parts are gone before this runs; what it still guards against is *attached* geometry standing well clear of the body (a part hanging by its last beam, a raised boom), which would stretch the box across empty air and report solid surface where there is none — and wreck the normalisation, collapsing every real body node into a slice of the 0–1 range so hull and band classification stop distinguishing anything. A percentile trim is the wrong tool because such a part is a **dense** cluster; what separates it from the body is empty space, so that is what gets measured. It cuts at the *first* gap from each end only, which is why it could never have handled debris in several pieces on its own. The outlier still normalises outside 0–1, trips the face test, and stays visible to the node tier.
  - **`M.debugVehScript()`** exists so the sim can compile the cross-VM chunk. A syntax error inside a `queueLuaCommand` string does not fail where it is written — it fails in another VM, silently, and the only symptom is that geometry never resolves and every caller sits on the `getPosition()` fallback for the whole session.
