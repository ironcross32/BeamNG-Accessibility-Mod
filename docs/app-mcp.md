# App: the MCP server

`crates/beam-engine/src/mcp_server/`, ported from the Python `mcp_server.py`. Port 4481, loopback, off by default.

- **beam-engine mcp_server/** — An MCP server so an AI agent can drive and test the mod: execute Lua in the game, place vehicles into known geometry, read live state, trigger any F9 command, and assert on what the mod announced. Gated by `mcp_server_enabled` (default **off**) and bound to `127.0.0.1` only. `get_config` **masks every secret-named setting** (`<redacted>` when set, empty when unset, off `SECRET_NAME_PARTS`): its output lands in agent transcripts and logs, so a key readable through it is a key that has left the machine — and it is masked even now that the stored value is a DPAPI blob, because that blob is still the credential in transportable form. Whether a key is *set* is left visible, because that is the fact an agent legitimately needs (it is why the describer refuses to run) and it gives away nothing. `mcp_server_sim` (`beam-engine`) stands the server up on a spare port and drives it over real HTTP — run it after touching any of this.
  - **Start beamtel BEFORE Claude Code.** MCP tools are discovered once, when the client connects and calls `tools/list`; a server that was not listening at that moment simply is not there, and the symptom is not an error but an *absence* — the agent quietly falls back to asking the user to do everything by hand, which is the exact failure this feature exists to remove. `mcp_server_enabled` is also read once in `run_engine`, so flipping the flag needs a beamtel restart either way. If the tools are missing mid-session, `/mcp` inspects and reconnects the server; that is cheaper than restarting the conversation. `.mcp.json` is committed at the repo root, so with the flag **off** — the default — every session in this repo shows one failed server. That is the accepted cost of not hiding the config somewhere ungitted, and it doubles as a reminder that the flag is off.
  - **It exists because half of this mod cannot be tested any other way.** The sims replay a state machine against a fake clock, which catches wording and sign errors; they cannot catch a resolver landing on the wrong node, which produces confident, plausible numbers. That half has until now cost the user a drive across a level per test.
  - **The transport is loopback HTTP, not stdio, and that is forced rather than preferred.** A stdio server is a process the agent starts itself, so it could not be the beamtel the user already has open. And it has to *be* that process: the engine state lives here, and port 4466 is exclusively bound by `console_listener`, so a separate process could never listen for a console reply. Hence an HTTP server (tokio + axum) on its own thread inside beamtel, like the UI bridge.
  - **No MCP SDK is a dependency.** The Python decided this against a release size limit; the reason that still holds is that MCP over streamable HTTP is JSON-RPC 2.0 with five methods, which axum already serves. Two protocol details are load-bearing and are asserted rather than remembered: a **notification must be answered with 202 and an empty body** (get it wrong and the client hangs on the handshake, with nothing to see), and **`GET /mcp` returns 405**, which is how a server says it offers no server-initiated stream. No `Mcp-Session-Id` is issued — there is no session state, and not issuing one deletes a class of bugs.
  - **A tool failure is `isError`, never a JSON-RPC error.** JSON-RPC errors are for protocol faults (unknown method, unknown tool, bad JSON); "the game is not running" is something the model has to *see and reason about*, so it comes back as content.
  - **EXEC correlation is the hard part, because `consoleAccessible.lua` has no request IDs** — ordering plus the `EXECEND` sentinel is all there is. `exec_lock` keeps exactly one EXEC outstanding, which is what makes ordering a sound basis. `register_console_tap` installs `console_tap` into `console_listener`, and the tap **consumes** the records it owns: `on_console_message` speaks any single-line result aloud, so without suppression every agent exec would talk over the user mid-test. `LOG` records are copied but **never** consumed — they arrive unsolicited and belong to the GUI's log pane. The tap is unset unless the server started, so the cost when it is off is one identity comparison per datagram.
  - **Reassembly must concatenate, not newline-join.** `emitChunks` repeats its prefix on *every* chunk, so a long value arrives as several `OUT|= ` records that are one string. Bare `OUT|` is genuinely ambiguous — a continuation of a long print line looks exactly like the next print line — so a chunk counts as a continuation when the previous one filled the datagram or already ended in a newline, and `verbose` always exposes the raw records for when that heuristic is wrong.
  - **The speech tap is a second buffer, not `SPEECH_BUFFER`.** That one holds only what the user can replay, and most mod output passes `exclude_from_buffer=True` — so it is not a record of what the mod said. `SPEECH_TAP` records every `say()` call, **including ones suppressed during loading** (flagged `spoken=False`), because "the mod correctly stayed quiet" is as worth asserting on as what it announced. It records at the point of utterance, so it captures the final text after the loading check and after the `speech_protected_until` interrupt demotion. Cursors are **sequence numbers, not timestamps**: a reader polling for what changed needs exactly-once semantics, and `time.time()` ties and skews. `dropped` says history was lost rather than letting an empty list mean two different things.
  - **F9 commands are injected in-process.** `on_next_key_press` duck-types its event — only `.event_type` and `.name`, with modifiers from `capture_mods` — so `mcp_press_command` drives any command with no OS key injection and without BeamNG having focus. `press_command` returns the speech produced during the call, making one round trip act *and* assert.
  - **One tool per UDP port would be forty tools.** `send_command` takes a module name resolved against a port map (a typo is then an error rather than a datagram into the void), and `lua_exec` reaches every Lua diagnostic that has no UDP verb at all. The set is ~16 on purpose.
  - **`camera_control` and `screenshot` are the eyes, and they are one instrument in two halves.** Every other tool reads numbers, and the failure this server exists to catch — a resolver landing on the wrong node — produces numbers that are confident and plausible. Looking is how you disprove one. The pairing is the point: place the eye, then shoot.
    - **Camera control is composed GE Lua through `exec_console`, not a new verb on `cameraInfo.lua`'s 4451, and `bng_mod/` does not change.** Readback is the requirement — a set that answers with the resulting pose is self-verifying in one round trip — and `exec_console` is the only channel that returns a value synchronously; 4451 is fire-and-forget, and giving 4450 a reply format for agent-only queries would be new wire protocol on a live junction. A new *listener* would additionally owe the `setsockname`-return / `onExtensionUnloaded` / `retryCmdBind` triple that `vehicle_geometry_sim.lua` scenario 12 polices. And this is precisely what `t_diag` already is: a curated wrapper over Lua the agent could have typed, leaving `lua_exec` the universal surface. `cameraInfo.lua` stays read-only telemetry.
    - **Two angle conventions collide, and both are DERIVED from the game source rather than measured**, because each is the exact algebraic inverse of the other. `core_camera.setFreeCameraYawPitchRollDeg` builds its forward as `(sin y·cos p, cos y·cos p, −sin p)` (`core/camera.lua:1105`), so its yaw is `atan2(f.x, f.y)` and its pitch is positive-**down**; `cameraInfo.lua:253/258` reports yaw as `atan2(−f.x, −f.y)` and pitch positive-**up**. Since `atan2(−x, −y) ≡ atan2(x, y) ± 180`, the yaws differ by exactly 180° with the same sign and the pitches by a sign alone — hence `CAM_YAW_OFFSET_DEG = 180.0` and a single negation, not a constant somebody had to fly around and calibrate. The tool speaks the **mod's** convention in both directions and derives its readback from `getForward()` the way `cameraInfo.lua` does, rather than from `core_camera.getYawPitchRoll()`, which speaks the engine's — so `get` can never disagree with the 4450 feed or the `Alt+H` readout about the same camera. A sign error here is invisible from the seat: the camera tilts the wrong way and every readout still agrees with itself, which is why `mcp_server_sim` (`beam-engine`) scenarios 17a–17e round-trip the whole sphere **and** assert what the un-offset and un-negated forms would have answered.
    - **`setPosition` and `setFreeCameraYawPitchRollDeg` both early-return unless the free camera is already active** (`core/camera.lua:1088`, `:1573`), so a `place` that skipped that step would report success and move nothing. Every `place` chunk enters it first — via `commands.setFreeCamera()` rather than a bare `setByName(0,'free')`, because that seeds the free cam at the current pos/rot (`commands.lua:38`) and there is no visible jump. `is_free` in the returned readback is therefore *proof* the placement landed, not an inference from the absence of an error.
    - **`rel_right_m` is positive to the vehicle's RIGHT, deliberately the mirror of the mod-wide positive-is-LEFT rule.** That rule governs bearings *reported to a driver*; this is a placement parameter literally named "right", and building it as `up:cross(fwd)` to honour a convention it is not part of would make every relative shot land on the wrong flank. Orbit elevation is measured off the **world** horizontal on the vehicle's **flattened** heading, so "30° up at 10 m" means the same thing on a machine parked nose-down a bank as on one standing level.
    - **A composed chunk must fit one datagram.** `consoleAccessible` receives `EXEC|<ctx>|<code>` as a single UDP packet, so the action and the readback are two round trips rather than one concatenated chunk, and the length is checked before sending. No chunk contains a percent sign — `n360()` replaces the modulo operator — because these strings share a file with `%`-formatting throughout. A camera *name* is validated as an identifier rather than escaped, which keeps quotes out of the chunk entirely.
    - **Argument validation runs before `require_world()`.** A typo'd action is a caller error and must name the valid ones whatever the game is doing; told "the game may be closed" instead, the agent goes and debugs the game. (This is otherwise `require_world`'s first caller — it had been defined and used by nothing.)
    - **A minimized BeamNG renders NOTHING, and a plain monitor grab of it returns the desktop.** Found on the first live run: the game parks its window at `-32000, -32000` and renames itself `BeamNG.drive - ... - background`, so `capture_primary_monitor()` — correct for the AI Describer, which fires from a keypress while the user is playing and the game fills the display — handed back a screenshot of the user's desktop, icons and all. That is the exact failure mode this server exists to catch: silent, and entirely plausible until you look at it. So `screenshot` defaults to **raising the game window** (`focus_game`), grabbing the window's own rectangle rather than the monitor, and putting the previously focused window back afterwards; `capture_scene_png` keeps `focus_game=False` so the describer's behaviour is byte-for-byte what it was, since raising a window under someone mid-corner is a real cost and buys that caller nothing. `SetForegroundWindow` is refused for a process that does not already own the foreground — and beamtel runs elevated while the game does not — so the input queues are attached first, which is the documented way to be allowed; every step is best-effort, because a refusal must degrade to a worse screenshot rather than an exception. **What was actually captured rides back in the result**, and `window_region` rejects the `-32000` park explicitly: without that the tool would report success while returning the desktop, which is the only outcome here worse than failing.
    - **`screenshot` shares the AI Describer's capture path and sends the image nowhere.** `capture_scene_png()` is factored out of `ai_describe_worker` in `beam-engine` so the HIDE → settle → grab → SHOW sequence, and the 0.2 s constant, exist once; the tool writes the PNG to a caller-named directory (the agent's own working directory) and returns an absolute path to read. Names are stamped to the **millisecond**, because a before/after pair is what the tool is mostly for and two shots in one second must not collide.
    - **The capture lock is NOT the describer's busy flag.** Both callers toggle the game UI, and two overlapping sequences race — the first one's `SHOW` lands mid-grab of the second, so the shot that asked for a clean world gets the HUD back in it. `describer_busy` answers a different question (a double-press of `F10` `Space` should buzz rather than queue a second AI request) and must not refuse an agent screenshot, nor be consumed by one; hence a separate `capture_lock` held across the whole sequence.
    - **Writing an arbitrary path is not a new class of exposure** — `lua_exec` already runs arbitrary Lua there — so the mitigation is unchanged and unchanged on purpose: the flag defaults off, the bind is loopback, and a non-loopback `Origin` is refused. A path allowlist would defeat the tool's only real use.
  - **Arbitrary Lua in the game is a real local exposure**, which is why the flag defaults off, the bind is loopback, and an `Origin` header from anywhere but loopback is refused. There is no auth token; the mitigation is that the port does not exist unless the user turns it on.
