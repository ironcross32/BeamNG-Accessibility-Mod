# Python Components

- **beamtel.py** — Main entry point. UDP telemetry listener, keyboard command system (F9 hotkey + modifier combos), drives audio and speech.
  - **`F9` `Space` is one key with two answers, split on whether the game world is live.** Driving, it fires a terrain sonification scan; in a menu it keeps doing what it always did and activates the on-screen control. That is a real disambiguation rather than a priority call: the only screens `bnvdaRuntime.js` offers a context action for are the freeroam wizard and the configurator, both of which run with **no level loaded**, so the two answers can never both apply. The world test is `_world_is_active()` — telemetry seen on 4444 within `WORLD_ACTIVE_TELEMETRY_S` — because that feed is the vehicle VM's own protocol and therefore exists exactly when a level is loaded with a vehicle in it. It is physics-driven, so it also stops while the game is **paused**, and a scan is declined there; that is the conservative way round, since the fallback is the harmless no-op the key already did. The scan speaks nothing on success: the reference ping at the head of the cloud *is* the acknowledgement, and speech would talk over the first half-second of the scan it was announcing. A watchdog thread speaks only if the mod never answers, because silence and a dead extension are otherwise identical.
  - **The cannon shot readout has no keybind, and that is the design.** It announces itself when the car comes to rest, which is the only moment it has anything to say — and the moment you are guaranteed to be listening, having just heard the crash. `_cannon_shot_phrase` follows `_dock_phrase_ramp`'s doctrine because it fires unprompted after a crash and every clause it adds is one nobody asked for: distance and how far off line, always, since those two *are* the outcome; apex, what it stopped beside, and the comparison against the previous shot only when each is the interesting thing about that shot. Nothing in it confirms a shot went well — there is no such thing as a good shot out of a cannon with no horizontal aim, and saying so would be inventing a target. It uses the **whole-number long-distance form**, not `fmt_distance`, which is tuned for implement clearances and renders a 300 m shot as "984.3 feet". The comparison clause is what makes a session-only log worth keeping with no key to read it back: the answer to "did raising the barrel do anything" arrives inside the announcement of the shot that answered it, and it skips a previous shot that never settled, because that one has no landing place to compare against. Spoken **without** `exclude_from_buffer` — unlike every keypress readout this is unsolicited, so it is exactly the kind of thing worth replaying.
  - **`terrain_scan_listener` reads with a 65535-byte buffer**, not the 1024/2048 the other listeners use. A snapshot is one datagram of a few kilobytes, and a short read there fails as a landscape that stops halfway rather than as an error. It also *renders* the scan on its own thread — see `render_scan` in `audio.py`.
  - **The alignment readout is one key with four answers.** `F9` `I` speaks the cannon's firing state when `cannon_active` (you are sitting in a ramp machine), otherwise the docking readout, otherwise **your own machine's deck state** when it has a ramp of its own, otherwise "instrument is off". Cannon-first because once you are in the cannon the alignment task is over and the aiming task has begun; folded into the existing key rather than given a binding of its own, for the same reason the slam gate rides on the docking toggle. `_dock_phrase` dispatches on the mode to `_dock_phrase_impl` (unchanged, and `dock_readout_sim.py` scenario 16 asserts it is byte-identical to before the split) or `_dock_phrase_ramp`, which shares none of its vocabulary — there is no band, no thickness, and nothing on a car that goes up or down.
  - **`F9` `Shift+V` is one key with two alignments**, routed on `dock_mode_active`: instrument on sends `RAMPALIGN` to the mod, otherwise the scanner's `ALIGN` path runs byte for byte as before. `_ramp_align_phrase` is a pure function next to `_dock_phrase` rather than inline in the listener, because the wording and the two margin bands are the part worth checking without the game; `dock_readout_sim.py` scenario 18 mirrors it, including that an `NA` margin is **silent** — a false "it will not fit" about a machine that fits is how a driver learns to ignore the clause.
  - **The deck readout is the answer for the machine you are SITTING IN**, and every other figure this key can produce measures from one machine to another. It exists because fixing the phantom-cannon bug left a hole: from the seat of a `us_semi` rollback the key used to answer with the cannon's aiming state (wrongly), and once that was corrected it answered "Docking instrument is off" — correct, and useless. `_ramp_self_phrase` reads the ramp's live pitch and then every hydraulic group the machine has, and it reads them out **unconditionally** rather than following `_dock_phrase_ramp`'s bad-news-only rule: that rule is about clauses nobody asked for appended to an utterance that was going to happen anyway, whereas these numbers *are* the question, and a readout that went quiet because the deck happened to be level would be indistinguishable from a broken one.
    - **It is ordered strictly BELOW a live docking reading, unlike the cannon branch.** The cannon wins outright on the argument that once you are in the cannon the alignment task is over; that argument does not carry here, because a hauler is a perfectly ordinary thing to drive up somebody else's ramp, and an alignment readout the driver deliberately switched on must not be displaced by a fact about their own bed. So the branch fills in the three cases that previously had nothing useful to say and changes no case that did.
    - **Tilt is an ANGLE off live geometry; extension is the RAM's own travel.** Not a stylistic split — the geometric route is wrong in exactly the pose the readout exists for. Measuring the mouth's displacement from the machine's reference node along the deck axis is exact at rest and picks the tilt up as false extension, because the reference node does not lie on the axis the deck rotates about: measured on the rollback, a pure 10.2° tilt with the bed fully home slid the mouth **0.123 m** along its own axis, i.e. four inches of announced extension on a deck that had not moved, growing with the angle. The ram carries no such term — against the same vehicle its stroke tracked the geometrically measured deck travel to **1 cm over 4.88 m**. The angle keeps the tilt job because it is what the driver of the car about to go up the ramp needs, it is what `_dock_phrase_ramp` already speaks, and it survives on a ramp with no hydraulics at all; the rams then say how much stroke is *left*, which the angle cannot.
    - **Groups are named by their own `directionElectricsName`, never by a word list.** That field is the string the vehicle's own Special Vehicle Keys bindings are driven by, so a machine nobody has thought about reports its controls under the names its own key list already uses. A leading segment shared by **every** group is dropped (`upfit_tilt` / `upfit_extendRetract` / `upfit_extendRetractFeet` → "tilt", "extend retract", "extend retract feet") and that requires **two or more groups** — a prefix is only identifiable as a namespace by several names sharing it, and on a machine with one group its first segment may be the only word saying what the thing does. `dock_readout_sim.py` scenario 19 asserts the guarded and always-strip forms differ.
    - A long stroke reads as a **distance** and a short one as a **percentage** (`RAMP_SELF_DISTANCE_STROKE_M`). Both figures are always available; the question is which one a driver can act on. Five and a half metres of deck travel is the run-up they are about to drive; "1 of 2 feet" is a worse way of saying 34 percent. It is a property of the ram, so nothing needs to know what vehicle it is on.
    - **The lip's height above ground is the third figure, and it is the only one that answers "can a car get onto this".** Neither of the other two does it alone. Measured on a `us_semi` `tc82s_rollback`: home and level the lip sits **1.30 m** up, **full tilt alone only brings it to 0.95 m**, and it is running the bed fully out *as well* that puts it at **0.15 m**. So a driver reading pitch and extension has to combine them; the lip is the answer directly, and it is stated in **both** directions (`Lip on the ground` / `Lip 4.3 feet up`) rather than as bad news only — this readout is solicited, so silence there would be indistinguishable from a mod half that cannot measure it. `be:getSurfaceHeightBelow` reports failure as a huge **negative**, not nil, so both copies use a magnitude band; `-999` is the sentinel and must never be `0`, which reads as the single most reassuring thing this readout can say.
    - **Both latches heartbeat, and that is a correction found in testing rather than a precaution.** The VM pushes hydraulics on change and `implementProximity` sends `RAMPSELF:` on change, and neither latch can be cleared by the *other* process restarting — which is exactly what happened: with beamtel restarted and `implementProximity` reloaded, the GE table was empty, the VM's change test then suppressed every push, and the key stayed silent until the bed was physically moved. The failure is invisible, because the fallback answer ("docking instrument is off") is a real answer for a real reason. The `ON` probe does re-arm the GE latch, but it cannot reach the VM's. Same argument, same interval and same fix as `IMPL_PUSH_HEARTBEAT_S`, which this repo already paid for once.
    - `-999` is the mod's "could not measure" pitch sentinel and must never be `0`, which reads as a perfectly level ramp; Python renders it as `Ramp angle unavailable` and still reads the rams out.
  - **`cannon_active` is derived from geometry, not from a jbeam name allowlist — but "has a ramp" is NOT that geometry.** The two aiming values come free off existing telemetry because large_cannon's controller publishes them there itself: `electrics.values.rpm = targetInclination * 1000` and `electrics.values.gear = "<strength>%"`. The signal was `rampGeometry.has()` on the player's own vehicle, which was sound for exactly as long as large_cannon was the only vehicle whose ramp resolved at all; `rampGeometry`'s part tiers exist precisely so a rollback, a tilt deck and a dry van resolve too, and every one of them then latched `CANNON:LARGE`. Measured from the seat of a `us_semi` `tc82s_rollback`: **"Inclination 100 percent, strength unknown"** — the inclination being the truck's *own engine RPM* over a thousand, pegged because its `hydraulicsCombustionEngineControl` raises idle to 1500 the moment the pump engages, and the strength a gear string that is not a percentage. It also silently masked the ramp readout that machine *should* get, because the cannon branch of `F9` `I` wins ahead of `_dock_phrase_ramp`. The signal is now `rampGeometry.isCannon()`, resolved from the presence of large_cannon's **own controller** in the vehicle VM — a capability check on the source of the readout, the same shape of argument `cannonGeometry` makes in demanding a `beamType 7` launcher beam rather than trusting a filename.
  - **That gear abuse is also a regression, and is suppressed rather than tolerated.** The cannon rewrites the gear string on *every* press of the strength keys, so without a `cannon_active` gate on the gear-change announcement, aiming produces a stream of `extended_gear_to_phrase("80%")` across the whole manoeuvre. The strength is not lost — `F9` `I` reads it on demand, which is the right shape for a value you sweep and then check. (The swept `rpm` needs no such gate: it never reaches `audio.py`, and the shift tone is driven by the `DL_SHIFT` dashboard bit, which a cannon has no engine to set.)
  - **The mode latch is not cleared on `DOCKCLEAR`/`DOCKFAIL`.** Losing the target is not a change of mode, and clearing it there re-announces every time you drift across the feed's edge — measured at twenty announcements for one approach. Only a part swap, a vehicle change or the toggle resets it, and the toggle claims the latch itself so it and the listener cannot both announce the same change. `implement_proximity_sim.py` scenario 12 asserts both halves.
  - **The `DOCK:` parse ladder must be `elif`, not a second `if`.** A successful 15-field split leaves `len == 15`, which is also `!= 13`, so an independent second test immediately re-splits it down to 11 and throws the mode and margin away on every ramp packet.
- **audio.py** — Procedural audio synthesis engine. Real-time stereo 48kHz float32 via `sounddevice` callback. Compass clicks, shift/TC/steering tones, warning buzzers, drift alerts, heading guidance, scanner beeps, obstacle detection tones.
  - **Articulation / hydraulic steering tone** — for machines whose steering does not self-centre (the WL-40 wheel loader bends its frame with a pair of opposed rams, so releasing the joystick leaves it bent). Driven by `actualSteering`, which is **0.0 on every vehicle with normal self-centring steering** — that is what auto-detects the hydraulic ones, so nothing here needs a per-vehicle check. Pitch (`HYDRO_STEER_LO_HZ`→`HI_HZ`) and level (`MIN_DB`→`MAX_DB`) rise with the offset, HRTF azimuth tracks it out to `HYDRO_STEER_MAX_AZIMUTH_DEG`, and the voice is **FM** rather than a sine because the loader itself is loud enough to bury one. The C:M ratio glides from an exact 2.0 near straight (sidebands land on harmonics — clean) to a non-integer 2.76 at full lock (off-harmonic — rough), with the modulation index rising alongside, so being badly off-centre *sounds* wrong rather than merely higher. Ratio and index follow `norm ** HYDRO_STEER_FM_DIRT_CURVE`, **not** `norm` — scaling them linearly is piercing in normal use, because half lock already lands at ratio 2.38 and a 1.5 kHz centroid. Cubed, the ratio holds within ~0.1 of the integer through the middle of the range and only goes wild in the last quarter. Pitch stays linear in `norm`; it's only the timbre that's curved. **`HYDRO_STEER_MAX_AZIMUTH_DEG` must stay well under 90°** (75° now): the KEMAR set's interaural level difference peaks near 67.5° and then *falls* about 5 dB out to 90°, so mapping full lock to 90° made turning harder past ¾ lock read as the sound coming back toward centre. The sim asserts this. Note the azimuth scales on raw `actual_steering` while level and pitch scale on the `HYDRO_STEER_FULL`-normalised value, so the stereo image keeps opening after the tone has saturated. Carrier and modulator phase, ratio and index are all glided across the callback block; stepping any of them per-callback zippers. and a **centre-crossing click** fires once as the frame arrives at straight — silence alone is ambiguous, since it also means "idle". That click is deliberately *atonal* (seeded band-limited noise, 2.5–7 kHz): the compass and cam clicks are FM tones around a 900 Hz carrier, so anything pitched near there gets mistaken for one. Band-limited rather than plain high-passed, because raw noise peaks near Nyquist — thin, and the first thing to go with high-frequency hearing loss. The click arms only past `HYDRO_STEER_DEADZONE * HYDRO_CENTER_REARM` so hunting around centre can't machine-gun it. Level uses a dB *range*, not a linear scale to zero, or the near-straight case would be inaudible — which is the case the feature exists to report. `diagnostic/hydro_steer_sim.py` (`python diagnostic/hydro_steer_sim.py`) replays the gate/envelope/click state machine against a fake clock — run it after touching that block.
  - **Loader implement tones** — two voices for the WL-40's bucket/forks, both driven off the implement block in the extended struct and both gated by one shared fade envelope. Both are **split left/right by a fixed equal-power pan** (`IMPL_STREAM_PAN`, ground left, tilt right). They were originally both centre-panned, reasoning that the articulation tone already owns the HRTF slot, the implement is dead ahead by definition, so an azimuth of 0 carries no information and would cost two `np.convolve` per callback for nothing. That was true and beside the point: **two continuous sounds from one point in space fuse into one object** — the same principle this file invokes to justify rendering the docking beat pair centre, running the other way. The two voices are continuous, and they overlap in register (the 180 Hz carrier sits 1.6 semitones under the tilt scale's 200 Hz floor and its sidebands land across the middle of it), so centred they were reported as *one tone that changes character*, with lift and tilt indistinguishable. The split is **not a direction cue, it is a streaming cue** — a constant offset cannot be misread as a bearing because a bearing moves and this does not — and being pure gain it costs two multiplies, not the convolution a real azimuth would. `implement_tone_sim.py` scenario 6c asserts the mirror and the equal-power sum. `diagnostic/implement_tone_sim.py` and `diagnostic/implement_proximity_sim.py` replay both state machines against a fake clock — run them after touching either block.
    - **Ground proximity (FM).** Grit means "close to the ground"; pitch means "you are levering the machine off its wheels". Keeping those on two axes is the whole design, which is why the carrier is **fixed during the approach** — a rising pitch can then only ever mean lift. The C:M ratio starts on an exact integer far out and drifts off it as the implement nears the ground, with the index rising alongside. **`IMPL_GROUND_RATIO_DRIFT` must stay below 0.5**: at 1.0 the drift would arrive at the *next* integer exactly at contact, so the tone would sound clean at the moment it means "about to hit" — the inverse of its meaning. The dirt curve is **2.0, not the articulation tone's 3.0**: there, grit is an alarm reserved for the last quarter of travel, so cubing is right; here the drift *is* the graded distance readout and has to be legible from about a metre out, and cubed it leaves 2.0 m → 0.5 m nearly clean. When the implement is actually against the ground and jacking the machine up, a smoothstep ramps the ratio onto the next integer (clean again) and the carrier rises by `IMPL_GROUND_JACK_OCTAVES` with the lift. **`IMPL_GROUND_INDEX_HI` and `IMPL_GROUND_MAX_DB` were both pulled back after play-testing** (3.2→2.2 and −16→−19.5 dB, together about a quarter off the brightness at contact). The original values assumed near-the-ground was a state you pass *through* on the way to a dig; getting a bucket **under** something means working there continuously, and at the old settings the tone was harsh enough to be a reason not to use the feature. The level is only a default — `implement_ground_tone_dbfs` overrides it, so an existing config keeps whatever it already had. **Both implement tones map their level as a span hanging below the configured value** (`IMPL_GROUND_SPAN_DB`, `IMPL_TILT_SPAN_DB`), not as an interpolation up from `IMPL_*_MIN_DB`. The MIN constants are the quiet end *at the default level*, not an absolute floor: the old form inverted as soon as the configured level fell below one of them, and the configurator allows −120, so a user turning the ground tone down to −40 got −30 dBFS two metres out and −40 at contact — quieter as the bucket approached, loudest with nothing to report. `implement_tone_sim.py` scenario 15 asserts monotonicity at −45 and −80 and that the default is unchanged.
    - **Tilt (quarter-tone, pure sine).** A sine rather than FM so it is instantly distinguishable against the two FM voices, and because steps are easiest to count on an uncluttered spectrum. 400 Hz is level — genuinely level since the tilt axis became the implement's floor plane rather than a diagonal across it (see `implementFlags` below); the scale's code did not change but its *meaning* did, and it was previously reporting level at an angle nothing can enter. ±24 quarter-tone steps reach 200 Hz and 800 Hz at the implement's **real** mechanical stops, which are learned since the last restart (falling back to `IMPL_TILT_FALLBACK_SPAN_DEG` so it is usable on the first lift). **A running extreme is not a mechanical stop, and using it as one was the "first tilt after a load snaps, then it's fine" bug**: while the implement is still travelling outward the running max *is* the current angle, so `tilt/span` is exactly 1.0 and the step pins to ±24 for the whole stroke — measured at a 22-step jump in one tick, then pegged, going sane only once a real stop had been passed. An extreme is promoted to a stop only after the implement retreats `IMPL_TILT_STOP_CONFIRM_DEG` off it, and the newly learned span is swapped into the scale only while within `IMPL_TILT_SPAN_SWAP_DEG` of level — the one place every span agrees on step 0, so the rescale is inaudible; adopting it at angle jumps the readout by however much the fallback over-estimated the real travel (~9 steps on the WL-40). `implement_tone_sim.py` scenario 6b asserts both, and asserts that the old form pegs. The two ends are not equidistant from level, so the map is two-sided about a shared zero. Linear degrees → logarithmic frequency is what makes the steps evenly *perceived*; a linear-Hz map bunches them badly at the bottom. The frequency is one-poled with `IMPL_TILT_GLIDE_TAU`, **never `linspace`d across a block to the new value** — that turns a discrete step into portamento and destroys the countability the scale exists for — and every step change fires a 6 ms notch, which is what makes a fast sweep countable rather than one continuous slide.
    - **The shared gate** fades both tones out ~1 s after the implement stops moving and re-attacks in ~30 ms. There is **no hold timer**: `implementActivity` already folds in the ram's travel *rate*, so a momentary joystick release mid-lift keeps the gate open on its own. The ground tone's gate additionally opens on **closing rate** (`IMPL_GROUND_CLOSING_MPS`), not just on actuation — driving forward into a pile with a motionless bucket is the implement's position changing relative to the ground, and gating purely on joystick input would go silent during exactly the approach the tone exists to report. While the gate fades, the tilt step is **frozen** at its last actuated value, or a bucket settling under gravity re-steps mid-fade and reads as though it were still being commanded. The articulation tone is ducked `IMPL_HYDRO_DUCK_DB` while the gate is open, using the previous callback's gate value (that block runs first) — one buffer of latency on a 4 dB change, i.e. inaudible.
  - **Docking instrument (`DOCK_*` constants, `_dock_*` state)** — the loader alignment tones, gated by `F9` `Ctrl+I`. Two voices for three dimensions: the panned pulse carries lateral on the stereo image and range on its repetition rate, the beat pair carries vertical. `diagnostic/dock_tone_sim.py` replays the gate/phase/lock state machine against a fake clock — run it after touching that block.
    - **Ramp mode reuses all four voices and changes only constants.** `update_dock_target(range, lateral, null_value, mode, acquire, bearing_deg)`. **The mode travels with the values, not on `set_dock_mode`**, because the two arrive on different threads (the F9 keypress vs the 10 Hz listener): a mode change sitting one packet ahead of its own scaling puts 24 Hz/m through a figure the other mode's slope was sized for, which saturates the beat and fires a spurious lock chime — the instrument announcing "aligned" at a moment nothing is. On a mode change `_dock_lock_armed` and `_dock_beat_env` are **reset**, because the arm latch is hysteresis on a quantity whose scale has just changed by an order of magnitude; `dock_tone_sim.py` scenario 13 asserts zero chimes across the switch and asserts the un-reset form fires one. `DOCK_RAMP_LATERAL_FULL_M` is 3.0 against the implement's 1.2 because on a ramp approach you are routinely three metres off centre at fifteen out, and at 1.2 the pan would be pinned hard over through the whole acquire phase — the one phase in which the pulse is the only voice and the pan is carrying everything. `ramp_resolve_sim.lua` scenario 10 now asserts the audio-vs-mod range invariant, which was previously only a comment.
    - **In ramp mode the null channel is LATERAL, not yaw** (`DOCK_RAMP_BEAT_HZ_PER_M`, 2.0). It carried yaw originally, which contradicted this instrument's own reasoning: the implement readout deliberately keeps squareness *off* the continuous channels because "it only matters at the instant of entry", and ramp mode then sonified exactly that while leaving the one axis you must nail to fit between two walls on the pan alone. Reported from the seat as *"the tones don't really let me know where I am side to side"*, which is what an instrument with no null channel on its most important axis sounds like. Lateral now arrives three ways that reinforce: the **pan** says which side, coarsely and spatially; the **beat** says how far off, finely and self-calibrating, chiming on the null; the **tremolo rate** says which side again, categorically — and that last one is the only one of the three that survives on speakers, where a 700 Hz pulse's low-frequency stereo image largely does not. Fast (`DOCK_AM_ABOVE_HZ`) means the centreline is to your **right**; arbitrary, so it is asserted in `dock_tone_sim.py` scenario 12 rather than remembered. The slope sets the lock window as always: 2 Hz/m → chime at 0.25 m, re-arm at 1.25 m, comfortably inside the ~1.2 m of margin a car has in a 2.15 m half-width mouth. Yaw moved to the spoken tap, where the implement readout already puts it. `null_value` is ignored in ramp mode and the pair is driven from `lateral_m` **inside** `update_dock_target`, so there is exactly one lateral figure and the two voices cannot be handed different ones.
    - **The ramp cane tap is two numbers and then only what is wrong.** Cut back hard after the same play-test ("too much verbiage"): it used to open with `Cannon ramp, Large Cannon standard white` on every press — twelve syllables identifying a machine you are already looking at — and then read four facts whether or not any needed acting on. Now the target is named **once, on acquisition**, by the mode announcement (`Ramp alignment, <machine>`, re-fired on a target change and latched under the same rules as `last_dock_mode`, i.e. never cleared by `DOCKCLEAR`); the tap itself is `<offset> <side>, <range> <unit>` with the unit spoken once, and squareness (`RAMP_DOCK_YAW_SAY_DEG`, 8°), clearance and ramp pitch appear **only as bad news**. The word "square" is gone entirely: nothing in this readout confirms that things are fine, because that is what the tones are for.
    - **Ramp mode has two phases, and they answer different QUESTIONS with the same three channels.** Lateral offset and squareness are corrections to a line you are already on; from beside or behind the machine there is no such line, and reading them out there ("four metres right, 123 degrees left") gives an operator nothing to do, because what they need first is simply *where the mouth is*. So outside the approach corridor the pulse becomes a beacon: its rate follows the straight-line distance to the mouth (`hypot` of the signed along-range and the lateral, derived in `update_dock_target` rather than sent, so it cannot disagree with its own terms) and it is panned at the **true bearing to the mouth over the whole circle** — deliberately *not* squeezed into `DOCK_MAX_AZIMUTH_DEG`, which is a front-hemisphere ceiling appropriate to a steering error, when the whole point of this phase is that the mouth can be behind you. The null channel is **held out entirely**, both because the "offset from the centreline" of a line you are not on is most of the width of the machine — nulling it drives you into its flank — and because the pair arriving as you come into the corridor is then itself the "you are lined up on it now" cue. `_ramp_acquire` is latched once per packet in `beamtel.py`'s listener — one authority for the tones and the spoken readout, atomic with the numbers by construction — and is hysteretic (`RAMP_CORRIDOR_ENTER_M`/`EXIT_M`) because the boundary swaps what the pan *means*. Losing the target, a part swap or a vehicle change all reset it to hunting. `dock_readout_sim.py` scenario 17 and `dock_tone_sim.py` scenario 14 assert both halves, including that the old floored range pinned the pulse at its contact rate from twelve metres out.
    - **The hunting phrase names a place, not a correction.** Bearing first then distance (`82 right, 9.9 meters`), plus `wrong side` when you are past the mouth plane, and the lateral/squareness/clearance clauses are dropped outright — the clearance one is actively misleading off the line, since the margin is the mouth's half-width minus your *current* offset and reads as "too narrow by three metres" about a car that fits. The bearing is `atan2(lateral, range) + yaw`, exact rather than approximate, and derived in Python for the same reason the distance is.
    - **The two clauses of the hunting phrase are in different reference frames, so only one of them may use a direction word.** The bearing is measured from the driver's nose; the mouth-plane clause is measured against the ramp. Both are routinely true at once — aimed squarely at an entrance you have already driven past is an ordinary state while hunting — and wording the second one `behind` produced `ahead, 73.9 feet. behind`, which is not contradictory but reads exactly as though it were. `wrong side` cannot be mistaken for a bearing. It also fires on the **sign of the range** rather than on `RAMP_CORRIDOR_MIN_RANGE_M`: a car half a metre short of the mouth plane is in the doorway, and the threshold called that wrong side too. `dock_readout_sim.py` scenario 17 sweeps 280 geometries asserting no utterance ever carries two direction words, and asserts the old wording collides.
    - **It replaces rather than adds.** The scanner block is suppressed outright while the dock gate is open and the articulation tone is ducked by `DOCK_HYDRO_DUCK_DB` (−12, far harder than the implement's −4). Not a mix decision: articulation says what your input *did*, the docking pan says what you *need*, and on a final approach they are the same axis twice — the goal wins. Both read the *previous* callback's `_dock_gate_env` since the dock block runs last; one buffer on a level change is inaudible. The articulation centre-crossing click is untouched, so the frame reference survives.
    - **Phased by range**, so no more than three dimensions are ever live: silent past `DOCK_MAX_RANGE_M`, pulse only in to `DOCK_BEAT_RANGE_M`, pair fading in inside that. The pair has its own envelope rather than sharing the gate, or the acquire phase would be three quiet dimensions instead of two real ones. At four metres the vertical genuinely does not matter and you are still steering; three channels there is how the obstacle detector became something the user never switched on.
    - **Vertical is a beat pair nulling to unison, not a pitch.** Self-calibrating (no reference frequency to learn), the ear resolves a beat far finer than a pitch, and it is texturally unmistakable against the two FM voices and the pure-sine tilt scale. Three things about it are corrections to a first version that failed in listening — it was reported as *"one tone that stutters and raises and lowers in pitch"*, which is precisely what that version produced:
      - **Both partners move, symmetrically about `DOCK_REF_HZ`.** Holding one fixed and sliding the other moves the pair's *average*, and two tones that close fuse into a single pitch percept sitting at that average — so the listener hears a tone gliding, with the beating masked behind it. Symmetric placement nails the centre pitch so the only thing that varies is the beat. Measured: 330.1 Hz centre across the whole error range.
      - **The detune is specified as a beat rate in Hz** (`DOCK_BEAT_HZ_PER_M`, `DOCK_BEAT_MAX_HZ`), not as an interval in cents. Cents makes the audible result a function of `DOCK_REF_HZ`, and the original 200-cent cap was ~40 Hz apart at 330 Hz — far outside the range where beating is heard as beating at all. **Past roughly 15 Hz of separation the percept turns into roughness and then into two separate pitches**, so the cap has to stay under it.
      - **The pair is rendered CENTRE, not summed into the panned pulse.** Two sounds from one point in space fuse into one object. Splitting them is also honest — the vertical null is not a directional quantity — and free, since centre needs no convolution, the same argument the ground and tilt tones already make.
      - The tremolo sign carrier multiplies the **sum**, not one partner: modulating a single tone adds sidebands and muddies the very beat the pair exists to produce.
    - **Beating is signless**, so above-versus-below rides on a tremolo whose *rate* differs (`DOCK_AM_ABOVE_HZ`/`DOCK_AM_BELOW_HZ`), suppressed inside the lock window — a steady unison is the clearest available "stop".
    - **The unison lock chime is an armed latch inside the callback**, like the articulation centre-crossing click: hysteresis (`DOCK_LOCK_CENTS`/`DOCK_LOCK_REARM_CENTS`) on a continuous quantity, fired from the callback so it is sample-accurate and cannot machine-gun while hunting the null. Silence cannot report a null on its own — a smooth tone is also what "nothing to say" sounds like. It is a *descending two-note* figure because every other slot is taken: FM around 900 Hz (compass/cam clicks), a noise burst (articulation centre), single sines near 1 kHz (scanner/coupler). `DOCK_LOCK_WAVEFORM` must be regenerated at **both** build sites, as `HYDRO_CENTER_CLICK_WAVEFORM` is.
    - Only the pulse is user-levelled (`dock_tone_dbfs`); the pair sits at a fixed offset from it, or a mix exists in which the null cue is inaudible under the range cue.
  - **Terrain sonification scanner (`SCAN_*` constants, `render_scan`)** — a one-shot picture of the landscape rather than a warning about it, fired by `F9` `Space` while the world is live and gated by `scan_tones_enabled`. The obstacle detector says what you are about to hit and the docking instrument says what you are lining up with; neither tells you that you are in a valley, on a ridge, or beside a lake. `diagnostic/terrain_scan_sim.py` (`python diagnostic/terrain_scan_sim.py`) asserts every property below — run it after touching any of it.
    - **The whole scan is pre-rendered on the LISTENER thread, not synthesized in the callback**, and that is the load-bearing decision. Six hundred overlapping grains evaluated per 512-frame block in Python would blow the callback's budget and take *every other voice in the mod* down with it, not just this feature. There is nothing to gain by deferring, either: the scan's length is fixed and its content is fully determined the moment the packet lands. The callback does nothing but `bufL += self._scan_buf[pos:pos+frames, 0]` and advance a cursor. Being pure is also what lets the sim assert on the instrument with no stream, no device and no clock — every other audio sim in this project needs a fake clock; this one needs nothing. It reads the buffer **before** the cursor and clamps, because `play_scan` can swap them from another thread between the two reads and a new buffer indexed by an old position is the one way that block can throw. Measured at ~35 ms to render a full 600-sample scan.
    - **Three mappings on three different axes, so none has to share a channel.** PITCH is elevation, TIME is distance, PAN is bearing. Level explicitly carries *nothing* — the user asked for time rather than volume to encode distance, and doubling it up on level as well would only make the far half of every scan quiet for no added information.
    - **Pythagorean, not equal temperament, and level ground is middle C.** A landscape is full of repeated intervals — a hillside at a steady grade lands on the same step over and over — and a 12-TET fifth is 2 cents narrow, which at this register beats at about 2 Hz. Pure 3:2 and 4:3 do not beat at all, so a constant slope reads as a stable chord instead of a wobble. `SCAN_PYTHAGOREAN_RATIOS` is the chain-of-fifths chromatic; the *quantization grid* is 12 equal steps per octave (which keeps the readout monotonic in elevation, the property that actually matters) while the *sounded* pitch of each step is Pythagorean. Fixed `SCAN_M_PER_OCTAVE` rather than auto-scaling each scan to the range it happens to find: auto-scaling would always use the full pitch range, but then a pitch would mean nothing on its own and flat ground would sound dramatic. Clamped rather than wrapped at `SCAN_OCTAVE_CLAMP` — a wrapped octave reports a peak as a pit. Sim scenario 2 asserts every producible pitch is a table degree **and** asserts an equal-tempered table fails the same check.
    - **The reference ping is not decoration.** An absolute-pitch elevation readout is unusable without a reference immediately beforehand, because the listener has nothing to judge "level" against. Middle C, centre, at the head of every scan, at a **fixed** level: the cloud is normalised and the ping is added *after*, or the calibration tone's loudness would become a function of the landscape it is calibrating.
    - **Water is the same pitch rule on a different timbre.** The depth rides on the **water bed**, not the surface, so "deeper is lower" falls out of the one elevation map with no second rule and the water stays pitch-continuous with the shore it meets. What marks it as water is the underscore field and timbre alone — `dz_0.0` is still definitively water, rendered as a 1/k saw against the terrain grain's near-sine. This keeps a zero-depth shoreline cell unmistakable even when its bed elevation has exactly the same pitch as adjacent dry ground.
    - **Onset jitter (`SCAN_TIME_JITTER_MS`) is required, not cosmetic.** Without it every spoke of a given ring fires on the same sample at the same pitch, so flat ground sums perfectly coherently and comes out as twenty-five rhythmic pulses — the sample rings themselves become audible as a beat, which is the exact opposite of the melded granular surface the feature exists to produce. It **must stay under half a ring's spacing in time**, or two rings can swap and time-is-distance stops being true; at `SCAN_DURATION_S` of 2.0 over the mod's 25 rings that spacing is 83 ms, so the ceiling is ~41 ms. **Shortening the scan tightens this**, which is why sim scenario 11 reads the ring count out of the Lua and asserts the margin rather than leaving it to be rediscovered. Scenario 5 separately asserts a farther sample always starts later.
    - **The cloud is normalised, so headroom is structural rather than a tuned hope.** Six hundred grains summing sixteen deep have no useful analytic peak bound. Nothing here may rely on the callback's final clip to stay clean — that clip catches the sum of every voice in the mod, and a scan arriving already at the ceiling would make every other cue distort. Only the cloud is user-levelled (`scan_tone_dbfs`); water and the object pings sit at fixed *offsets* from it, or a mix exists in which the terrain bed is inaudible under the pings.
    - **A missing sample is silence, never zero.** Zero is level ground, so rendering an off-the-map sample as 0.0 would report a flat plain where the world simply ends — a lie the listener has no way to catch. The mod sends `~` and `render_scan` skips it; sim scenario 9 asserts the naive zero-fill form produces a plateau.
    - Every grain fades in and out with a raised cosine (`SCAN_GRAIN_FADE_MS`), and a scan landing while one is still playing **crossfades** over it (`SCAN_CROSSFADE_MS`) rather than cutting — a double tap of the key is an ordinary thing to do and a hard cut mid-cloud is a click at full level.

- **secretstore.py** — At-rest protection for the secrets in `beamtel_config.json`, today the two AI describer API keys. Windows DPAPI (`CryptProtectData`) via ctypes, stored as `dpapi:v1:<base64>`.
  - **DPAPI rather than a keyring or a passphrase, because it is the only store that needs no key of our own.** The ciphertext is tied to the Windows *user account*, so beamtel needs no first-run prompt and no secret of its own to unseal it, while a copied config file, a synced profile or a backup carries nothing usable. Scope is deliberately the user and not the machine (no `CRYPTPROTECT_LOCAL_MACHINE`): another account on the same PC must not be able to read the key. This is not secrecy from code already running as the user — anything with that privilege can call `CryptUnprotectData` too. It is the guarantee a browser gives a saved password, and it is the one that matters here: the key stops being visible in a file people paste into bug reports.
  - **Which settings are secrets is decided by NAME, and there is exactly one list.** `SECRET_NAME_PARTS` is matched as a substring (the names are compound, `ai_describer_openai_api_key`) so a provider added later is covered the day it is added rather than the day someone notices. `mcp_server.py`'s `get_config` masking reads that same list rather than carrying its own copy — two lists would drift on the first new provider, and the failure would be silent in the direction that leaks.
  - **A failed *seal* falls back to plaintext; a failed *unseal* does not fall back to anything.** The two are not symmetric. Refusing to store a key because DPAPI was unreachable turns hardening into a feature outage, and the caller has just validated that key against a live endpoint. But a protected value that will not decrypt is a fact, and `unprotect` returns **None** for it — distinct from `""` — because a blob from another Windows account (a restored profile, a copied config) is not "no key configured": the fix is to enter it again, and announcing "no API key set" would send the user hunting for a key that is plainly there in the file.
  - **Migration is on LOAD, in both halves, and writes back.** `migrate_config` mirrors `speech.migrate_config` and is called from the same place in `beamtel.py`'s and `configurator.py`'s `load_config`, so an existing install is sealed on the next run rather than only when the user next re-enters a key they have no reason to touch again. The configurator writes it back there too — a config that is only ever opened and closed would otherwise stay in the clear forever. Idempotent: an already-marked value is skipped, so a load costs nothing after the first.
  - **The key is unsealed at the point of use, never into `ai_describer_settings`.** `_ai_describe_worker` unseals into its own frame; the settings dict, which is what state dumps and the MCP surface see, holds only the sealed form.
- **nvda_ws_speaker.py** — aiohttp WebSocket server on port 8765. Bridges UI events to speech output.
- **mcp_server.py** — An MCP server so an AI agent can drive and test the mod: execute Lua in the game, place vehicles into known geometry, read live state, trigger any F9 command, and assert on what the mod announced. Gated by `mcp_server_enabled` (default **off**) and bound to `127.0.0.1` only. `get_config` **masks every secret-named setting** (`<redacted>` when set, empty when unset, off `secretstore.SECRET_NAME_PARTS`): its output lands in agent transcripts and logs, so a key readable through it is a key that has left the machine — and it is masked even now that the stored value is a DPAPI blob, because that blob is still the credential in transportable form. Whether a key is *set* is left visible, because that is the fact an agent legitimately needs (it is why the describer refuses to run) and it gives away nothing. `diagnostic/mcp_server_sim.py` stands the server up on a spare port and drives it over real HTTP — run it after touching any of this.
  - **Start beamtel BEFORE Claude Code.** MCP tools are discovered once, when the client connects and calls `tools/list`; a server that was not listening at that moment simply is not there, and the symptom is not an error but an *absence* — the agent quietly falls back to asking the user to do everything by hand, which is the exact failure this feature exists to remove. `mcp_server_enabled` is also read once in `_run_engine`, so flipping the flag needs a beamtel restart either way. If the tools are missing mid-session, `/mcp` inspects and reconnects the server; that is cheaper than restarting the conversation. `.mcp.json` is committed at the repo root, so with the flag **off** — the default — every session in this repo shows one failed server. That is the accepted cost of not hiding the config somewhere ungitted, and it doubles as a reminder that the flag is off.
  - **It exists because half of this mod cannot be tested any other way.** The `diagnostic/` simulators replay a state machine against a fake clock, which catches wording and sign errors; they cannot catch a resolver landing on the wrong node, which produces confident, plausible numbers. That half has until now cost the user a drive across a level per test.
  - **The transport is loopback HTTP, not stdio, and that is forced rather than preferred.** beamtel is built `--windows-uac-admin`, so it runs elevated while the agent does not — a stdio server could not be this process. And it has to *be* this process: `state_lock`-guarded globals live here, and port 4466 is exclusively bound by `console_listener`, so a separate process could never listen for a console reply. Hence an aiohttp thread inside beamtel, shaped exactly like `nvda_ws_speaker.start_server_in_thread`.
  - **The `mcp` SDK is deliberately not a dependency.** The Nuitka onefile build fights a 25 MB release limit (h5py was already dropped for it) and `mcp`+starlette+uvicorn is a large new tree. aiohttp is already here, and MCP over streamable HTTP is JSON-RPC 2.0 with five methods. Two protocol details are load-bearing and are asserted rather than remembered: a **notification must be answered with 202 and an empty body** (get it wrong and the client hangs on the handshake, with nothing to see), and **`GET /mcp` returns 405**, which is how a server says it offers no server-initiated stream. No `Mcp-Session-Id` is issued — there is no session state, and not issuing one deletes a class of bugs.
  - **A tool failure is `isError`, never a JSON-RPC error.** JSON-RPC errors are for protocol faults (unknown method, unknown tool, bad JSON); "the game is not running" is something the model has to *see and reason about*, so it comes back as content.
  - **EXEC correlation is the hard part, because `consoleAccessible.lua` has no request IDs** — ordering plus the `EXECEND` sentinel is all there is. `_exec_lock` keeps exactly one EXEC outstanding, which is what makes ordering a sound basis. `register_console_tap` installs `console_tap` into `console_listener`, and the tap **consumes** the records it owns: `on_console_message` speaks any single-line result aloud, so without suppression every agent exec would talk over the user mid-test. `LOG` records are copied but **never** consumed — they arrive unsolicited and belong to the GUI's log pane. The tap is `None` unless the server started, so the cost when it is off is one identity comparison per datagram.
  - **Reassembly must concatenate, not newline-join.** `emitChunks` repeats its prefix on *every* chunk, so a long value arrives as several `OUT|= ` records that are one string. Bare `OUT|` is genuinely ambiguous — a continuation of a long print line looks exactly like the next print line — so a chunk counts as a continuation when the previous one filled the datagram or already ended in a newline, and `verbose` always exposes the raw records for when that heuristic is wrong.
  - **The speech tap is a second buffer, not `SPEECH_BUFFER`.** That one holds only what the user can replay, and most mod output passes `exclude_from_buffer=True` — so it is not a record of what the mod said. `SPEECH_TAP` records every `say()` call, **including ones suppressed during loading** (flagged `spoken=False`), because "the mod correctly stayed quiet" is as worth asserting on as what it announced. It records at the point of utterance, so it captures the final text after the loading check and after the `_speech_protected_until` interrupt demotion. Cursors are **sequence numbers, not timestamps**: a reader polling for what changed needs exactly-once semantics, and `time.time()` ties and skews. `dropped` says history was lost rather than letting an empty list mean two different things.
  - **F9 commands are injected in-process.** `_on_next_key_press` duck-types its event — only `.event_type` and `.name`, with modifiers from `_capture_mods` — so `_mcp_press_command` drives any command with no OS key injection and without BeamNG having focus. `press_command` returns the speech produced during the call, making one round trip act *and* assert.
  - **One tool per UDP port would be forty tools.** `send_command` takes a module name resolved against a port map (a typo is then an error rather than a datagram into the void), and `lua_exec` reaches every Lua diagnostic that has no UDP verb at all. The set is ~16 on purpose.
  - **`camera_control` and `screenshot` are the eyes, and they are one instrument in two halves.** Every other tool reads numbers, and the failure this server exists to catch — a resolver landing on the wrong node — produces numbers that are confident and plausible. Looking is how you disprove one. The pairing is the point: place the eye, then shoot.
    - **Camera control is composed GE Lua through `exec_console`, not a new verb on `cameraInfo.lua`'s 4451, and `bng_mod/` does not change.** Readback is the requirement — a set that answers with the resulting pose is self-verifying in one round trip — and `exec_console` is the only channel that returns a value synchronously; 4451 is fire-and-forget, and giving 4450 a reply format for agent-only queries would be new wire protocol on a live junction. A new *listener* would additionally owe the `setsockname`-return / `onExtensionUnloaded` / `retryCmdBind` triple that `vehicle_geometry_sim.lua` scenario 12 polices. And this is precisely what `_t_diag` already is: a curated wrapper over Lua the agent could have typed, leaving `lua_exec` the universal surface. `cameraInfo.lua` stays read-only telemetry.
    - **Two angle conventions collide, and both are DERIVED from the game source rather than measured**, because each is the exact algebraic inverse of the other. `core_camera.setFreeCameraYawPitchRollDeg` builds its forward as `(sin y·cos p, cos y·cos p, −sin p)` (`core/camera.lua:1105`), so its yaw is `atan2(f.x, f.y)` and its pitch is positive-**down**; `cameraInfo.lua:253/258` reports yaw as `atan2(−f.x, −f.y)` and pitch positive-**up**. Since `atan2(−x, −y) ≡ atan2(x, y) ± 180`, the yaws differ by exactly 180° with the same sign and the pitches by a sign alone — hence `CAM_YAW_OFFSET_DEG = 180.0` and a single negation, not a constant somebody had to fly around and calibrate. The tool speaks the **mod's** convention in both directions and derives its readback from `getForward()` the way `cameraInfo.lua` does, rather than from `core_camera.getYawPitchRoll()`, which speaks the engine's — so `get` can never disagree with the 4450 feed or the `Alt+H` readout about the same camera. A sign error here is invisible from the seat: the camera tilts the wrong way and every readout still agrees with itself, which is why `mcp_server_sim.py` scenarios 17a–17e round-trip the whole sphere **and** assert what the un-offset and un-negated forms would have answered.
    - **`setPosition` and `setFreeCameraYawPitchRollDeg` both early-return unless the free camera is already active** (`core/camera.lua:1088`, `:1573`), so a `place` that skipped that step would report success and move nothing. Every `place` chunk enters it first — via `commands.setFreeCamera()` rather than a bare `setByName(0,'free')`, because that seeds the free cam at the current pos/rot (`commands.lua:38`) and there is no visible jump. `is_free` in the returned readback is therefore *proof* the placement landed, not an inference from the absence of an error.
    - **`rel_right_m` is positive to the vehicle's RIGHT, deliberately the mirror of the mod-wide positive-is-LEFT rule.** That rule governs bearings *reported to a driver*; this is a placement parameter literally named "right", and building it as `up:cross(fwd)` to honour a convention it is not part of would make every relative shot land on the wrong flank. Orbit elevation is measured off the **world** horizontal on the vehicle's **flattened** heading, so "30° up at 10 m" means the same thing on a machine parked nose-down a bank as on one standing level.
    - **A composed chunk must fit one datagram.** `consoleAccessible` receives `EXEC|<ctx>|<code>` as a single UDP packet, so the action and the readback are two round trips rather than one concatenated chunk, and the length is checked before sending. No chunk contains a percent sign — `n360()` replaces the modulo operator — because these strings share a file with `%`-formatting throughout. A camera *name* is validated as an identifier rather than escaped, which keeps quotes out of the chunk entirely.
    - **Argument validation runs before `_require_world()`.** A typo'd action is a caller error and must name the valid ones whatever the game is doing; told "the game may be closed" instead, the agent goes and debugs the game. (This is otherwise `_require_world`'s first caller — it had been defined and used by nothing.)
    - **A minimized BeamNG renders NOTHING, and a plain monitor grab of it returns the desktop.** Found on the first live run: the game parks its window at `-32000, -32000` and renames itself `BeamNG.drive - ... - background`, so `capture_primary_monitor()` — correct for the AI Describer, which fires from a keypress while the user is playing and the game fills the display — handed back a screenshot of the user's desktop, icons and all. That is the exact failure mode this server exists to catch: silent, and entirely plausible until you look at it. So `screenshot` defaults to **raising the game window** (`focus_game`), grabbing the window's own rectangle rather than the monitor, and putting the previously focused window back afterwards; `capture_scene_png` keeps `focus_game=False` so the describer's behaviour is byte-for-byte what it was, since raising a window under someone mid-corner is a real cost and buys that caller nothing. `SetForegroundWindow` is refused for a process that does not already own the foreground — and beamtel runs elevated while the game does not — so the input queues are attached first, which is the documented way to be allowed; every step is best-effort, because a refusal must degrade to a worse screenshot rather than an exception. **What was actually captured rides back in the result**, and `_window_region` rejects the `-32000` park explicitly: without that the tool would report success while returning the desktop, which is the only outcome here worse than failing.
    - **`screenshot` shares the AI Describer's capture path and sends the image nowhere.** `capture_scene_png()` is factored out of `_ai_describe_worker` in `beamtel.py` so the HIDE → settle → grab → SHOW sequence, and the 0.2 s constant, exist once; the tool writes the PNG to a caller-named directory (the agent's own working directory) and returns an absolute path to read. Names are stamped to the **millisecond**, because a before/after pair is what the tool is mostly for and two shots in one second must not collide.
    - **The capture lock is NOT the describer's busy flag.** Both callers toggle the game UI, and two overlapping sequences race — the first one's `SHOW` lands mid-grab of the second, so the shot that asked for a clean world gets the HUD back in it. `_describer_busy` answers a different question (a double-press of `F10` `Space` should buzz rather than queue a second AI request) and must not refuse an agent screenshot, nor be consumed by one; hence a separate `_capture_lock` held across the whole sequence.
    - **Writing an arbitrary path from an elevated process is not a new class of exposure** — `lua_exec` already runs arbitrary Lua there — so the mitigation is unchanged and unchanged on purpose: the flag defaults off, the bind is loopback, and a non-loopback `Origin` is refused. A path allowlist would defeat the tool's only real use.
  - **Arbitrary Lua in an elevated process is a real local exposure**, which is why the flag defaults off, the bind is loopback, and an `Origin` header from anywhere but loopback is refused. There is no auth token; the mitigation is that the port does not exist unless the user turns it on.
- **updater.py** — The GitHub-only auto-updater. One release asset (`build.py`'s `BUNDLE_NAME`), one hand-maintained `APP_VERSION`, and a two-phase install that survives the restart the self-replacement forces.
  - **The running exe cannot replace itself, so the swap happens after we exit.** Nuitka builds beamtel onefile and Windows holds the image open for the life of the process, so `apply_and_restart` writes a detached `.cmd` that polls `tasklist` until the program is gone, then robocopies the staged tree over the program directory and starts the new exe. It waits on the **image name**, not on our own PID: a onefile build is two processes -- the bootstrap and the payload it spawns, both called `beamtel.exe` -- and `os.getpid()` is only the payload, so a PID wait releases the copy while the bootstrap still holds the image and the cache open. It also removes the `.appdata` directory first — that is Nuitka's onefile cache (`--onefile-tempdir-spec={PROGRAM_DIR}/.appdata`, `--onefile-cache-mode=cached`), a **fixed** name beside the exe holding the *old* build's unpacked payload, and the only moment it is safe to delete is the one the helper runs in. The helper is detached because a child in our own process group would die with us before it had done anything -- but `DETACHED_PROCESS` makes `CREATE_NO_WINDOW` a **no-op** (the two are mutually exclusive), and beamtel is built `--windows-console-mode=disable`, so it has neither a console nor usable standard handles to hand down. A detached `cmd` with neither allocates a console of its own, which is the stray window an update used to leave behind; explicit `DEVNULL` handles are what actually suppress it. **And every step after the copy is logged and VERIFIED**, because `start` is asynchronous and reports almost nothing: the old helper's last line was written *before* the launch attempt, so a restart that silently never happened left no evidence anywhere. Every external command is fully qualified to `%SystemRoot%\System32` for the same class of reason -- a `find` from some other toolchain on PATH does not take `/I` and breaks the wait loop with nothing in the log.
  - **The program directory is `sys.argv[0]`'s, never `sys.executable`'s.** beamtel's own `BASE_DIR` is built from `sys.executable`, which under a onefile build points into the temp extraction directory — an update written there lands in a folder Windows deletes. `program_dir()` therefore mirrors `configurator._get_program_dir()`, which is also the directory `install_mod_interactive` reads the mod zip out of, so the two halves of the install cannot disagree about where the program lives.
  - **The pending flag is written only AFTER the download validates and stages.** `pending_update_version` is a promise to the next run that there is a new mod zip beside the exe waiting to be installed; a promise made at the "yes, update" answer could not be kept by a download that then failed, and the next start would offer to install an update that was never applied. The same ordering argument runs the other way at the end: a failed `apply_and_restart` clears it again.
  - **The launch is GATED, not reordered.** The game launch sits in the middle of `_run_engine`, after speech, audio and the UI bridge, and moving it would change what is initialised by the time the game starts. So `LAUNCH_GATE` blocks just that block while everything above it proceeds under the dialog, and `LAUNCH_ALLOWED` is read once immediately after the wait — which is why `deny()` fires at the point of no return, immediately before the helper is spawned, and not at the user's "yes": denying earlier would strand a user whose download then failed or who cancelled it, because the engine reads the decision once and never looks again. The wait has a timeout, and the timeout is the failure path: a flow that never answers degrades to today's behaviour rather than to a game that never starts.
  - **A failed check is silent and a failed update is loud.** `check_latest` answers `None` for every failure it can have — offline, rate limited, malformed JSON, a release with no matching asset — because a check that cannot complete must never hold up a startup, still less the game behind it. Once the user has said yes, the opposite applies: every failure reports itself, because they are now waiting for something.
  - **The bundle is validated before anything is staged, and the required members are the test.** A truncated download and an HTML error page saved under a `.zip` name are both plausible, and everything after this point overwrites the user's install: `zipfile.testzip()` plus the presence of `beamtel.exe` and `bng_screenreader_mod.zip` is what separates a release asset from a file that merely arrived. The zip-slip guard in `stage` is there for the same reason and not because the archive is untrusted — this is the one place in the project that writes remote-named paths into the program directory.
  - **`ASSET_NAME` must equal `build.py`'s `BUNDLE_NAME`, and `APP_VERSION` must equal the tag.** Both are one contract seen from two ends with no import that could tie them together. The tag half is checked in `release.yml` before the build, because a drifted `APP_VERSION` does not fail loudly: every client simply concludes it is already up to date and the release reaches nobody.
  - **The manual button's gate decides nothing.** Startup and the Main-tab button run the same flow; by the time the button can be pressed the deferred launch has long since been released, so its gate is `NullGate` rather than an already-set one — an inert gate cannot fire a second launch. `manual` additionally makes the flow ignore the config gate and report the up-to-date case, which the startup check deliberately does not.
  - **Phase two reuses `install_mod_interactive` rather than copying it**, so the post-update install and the Install Mod button are the same act, including the version comparison and the freeroam-layout cleanup. It gained a boolean return for the log only; every one of its early exits has already told the user what went wrong, so the caller must not report anything a second time. The flag is cleared whichever way the user answers — it records that an update was applied and the mod has not been *offered* yet, and it has now been offered — and declining does not withhold the game.
  - **Which mod zip is newer is decided by a STAMPED version, never by file mtime.** `build.py`'s `package_mod()` writes `bnvda_mod_version.json` (`MOD_VERSION_MEMBER`) into the zip and `config_ui._mod_zip_version` reads it back. An mtime cannot answer this question, because nothing in the path treats it as data about the build: `shutil.copy2` -- the installer itself -- *preserves* it, so an installed zip carries whatever some other machine's clock said when it was built; `zipfile.extractall`, which is how `stage()` unpacks a release, does not restore it at all and invents "now"; and robocopy forwards whatever it is handed. Comparing those compares clocks across machines, which is how a freshly downloaded release came to announce itself as older than the copy it was replacing. An **unstamped** installed zip is treated as older, which is correct -- it predates stamping -- and a byte-identical pair short-circuits to "already installed" before any version is read. Where neither side carries a stamp the dialog says so rather than inventing a direction.
  - **The dialogs say the minimum and carry no links.** The offer is the two version numbers and the question, and it ends there: the release notes are commit messages rather than a maintained changelog, so `Release` no longer carries `body` at all, and neither the restart nor the mod prompt after it needs announcing in advance because each announces itself when it happens. The releases-page URL is gone from the failure boxes for a mechanical reason -- getting a link out of a message box with a screen reader is possible but painful, so a URL there is a cost with no payoff. Accessible is not the same as chatty.
  - **`APP_VERSION` is in the window title.** `BeamTelFrame` reads it for its title bar, so the running version is something a screen reader announces on focus rather than something you go looking for -- which is what makes "did that update actually land?" answerable after the self-replacement restart. It is appended, so `_find_game_window`'s `startswith` prefix match is untouched, and a failed import falls back to the bare title: a window that cannot name itself beats a window that will not open.
