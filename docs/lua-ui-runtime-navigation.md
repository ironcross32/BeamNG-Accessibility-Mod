# Lua/JS: UI Runtime: Held-navigation coalescing

Part of `ui/ui-vue/mods/bnvda/bnvdaRuntime.js`. The overview, the poll/event model and the shared text helpers are in `lua-ui-runtime.md`.

How a held direction is told apart from a tap, and how a sweep announces only where it lands. The radial menu opts out of all of this; see `lua-ui-runtime-radial.md`. Run `diagnostic/navburst_sim.js` after touching it.

- **Held-navigation coalescing** — holding a direction to sweep a list, slider or dropdown otherwise speaks every item flown past. `scheduleSpeak` instead announces the first item, stays silent through the run, and speaks the landing once motion stops.
  - **A tap and a hold are told apart by the KEY, not by the clock.** `menu.json` binds `onDown` *and* `onUp` of every D-pad direction to the `UINavigation` hook, and a held direction repeats inside the UI (crossfire: 500 ms, then every 200) with no further press. So `trackNavigationInput` records both edges, and `navBurstCapture` reads them: an announcement that follows a press is deliberate and is spoken at once, however fast the presses come; one that arrives under a held key with no press of its own is a repeat and is coalesced; the release flushes the landing after `NAV_RELEASE_DRAIN_MS` (40).
  - **It used to be cadence alone, because the hold tracking was dead.** `NAV_ACTION_RE` matched `up`/`down`/`left`/`right`, and the engine's names are `focus_u`/`focus_d`/`focus_l`/`focus_r` — so nothing was ever recorded as held, on any screen. The earlier note here that "the part selector reports no key state" was that bug misread as a property of the screen. With cadence deciding, any two moves inside `NAV_BURST_GAP_MS` were a sweep: seven taps 220 ms apart spoke the first row, nothing for the next five, and the seventh 400 ms after it landed (measured), and a hold's landing came 224 ms after the release.
  - **One press answers ONE announcement** (`fresh` is a count, consumed per utterance, expiring after `NAV_PRESS_FRESH_MS`). A second utterance from the same press — a state change the poll notices a tick later — is held until release rather than cutting the first off.
  - **A stick is one press per crossing.** `focus_ud`/`focus_lr` report continuously, so a deflected stick would otherwise mark every repeat as deliberate; `NAV_AXIS_PRESS`/`NAV_AXIS_RELEASE` are a hysteresis pair for the same reason. A button that presses again while recorded as down has lost its release and *is* a new press, unless it is the AngularJS echo of the same edge inside `NAV_EDGE_ECHO_MS`. Window blur clears the held set.
  - **Landing text that arrives after the release must not re-arm the timer.** A slider's value has no focus event, so the release-kicked poll is what reads the final value; re-arming there is what used to push the landing out by a whole settle delay after the key was already up.
  - **Held with no movement for `NAV_HOLD_STALE_MS` also flushes**, which is what announces the last row when a sweep runs into the end of a list with the key still down.
  - The cadence path below is kept only for movement with no key state behind it (a build that reports none, or a change nothing was pressed for). Its settle delay is derived from the observed repeat cadence (clamped `NAV_SETTLE_MIN_MS`–`NAV_SETTLE_MAX_MS`, i.e. 90 ms–`NAV_BURST_GAP_MS`) rather than a fixed idle debounce, because a ~500 ms wait makes the UI feel sluggish. **`NAV_SETTLE_MAX_MS` must stay >= the engine's controller repeat interval** (~240 ms on the part selector): a lower ceiling makes the settle timer fire in the gap between two repeats, which flushes on every item — defeating the coalescing entirely while still charging its full delay to every announcement. It is tied to `NAV_BURST_GAP_MS` because a gap that large already starts a new burst by definition. Only `P.KEYBOARD`/`P.CONTROLLER` are captured; `P.SYSTEM` (toasts, damage, camera, cruise control) must never be, or a sweep will delay or drop it. Gated by `ui_nav_hold_suppression`. `diagnostic/navburst_sim.js` (`node diagnostic/navburst_sim.js`) replays the state machine against a fake clock — run it after touching that logic. It **lifts the functions out of the source by name**: the previous version carried its own copy and called `press('down')`, which is exactly how it kept passing while the real matcher never recognised `focus_d`. Scenario 3 runs the same seven taps with and without key state and asserts the second form still coalesces, so the first cannot pass by accident.
