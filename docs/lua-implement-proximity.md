# Lua: `implementProximity.lua`

- **`lua/ge/extensions/implementProximity.lua`** — What the loader's bucket or forks are about to run into. Port 4469→4470. Deliberately does **not** handle the ground: that is the vehicle VM's job (see `implementFlags` below), because that VM owns the implement node set and has both `obj:getSurfaceHeightBelow` and `obj:castRayStatic`. This extension covers only what the vehicle VM cannot see — other spawned objects. In BeamNG most "props" (cones, barriers, haybales, pallets) *are* spawned vehicle objects, so `be:getObject` covers them; map-placed `TSStatic` clutter is enumerable (`scenetree.findClassObjects("TSStatic")`) but is deliberately **not** used here — on a stock map that is thousands of trees and building shells, so it shows up only in the vehicle-VM ground raycast.
  - **Node cloud for contact, oriented box for containment.** These answer different questions and neither substitutes for the other. When a part breaks off a vehicle its nodes stay part of the *same object*, so a detached bumper lying in the dirt is invisible to that vehicle's bounding box but perfectly visible in its node cloud — hence the strided node-to-node narrow phase for "about to hit something". The box is used for the opposite question, "are the tines *inside* the vehicle's volume without touching it", i.e. under the frame ready to lift. Box overlap alone false-positives constantly, because a solid box also contains the air beside a low car's wheels, so containment additionally requires ≥2 implement points inside and the implement centroid *below* the box's mid-height. It deliberately does **not** also require a nearest-approach greater than `CONTACT_M`: that clause made "under it" and "touching it" mutually exclusive, so tines resting against the underside of a load — the state immediately before a lift, and the one an operator most needs confirmed — reported contact and dropped the "under" entirely. `contact` is its own field on the `NEAR:` line, so the two are independent. **That count, and the slam gate's, are over the five sample cids — never the full `implCids` cloud.** `INSIDE_MIN_PTS`/`SLAM_OVER_MIN_PTS` are counts, not fractions, so feeding them ~120 nodes quietly redefines "over it" as "about 2% of the bucket is over it", and since losing the footprint takes *every* point the state then cannot be dropped again either — `COMMITTED` fired beside the target. The narrow-phase nearest-approach sweep keeps the full cloud, because that is the tier that sees a part which has broken off. The box is built from `getDirectionVector()`/`getDirectionVectorUp()`/cross and the extents measured from the node cloud — **not** `be:getObjectOOBBHalfExtentsXYZ` against world axes, which for a car parked at any angle describes a box it isn't in.
  - **The cid list is pushed, not pulled.** `796F6C6F313035.lua` resolves the implement (it has `v.data.nodes` and `partOrigin`) and hands the result over with `obj:queueGameEngineLua` on spawn and after every reset. Re-deriving the name matching here would be two copies of one fragile thing, and because the resolution only ever changes when it re-runs, the newest push is always authoritative — there is no window in which this extension could hold cids belonging to a part that is no longer fitted. The cache is still dropped on `onVehicleSwitched`/`onVehicleResetted` and the extension stays quiet until the next push, because stale cids return confident *wrong* world positions rather than an error.
  - **Pushes are stored per vehicle (`implByVeh`) and only the player's is promoted.** They used to land straight in the shared globals whichever vehicle sent them, which was survivable while each pushed once (last spawn quietly won) but not once the push became a heartbeat — two claimants then take it in turns every few seconds. The vehicle-side match is pure name matching against `IMPL_PART_WORDS` (`bucket`, `fork`, `blade`, `scoop`, `plow`), which a bucket *seat*, a wiper *blade* or a hood *scoop* can satisfy, so an ordinary car parked beside the loader could take ownership and flip the scanner's origin between the cutting edge and the reference node on a 4 s cycle. Nothing logged it, because the re-push is idempotent and only speaks when the payload changes.
  - **`getImplementFrame`'s hemisphere test guards both operands.** The lateral baseline was length-checked but `veh` was not, and it is the other half of the same sign test — flattening the machine heading collapses it to numerical residue when the machine pitches near vertical (nose into a pile, jacked on its own bucket), and the test then picks a side per tick. It does not degrade gracefully: negating `fwd` negates the derived left vector, so the bearing *mirrors*. It now holds `lastGoodFwd` instead of guessing.
  - Active by default rather than keybind-toggled: with no implement resolved a tick costs one `getPlayerVehicle` and an early return, and an ON-on-startup handshake would break when BeamNG is launched after beamtel.
  - **The docking readout (`DOCK:` line, `DOCK_ON`/`DOCK_OFF`/`BANDNEXT`/`BANDPREV`/`BANDAUTO`)** is the alignment instrument, separate from the proximity speech above and off by default — it is a mode you enter to line something up, not ambient awareness, and it is meaningless with no implement fitted. Three numbers plus a reference: lateral and vertical are what you steer and lift with, range says how long you have to get them right. **Yaw is reported but is deliberately not a fourth continuous channel** — it only matters at the instant of entry, and sonifying a fourth axis is exactly how the obstacle detector became unusable.
  - **It is not a pocket finder — the reference band is *selected*, not derived.** Lifting and ramming want different bands out of identical geometry: forks into a pallet want the void, forks through a window want the glass, a bucket into a flank wants the sill. `vehicleGeometry.bands()` collapses the histogram into alternating GAP/SOLID runs and `autoSelectBand` picks one (lowest real void for forks, tallest solid face for a bucket), with a key to override. Selecting rather than deriving is also what makes the reference *announceable*: with a derived pocket the operator could never tell what the readout was measuring against.
  - **Auto-selection needs to know a bucket from forks, which is otherwise Python's job.** Only the *choice* is made in Lua (`implementIsFork`); the spoken naming stays in `beamtel.py`'s `_implement_word`. One copy of each: Lua picks, Python speaks.
  - **A manual band pick is scoped to one target and one implement.** `resolveBand` drops back to auto when the target id changes, and every cid-cache invalidation clears it too — an index against a pallet means nothing against the car you have since turned toward. Cycling clamps rather than wraps, and the clamp is written back, or holding the key past the end runs the index away and the same number of presses is needed to get back into range.
  - `vertical` is `bandMid - implementEdge.z`, so **positive means raise**; `lateral` is positive-LEFT, matching the scanner bearing and the compass clicks. `diagnostic/dock_readout_sim.py` asserts both signs, because a sign error here reads as perfectly plausible speech and this project has already lost time to one.
  - **The slam gate (`SLAM:` line)** is the destruction case, and it is three discrete hysteretic states rather than a continuous readout because nulling is the wrong *shape* for it — an overhead drop wants to be decisively above, then over, then commit, not to drive an error to zero. `overBox` is the plan-view half of the existing containment test with the `implCentre.z < boxMidZ` clause dropped; the height half is the clearance test instead. **It needs no new geometry** — the five cids are already resolved and pushed, and the mode only changes which of them drive the test.
    - Both thresholds are asymmetric on purpose: clearance uses `SLAM_CLEAR_ENTER_M`/`SLAM_CLEAR_EXIT_M`, and the footprint takes `SLAM_OVER_MIN_PTS` to claim but *all* points to lose. Without that, a machine idling on its suspension at the boundary toggles continuously, and this cue is meant to mark a decision. `vehicle_geometry_sim.lua` scenario 9 runs 200 ticks of threshold wobble and asserts zero state changes.
    - It rides on the **docking toggle** rather than a key of its own — same act, other end, and a second mode key is one more thing to remember mid-manoeuvre.
    - Only `COMMITTED` is spoken. The other two are waypoints you pass through, and narrating each would talk over the manoeuvre it describes. `NONE` fires no cue at all: leaving the gate is not an event, and marking it would fire constantly while manoeuvring in a yard.
    - **The committed earcon RISES where the docking lock chime FALLS.** They are the only two-note figures in the mod, and opposite contours are what stop "arrived at the null" and "armed to drop" being confused — an expensive confusion, given what the second one leads to.
  - **Ramp mode is the instrument's second ANSWER, not a second instrument.** Everything else in this file measures from an implement to a load; ramp mode measures from the vehicle you are driving to the drive-in mouth of a ramp on some other machine. Same toggle, same wire format, same three audio channels, so there is no second mode key and no second set of tones to learn. The mode is auto-selected per tick and never sticky: implement fitted → today's behaviour byte for byte; otherwise the nearest vehicle with a `rampGeometry` resolve in range. The one structural change was turning the `not implCids` early return into a **fall-through** — a machine with no implement is exactly the machine you drive *into* a ramp — and every other early return is untouched and still names itself, which is what stops ramp work being able to regress the implement case. `SLAM:` is implement-only, and so is the `NEAR:`/`CLEAR` proximity speech: on a car there is no bucket.
    - **The origin is `vehicleGeometry.contactPoints(playerID, +1)`**, the identical non-implement fallback `vehicleScanner` already uses — reused rather than reinvented, so the ramp readout and the scanner bearing measure from the same point on the same vehicle. Forward band unconditionally, never `activeDirection`: you drive *forwards* into a cannon.
    - **`range` is measured ALONG the ramp axis, not straight-line to the mouth centre.** Straight-line inflates with lateral offset, so drifting sideways would sound like backing away, and it would bottom out at the offset instead of at zero. `lateral` is positive-LEFT as everywhere else in the mod. `yaw` is deliberately **not** folded to ±90 the way the implement's squareness is — a pallet has no front or back as far as the tines are concerned, and a ramp emphatically does.
    - **That range is SIGNED, and the feed ceiling is the in-plane distance rather than the range.** It used to be floored at zero, on the reasoning that crossing the mouth plane should read as arrived. True of the last half metre, false of everything else: the negative half-space is the *entire hemisphere behind the mouth plane*, which is where a driver circling a sixteen-metre cannon looking for its entrance spends nearly all of their time. The floor pinned the range channel at 0 throughout — the pulse ran at its contact rate and never moved, and the readout said "mouth 0.0 feet" from ten metres away on the wrong side, which is the bug this whole phase split came out of. Consumers apply their own floor. Testing the *signed* range against `RAMP_REPORT_M` would then leave the whole negative half-space permanently under the ceiling, so the gate is `hypot(range, lateral)` — which is also the honest answer on the approach side, where ten metres out and eight across is fifteen metres from the mouth, not ten. `ramp_resolve_sim.lua` scenario 9 asserts both and asserts what the floored form reported.
    - **`M.rampTruth()` prints the sign in words.** Negative means behind the mouth plane, and that one fact is worth more than the other three numbers put together while the entrance is still being hunted for.
    - **The width margin takes the WORSE side of the player's box** (`max(|minR|, |maxR|)`), because the vehicle origin is not necessarily on its lateral centreline and reporting clearance from the roomier side of an off-centre car is the one error here that ends with a mirror torn off. `-1` is the not-measured sentinel and must never be `0`, which reads as exactly touching both walls.
    - **Ranges are per mode, not a raise of `REPORT_M`** (`RAMP_REPORT_M` 45.0 against 6.0): the implement instrument is short-range on purpose. `RAMP_SEARCH_M` is 70 rather than reusing `BROAD_RADIUS_M`, because that prefilter measures to the object's *reference node*, which on a ~16 m cannon sits ten to fifteen metres behind the mouth — a mouth twenty metres away can have its object centre thirty-five metres away and be filtered out before it is ever looked at; it has to keep clearing `RAMP_REPORT_M` by more than half a machine length or it silently becomes the real ceiling.
    - **The FEED ceiling and the range at which anything is sonified are different jobs**, and conflating them killed the instrument in the one place it was most needed. At 20 m *measured to the mouth*, parking beside a sixteen-metre cannon at the barrel end puts the mouth outside the feed, so the mod sent `DOCKCLEAR` — which clears the reason as well as the reading — and `F9` `I` answered "Nothing in range" about a machine the scanner was reporting nine feet away, with the toggle-on message naming no mode. Indistinguishable from a switched-off instrument. The feed now runs to 45 m while audio fades out at `DOCK_RAMP_MAX_RANGE_M` (25), and that gap is the design: **the spoken readout keeps answering after the tones have gone quiet**, which is the state someone reaches for the key in. The phrase names it (`too far for tones`) rather than leaving unexplained silence.
    - **Ramp mode never sends `DOCKCLEAR`.** "There is no ramp" is already a `DOCKFAIL`; "there is one and it is over there" is the most useful sentence this instrument can produce for someone who cannot find it, so past the ceiling it sends `DOCKFAIL:<name> ramp mouth <n> metres away`, rounded to the metre so the dedupe still holds most ticks. `ramp_resolve_sim.lua` scenario 9 greps for the absence of the `send("DOCKCLEAR")` **call** — not the word, which appears in the comment explaining why it is not there.
    - `M.rampTruth()` is the ramp analogue of `dockTruth()` and earns its place by the same argument: this resolve's failure mode is "it landed on the wrong node", which produces confident, plausible numbers and is invisible to every kind of inspection except printing what it chose.
    - **The ramp align teleport (`RAMPALIGN`)** is the other half of the act `vehicleScanner`'s `ALIGN` performs. That one places you to *reverse* onto a trailer coupler; this places you to *drive up* a ramp, 20 ft (`RAMP_ALIGN_STANDOFF_M`) of clear air in front of the mouth and square on its axis. Same key (`F9` `Shift+V`), because coupling to a trailer and driving up its ramp are the same act from the seat — get me squared up to that machine — and a second keybind is one more thing to remember mid-manoeuvre, the argument the slam gate already made for riding the docking toggle.
      - **The disambiguator is the docking instrument being on**, which is not a flag invented for the purpose: it is what you would already be running to drive onto something, and it is the half of the mod that knows where a ramp mouth is at all. The mod re-checks `dockActive` itself rather than trusting Python, because a `RAMPALIGN` arriving with the instrument off is a version skew, not a request. It also refuses when `implCids` is set — the instrument decides implement-vs-ramp per tick from whether an implement is fitted, and the align has to use the same rule or the key teleports you to something the readout was never talking about.
      - **It does not fall back to the coupler align when no ramp is found.** With the instrument on you asked for a ramp; being quietly lined up to reverse onto a tow hitch instead is a surprise, and `findRampTarget`'s short reason already names the machine and is already speech-sized.
      - **`mouth.axis` points INTO the ramp**, so the standoff *subtracts* it and `quatFromDir(mouth.axis, up)` faces the driver **at** the ramp. The coupler align does the opposite on both counts (`quatFromDir(awayDir, …)`) because that manoeuvre is reversed into. Either negation reads as perfectly reasonable in isolation, so `ramp_resolve_sim.lua` scenario 16 greps both files and asserts they disagree.
      - **The standoff is measured nose-to-mouth, not origin-to-mouth**, using `vehicleGeometry`'s gap-trimmed `ext.maxF`. The reference node is metres from the front bumper on a semi, so an origin-referenced standoff gives a hatchback twenty feet of run-up and a truck about eight; the number being promised is the gap the driver can see. `RAMP_ALIGN_NOSE_FALLBACK_M` is deliberately generous, because over-estimating parks you further back while under-estimating parks you inside the mouth.
      - **Ground height comes from the player, not from `mouth.floorZ`** — a tilt deck's mouth floor is a metre in the air until the deck is down — floored against terrain so a teleport across a dip cannot bury the vehicle. `spawn.safeTeleport(player, pos, rot, nil, nil, nil, false, false)` — `checkOnlyStatics` and `visibilityPoint` stay nil for the reason `vehicleScanner` records (a boolean `visibilityPoint` throws inside `LuaVec3.__sub` and the teleport silently never happens), and the trailing `false` is `resetVehicle`, which is **never** left at its default here (see **No teleport in this mod may reset the vehicle**).
      - **It reports when the ramp is not DEPLOYED, which is the failure that made the key dangerous.** The align is geometrically perfect against a stowed deck — it will happily park you twenty feet in front of a lip 1.30 m in the air and say only where you are, which from the seat is driving nose-first into the back of a truck, and then tilting the deck down onto the car. The teleport code already *knew* a mouth can be a metre up (it is why the standoff Z comes from the player rather than from `mouth.floorZ`) and simply never passed the fact on. Reported, never enforced: lining up before deploying is a reasonable order to work in, and refusing would make the key useless in exactly that case. Spoken **before** the width margin, because a ramp you cannot climb settles the question the margin was asking. `RAMP_ALIGN_LIP_SAY_M` is 0.30 on both sides, and the measured poses sit either side of it with a wide margin — it is not balancing anything finely.
      - **It centres the vehicle's BODY on the ramp axis, not its reference node**, and quotes the **symmetric** half-span as the margin. Those are different points on a real car: an `etk800` wagon measures `minR -0.680` / `maxR +1.340` — 2.02 m wide with its reference node a third of a metre off its own centreline — so placing the node on the axis put the body 0.33 m over, leaving **0.61 m on one flank and −0.05 m on the other** in a mouth the car clears by 0.28 m a side. The readout then announced "you do not fit", which was correct about where the align had just parked the car and wrong about the car. Measured after the fix: flanks at ±1.010 in a ±1.292 mouth. **The worse-side rule in `playerHalfWidth` is unchanged and still used by the live `DOCK:` readout** — there the driver is wherever they are and the margin has to come from the flank that hits first; only the align gets to *choose* its lateral position, so only the align should be centring anything.
      - **The width margin's "not measured" is the literal `NA`, not the `-1` the `DOCK:` line uses.** There the margin is a continuous channel recomputed at 10 Hz, where a real `-1` could only be transient; here it is a one-shot clearance figure and a genuine −1.00 m margin is exactly the case the warning exists for. A sentinel that can be a real value is a sentinel that silences the warning.
  - **The command socket is checked, closed and retried, and each of those is a separate bug this file has already had.** `setsockname` **returns `nil` plus a message rather than throwing**, so the `pcall` around it reported success on a socket bound to nothing — the extension went deaf with *nothing in the log*, while still sending normally, because a UDP sender needs no bind. Measured: every other command port in the mod was listening and 4470 was absent from `netstat` entirely; `DOCK_ON`, `REBUILD` and `RAMPALIGN` all went into the void, so `F9` `Shift+V` spoke "Aligning to ramp" and then did nothing — not even a failure, since the failure path is on the far side of the socket that never opened. What *caused* the failed bind is the second bug: **`setupSockets` closes the sockets held by THIS module instance**, and `extensions.reload` builds a fresh instance whose locals are nil, so it closes nothing and the outgoing instance keeps the port. Hence `M.onExtensionUnloaded`. And because a failed bind is otherwise permanent, `CMD_BIND_RETRY_S` re-arms it — **that retry is the recovery path, not a precaution, and the whole cycle has been watched end to end.** The first live reload of the patched files was an accidental controlled experiment: the *outgoing* code had no unload hook, so eight ports were leaked at once and `implementProximity` — the one file that already had the hook — was the only one to rebind. The retry could not take the other eight while the old module tables were still referenced (a socket held that way is not one the collector is about to free) and ticked uselessly for two minutes. Then Ctrl+L, which **did not re-load these extensions at all** — there is no load line for any of them at that timestamp, so `setupSockets` never ran a second time — and all thirteen ports came back through `retryCmdBind` within one frame of each other, the moment those tables went away. So the three fixes divide cleanly: the checked return makes the failure *visible*, the unload hook *prevents* the leak, and the retry is the only thing that *heals* one — without it a Lua reload would not have fixed this, and the mod would have stayed deaf until the game was restarted. **All three fixes are now in every one of the fourteen listening extensions, written in the same shape in each** — `local bound, berr = udpCmd:setsockname(...)`, `M.onExtensionUnloaded`, and a `retryCmdBind(dtReal)` called as the first line of `onUpdate` — precisely so that one grep can police them; `vehicle_geometry_sim.lua` scenario 12 is that grep, and it additionally enumerates the extensions directory and fails on any file that binds a port without being on its list, so a new listener cannot be added without the three. It verifies the enumeration itself worked, because a shell that cannot list the directory would otherwise turn the whole check into one that passes because it found nothing.
  - **The `RAMPSELF:` line is the one readout in this file about the machine UNDER you.** Everything else here measures from one machine to another. It sits beside the `CANNON:` line rather than inside the docking toggle, and is gated on nothing, for the same reason that one is: you tilt a deck and run it out while parked, with the instrument off, before any alignment work has begun. It carries the ramp's live `mouthFrame.pitchDeg` plus the hydraulics payload forwarded **verbatim** — this extension knows where the ramp is, the vehicle VM knows where the rams are, and neither needs to learn the other's job. `rampHydByVeh` is stored per vehicle for exactly the reason `implByVeh` is (every VM pushes its own; only the driven one may answer), and `lastRampSelf` is latched so the line is sent on change only. **A vehicle switch clears the latch but never the stored pushes** — the hauler you climbed out of is still holding its deck where you left it, and clearing the latch is what forces the line to be re-stated for the new machine, including the `NONE` that says it has no ramp.
  - **The entry gate** answers the question none of the three continuous channels can: lateral, vertical and range can all be nulled perfectly and the tines still not go in, because a tilted implement climbs through the selected band's whole thickness after a few centimetres of travel and hits the far side. `resolveEntry` is pure trigonometry on numbers already resolved — the floor plane's world pitch `θ` (`edgeMid → heelMid`, the same axis the vehicle VM reports as tilt), the tine length `L`, and the band thickness `T` — giving a usable insertion depth `d = min(L, T / sin|θ|)`, or `L` below `IMPL_ENTRY_LEVEL_DEG`. Hysteretic (`IMPL_ENTRY_MIN_DEPTH_M`/`IMPL_ENTRY_EXIT_DEPTH_M`) for the same reason `SLAM_CLEAR_*` is: it drives a one-shot earcon, and a machine breathing on its suspension at the threshold would machine-gun it.
    - **Reported as a depth, not as a maximum angle.** "The tines go in 15 centimetres" is directly actionable; "you are 12° over the limit for this band" asks the operator to redo geometry the mod has already done.
    - `θ` and `d` ride as **two fields appended to the end of the `DOCK:` line**, parsed positionally with a length guard — the same optional-tail contract the scanner packet's fourth field uses, because `bng_mod/` is a live junction and the two halves genuinely do go out of step. `d = -1` is the "could not measure" sentinel; Python treats that and a missing field as silence rather than as `0`, which would read as *perfectly level*.
    - Spoken only when it is bad news (`_dock_phrase` gains a "tines enter … , too steep" clause), and marked by a **one-shot earcon on the transition into enterable** — a single high sine at `ENTRY_CUE_HZ`, because both two-note contours are taken and a third would be one distinction too many mid-manoeuvre. Python edge-detects with the *same two thresholds* the mod applies; using only the enter threshold there would re-introduce exactly the chatter the mod's hysteresis exists to prevent. Losing the target resets to "not known", so re-acquiring an already-enterable band is silent — the cue means "you can go in *now*".
